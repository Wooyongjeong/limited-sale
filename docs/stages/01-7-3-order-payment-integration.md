# 1-7-3 사용자 결제 연동과 주문 마무리

상태: 2026-11-16 정책·구현 계획 확정 후 사용자가 "ㄱㄱ"로 구현 시작을 지시했다. 워커 구현·주 에이전트 독립 리뷰와 검증·위키 갱신을 완료했다.

[작업 분할](01-7-order-payment.md), [기술 계약](01-contracts.md), [PG 계약](01-7-2-mock-pg-http-and-scenarios.md)을 따른다.

## 확정 정책

- 본인 주문의 결제 요청은 POST /api/v1/orders/{orderId}/payment로 제공한다. 기존 인증·CSRF 보호를 적용하고, 없는 주문과 타인의 주문은 404다. 금액·PG 키는 클라이언트가 지정하지 않는다.
- 주문 생성과 결제 요청을 분리하며 주문에 고정된 금액·PG 키만 사용한다. 결제 실패·만료 주문을 새 키로 되살리지 않는다.
- 첫 결제는 결제 시작 상태를 DB에 커밋한 뒤 PG를 호출한다. HTTP 통신 중 DB 트랜잭션·행 잠금을 유지하지 않는다.
- 처리 중·결과 미확인 재시도는 PG 조회 우선이다. 조회 404이고 주문 생성 후 5분 전이면 같은 키로 결제를 재전송한다. 404만으로 점유를 해제하지 않는다.
- 주문 생성 후 5분 이상이면 새 결제를 시작하지 않고 PG 종료 확인으로 진입한다. 성공이면 주문 확정, 실패면 결제 실패, CLOSED면 만료로 정리한다. 통신 실패·결과 미확인은 점유를 유지하고 202다. DB 시각으로 경계를 판정한다.
- 결제 성공 200, 처리 중·결과 미확인 202의 data는 기존 주문 상세에 paymentStatus를 추가한 형태다. 상세 GET에도 paymentStatus를 제공하며 GET은 PG를 호출하거나 상태를 변경하지 않는다.
- 명확한 실패는 409/PAYMENT_DECLINED·data:null, 종료 확인된 만료는 409/ORDER_EXPIRED·data:null이다. 이미 최종 정리된 주문의 재요청은 PG를 다시 호출하지 않고 기존 결과를 반환한다.
- 기본 3초는 한 사용자 요청의 PG 통신 전체 예산이다. 조회와 재전송에도 남은 예산만 사용한다. DB 처리까지 포함한 API 전체 응답 시간 보장은 아니다. 대기 설정은 변경 가능하게 한다.
- 처리 중·미확인은 사용자 재시도에도 기본 10초 간격을 적용하고 그전에는 저장된 상태로 202를 반환한다. 재조회 시각은 DB에 영속 저장한다. 5분 만료에 도달하면 간격과 관계없이 종료 확인을 허용한다. 시간 값은 설정 가능하게 한다.

사용자는 만료 시 PG 종료 확인, 조회 우선 재시도, 주문과 결제 상태의 동시 반환, 전체 PG 통신 예산, 사용자 재시도의 10초 간격을 각각 선택했다. 임의 시간 만료만으로 수량을 해제하지 않고, 중복 결제와 불필요한 재조회를 줄이는 것이 선택 이유다.

## 구현 설계

1. order.application이 본인 주문·상태·DB 시각을 검사하고 결제 시작 또는 재조회 가능 여부를 짧은 트랜잭션에서 결정한다. 동시 요청이 시작·조회 구간을 무제한 중복 실행하지 않도록 주문 잠금과 영속 재조회 시각으로 조정한다.
2. payment.api를 통해 준비된 고정 키·금액으로 PG 결제·조회·종료를 호출한다. 네트워크 응답은 상태·키·금액·형식까지 검증한다. 타임아웃·잘못된 응답을 결제 거절로 간주하지 않는다.
3. payment가 PG 결과를 보관한다. 성공·실패·종료 등 최종 결과는 늦은 PROCESSING·UNKNOWN 응답으로 되돌리지 않는다.
4. order가 최종 결제 결과를 확인하고 주문·판매 이벤트 수량·사용자 수량·점유 기록을 하나의 로컬 트랜잭션으로 마무리한다. 기존 주문 잠금 → 이벤트 → 사용자 수량 → 점유 순서를 유지하며 확정·해제는 중복 적용하지 않는다.
5. 결제 결과 저장과 주문 마무리 사이의 실패를 허용하되 재시도에서 저장된 결과를 다시 적용한다. 내부 DB 장애를 정상 202나 결제 거절로 감추지 않는다. 자동 복구는 다음 단계에서 담당한다.
6. 주문·결제의 순수 상태 규칙과 JPA 엔티티를 분리하고 도메인 간에는 api만 참조한다. 외부 요청·응답은 presentation의 독립 파일로 관리한다.

이벤트 종료·중단은 기존 점유의 결제·확정·해제를 막지 않는다. 사용자 인증이 끝난 뒤 이미 시작한 서버 내부 마무리도 세션을 다시 요구하지 않는다.

## 검증 기준

- 정상 결제 시 주문 CONFIRMED, 점유의 확정 전환, 이벤트·사용자별 수량과 결제 금액 일치.
- 거절·CLOSED 시 각각 PAYMENT_FAILED·EXPIRED, 수량 해제와 중복 요청의 멱등성.
- DELAY·RESPONSE_LOSS·통신 장애에서 점유 유지와 202, 이후 조회·재시도로 최종 수렴.
- 동시 첫 요청·재시도·늦은 응답에도 최종 상태 불변, 이중 확정·해제 및 초과 판매 없음.
- 만료 경계와 PG 성공/종료 경쟁, 종료 확인 불가 시 점유 유지.
- 조회 후 재전송이 합산 통신 예산을 초과하지 않으며 10초 간격·만료 예외가 재시작 후에도 유지.
- 인증·권한·CSRF·엄격 입력·본인 주문 확인과 내부 정보 비노출.
- 결제 결과 저장 후 주문 마무리 실패의 재시도, GET의 읽기 전용 동작.
- 격리 MySQL·실제 HTTP 통합 검사, 이전 전체 회귀와 전체 build.

## 워커 구현과 검증 근거

- 주문 결제 요청은 본문 없이 받는다. 본인 주문만 조회하며 주문 상세에 `paymentStatus`를 포함한다. 주문 잠금 후 DB 시각으로 재시도·만료를 판정하고 통신 전에 요청 의도와 다음 재조회 시각을 저장한다.
- `payment.api`를 통해 고정 키·금액으로 PG에 요청한다. 조회 404에는 만료를 다시 판정하고 남은 통신 예산으로 결제 또는 종료를 요청한다. HTTP 응답 본문 수신도 전체 시간 예산에 포함한다. PG 상태·키·금액·응답 형식이 맞지 않으면 결과 미확인으로 보관한다.
- 결제 결과 저장을 주문 마무리와 별도 트랜잭션으로 처리한다. 최종 결제 결과는 늦은 응답으로 되돌리지 않으며, 주문·이벤트·구매자 수량·점유를 한 트랜잭션에서 마무리한다. 주문 마무리 실패 후에는 저장된 결제 결과를 재적용한다.
- 기본 통신 예산 `limited-sale.payment.timeout=PT3S`, 사용자 재조회 간격 `limited-sale.payment.retry-interval=PT10S`, 기존 주문 만료 `limited-sale.order.expiration=PT5M`은 설정할 수 있다.
- Java 21의 `./gradlew clean build`가 성공했다. 판매 앱 단위 55건·통합 82건, Mock PG 단위 11건·통합 15건이며 실패·오류·건너뜀은 각각 0건이다. 로그는 `/tmp/173-clean-build-verified.log`다.
- 실제 HTTP와 격리 MySQL·Redis로 성공, 거절, 종료, 응답 유실, 지연, 통신 장애, 동시 요청, 늦은 응답, 마무리 실패 후 재시도, 재조회 시각의 다른 앱 인스턴스 공유, 인증·CSRF·소유권과 읽기 전용 조회를 검사했다. HTTP 본문 수신 지연과 조회 후 재전송의 공유 예산도 검사했다.
- 첫 전체 빌드는 새 `paymentStatus` 필드를 기존 응답 필드 검사에 반영하지 않아 실패했다. 기대값 수정 후 해당 검사와 전체 빌드를 다시 실행했다. 앞선 기준 빌드 종료 코드 130은 워커가 직접 중단해서 발생했으며 환경 실패가 아니다.

## 주 에이전트 독립 검증과 위키 갱신

- 결제 시작·재시도·만료 판정, PG 호출의 트랜잭션 분리, 결과 검증과 최종 상태 유지, 주문·수량 마무리의 잠금과 원자성, API 입력·응답 및 테스트 코드를 검토했다. 추가 수정이 필요한 코드 문제는 발견하지 못했다.
- 마지막 코드 변경 이후 주 에이전트가 Java 21 `./gradlew clean build`를 직접 실행해 2분 59초에 성공했다. XML 결과는 판매 앱 단위 55개·통합 82개, PG 단위 11개·통합 15개로 총 163개이며 실패·오류·건너뜀 모두 0개다. 로그는 `/tmp/limited-sale-173-primary-build.log`다.
