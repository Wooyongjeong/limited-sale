# 1-7-2 Mock PG HTTP API와 장애 재현

상태: 2026-11-13 구현·리뷰 보완·주 에이전트 독립 검증·위키와 도식 갱신 완료. 커밋·푸시·PR·머지는 미진행.

[1-7 작업 분할](01-7-order-payment.md), [기술 계약](01-contracts.md)의 기존 합의를 따른다. 이 문서는 이번 단계에서 추가로 확정한 정책과 구현 기본안이다.

## 범위

- 별도 Mock PG 서버의 결제·조회·종료 HTTP API와 키별 영속 결과를 구현한다.
- 판매 서버에는 로컬·테스트 환경의 ADMIN 시나리오 설정 API를 추가한다. 주문 UUID를 받아 내부 결제 키로 설정을 전달한다. 설정만으로 결제를 시작하지 않는다.
- 판매 서버의 사용자 결제 요청·PG 업무 연동·주문 확정·점유 해제는 1-7-3, 주문 복구 실행기는 1-7-4다. 이번 ADMIN 설정 전달에 필요한 HTTP 연동만 먼저 구현한다.
- Terra high 워커 구현 → 주 에이전트 독립 리뷰·검증 → 문제 해결까지 보완 → 위키·Excalidraw 도식 갱신·검증 순서다.

## 사용자와 확정한 정책

| 항목 | 확정 내용 |
|---|---|
| 기본 동작 | 시나리오 미지정 결제 키는 정상 성공 |
| 설정 범위 | 결제 키별 지정, 결제·종료 처리 시작 후 고정 |
| 설정 재시도 | 처리 전 변경 가능. 처리 후 같은 설정은 200, 다른 설정은 409 |
| 설정 영속성 | DB에 저장하여 PG 재시작 후 유지 |
| HTTP 결과 | 성공·거절 등 확정 결과는 200과 data.status, PROCESSING은 202 |
| HTTP 충돌·없음 | 같은 키의 다른 금액은 409, 없는 결제 키 조회는 404 |
| 정상 SUCCESS | SUCCEEDED 저장 후 즉시 응답 |
| 거절 DECLINE | FAILED 저장 후 즉시 응답 |
| 처리 지연 DELAY | PROCESSING·완료 예정 시각 저장. 기본 10초 뒤 성공 판정 가능 |
| 성공 응답 유실 RESPONSE_LOSS | SUCCEEDED는 먼저 저장하고 최초 결제 응답만 기본 5초 지연 |
| 지연 범위 | 두 지연 시나리오의 시간은 각각 1~600초로 지정 가능 |
| 유실 횟수 | 키별 최초 한 번에만 응답 지연 적용. 후속 조회·재요청에는 저장된 성공 즉시 반환 |
| 관리자 경계 | 판매 서버의 로컬·테스트 ADMIN API에서 주문 UUID로 설정. 일반 사용자는 시나리오 지정 불가 |

Mock PG의 확정 실패 200과 판매 서버가 사용자에게 반환할 결제 거절 409는 서로 다른 계약이다. 판매 서버의 PAYMENT_DECLINED 계약은 유지한다.

## 지연 결제의 시간과 종료

완료 예정 시각은 DB에 저장한다. 별도 PG 스케줄러 없이 조회·결제 재요청·종료 요청에서 행 잠금을 획득한 뒤 별도 MySQL UTC 시각 쿼리로 판정한다.

- 현재 시각이 예정 시각 미만이면 PROCESSING을 유지한다. 이때 종료를 요청하면 CLOSED로 확정한다.
- 현재 시각이 예정 시각 이상이면 SUCCEEDED로 먼저 확정한다. 이후 종료를 요청해도 성공을 반환한다.
- SUCCEEDED·FAILED·CLOSED는 최종 상태이며 반대로 바꾸지 않는다. 이미 FAILED이면 종료에도 FAILED를 유지한다.
- 존재하지 않는 결제 키의 종료는 CLOSED를 영속 저장하여 늦은 결제가 성공하지 못하게 한다.
- 결과 조회 404만으로 판매 서버가 주문 점유를 해제해서는 안 된다.

지연 응답 대기는 DB 커밋·잠금 해제 후에 수행한다. RESPONSE_LOSS는 실제 패킷 유실 대신 응답 지연으로 호출자 타임아웃을 재현한다. 기본 판매 서버 대기 3초보다 긴 5초를 사용하며, 설정을 바꿀 때도 실험 클라이언트의 타임아웃보다 길게 지정해야 한다. DB의 한 번 소비 표시를 먼저 커밋해 동시 재요청·재시작이 여러 응답을 의도적으로 지연시키지 않도록 한다.

## 구현 기본안

다음 경로·DTO·인증 방식은 사용자가 계획으로 확정한 구현 기준이다. 계획 확정은 구현 시작 지시와 구분한다.

| 대상 | 경로 기본안 | 입력·응답 |
|---|---|---|
| PG 결제 | POST /api/v1/payments | pgKey UUID·amount 정수 |
| PG 조회 | GET /api/v1/payments/{pgKey} | 키별 현재·최종 결과 |
| PG 종료 | POST /api/v1/payments/{pgKey}/close | amount 정수 |
| PG 설정 | PUT /api/v1/simulations/{pgKey} | scenario·해당 시나리오의 delaySeconds |
| 판매 ADMIN 설정 | PUT /api/v1/admin/orders/{orderId}/payment-simulation | scenario·해당 시나리오의 delaySeconds |

- PG 응답 data는 pgKey·amount·status·createdAt·updatedAt·finalizedAt을 기본으로 한다. 판매 ADMIN 응답에는 내부 PG 키를 노출하지 않고 주문 UUID·설정·지연 시간을 반환한다.
- 판매 앱과 PG 앱은 소스·엔티티·common 구현을 직접 공유하지 않는다. PG도 동일한 공통 응답 모양과 도메인별 코드 enum, 별도 Request·Response 파일을 갖는다.
- PG 업무·설정 API는 환경변수로 주입하는 전용 인증값을 X-Mock-PG-Key 헤더로 검증한다. health는 공개한다. 인증값 누락·불일치는 401이며 비밀값을 로그·응답에 넣지 않는다.
- 판매 ADMIN 설정은 ADMIN 세션·CSRF를 검증하고 로컬·테스트 환경에서만 노출한다. 주문 확인은 order.api, PG 키 확인과 설정 전달은 payment.api를 사용한다. 다른 도메인 저장소를 직접 참조하지 않는다.
- 가격은 기존 합의대로 1~10^15원의 long/BIGINT 정수다. 엄격한 JSON·UUID·enum·시간 범위 검증 실패는 400이며 시스템 장애와 확정 업무 결과를 구분한다.
- SUCCESS·DECLINE에는 delaySeconds를 받지 않고, DELAY·RESPONSE_LOSS에는 생략 시 기본값을 적용한다. 고정 이후 설정 비교는 기본값을 적용한 실제 설정으로 수행한다.
- PG 시나리오 저장은 별도 테이블을 새 Flyway 버전으로 추가하는 안이다. 결제 미시작 키도 설정할 수 있으므로 결제 테이블을 부모로 하는 FK를 두지 않는다. 설정 저장을 PROCESSING 결제 생성으로 오해하지 않게 분리한다.
- 같은 키의 결제·종료·설정 경쟁은 일관된 DB 잠금 순서와 유니크 제약으로 직렬화한다. 정확한 키 중복만 분류하며 실패 트랜잭션 안에서 재조회하지 않는다. Spring Data JPA·도메인/엔티티 분리를 유지한다.
- 적용된 Flyway 이력과 개발 DB 데이터·볼륨은 보존한다.

## 워커 구현·검증 기록

- PG 설정을 별도 V3 테이블에 저장하고, 같은 키의 설정 행을 먼저 잠근 뒤 결제 행을 잠근다. 최초 설정 행 삽입이 충돌하면 해당 트랜잭션을 종료하고 새 트랜잭션에서 다시 조회한다. 기존 PG V1·V2는 수정하지 않았다.
- 지연 결제는 잠금 획득 후 별도 DB 시각으로 판정한다. 응답 유실 시나리오는 성공과 소비 표시를 커밋한 뒤 최초 HTTP 응답만 지연한다.
- 판매 서버의 local/test ADMIN 설정은 주문 API와 결제 API를 거친다. PG 설정 전달은 DB 트랜잭션 밖에서 이루어지며 기존 트랜잭션 안에서 호출하면 거부한다. PG 충돌은 409, 연결·응답 오류는 503으로 구분한다.
- Java 21과 격리된 Testcontainers MySQL·Redis를 사용한 `./gradlew clean build` 성공. 판매 앱 단위 43개·통합 66개, Mock PG 단위 9개·통합 13개가 통과했으며 실패·오류·건너뜀은 각 0개다. 로그: `/tmp/ticketing-1-7-2-clean-build-verified.log`.
- 실제 SQL 잠금 대기를 관찰한 후 예정 시각 경과를 검증했고, PG 애플리케이션 컨텍스트 재시작, 짧은 호출자 타임아웃, 응답 대기 중 재조회, 금액·설정·종료 경쟁과 ADMIN 보안·환경 제한을 검사했다. Flyway의 MySQL 8.4 지원 경고와 Jackson 사용 중단 예정 API 컴파일 경고는 남아 있다.
- 이 최초 워커 보고 뒤 주 에이전트가 독립 검증을 수행했다. 보완과 최종 결과는 아래에 기록한다.

## 리뷰 보완 기록

- 주 에이전트가 실제 HTTP에서 `/api;probe/v1/payments`의 인증 우회를 재현했다. 워커는 정확한 `/actuator/health` GET·HEAD만 공개하고 그 밖의 요청에 기본적으로 인증을 적용했다. 실제 HTTP와 격리 MySQL에서 기본 경로와 세미콜론·인코딩·경로 변형 8종에 결제·조회·종료·설정을 요청해 각각 400 또는 401을 확인했고, 결제·설정 기록이 생성되지 않음을 확인했다. 인증된 결제와 공개 health GET·HEAD는 정상 동작했다.
- 외부 PG 응답의 `delaySeconds`가 32비트 정수로 변환 가능한지 확인한 뒤 기대값과 비교한다. 실제 HTTP 스텁에서 `4294967301`, `-4294967291`, `18446744073709551621`을 거절하고 정상 정수 `5`를 수용했다. 기존 `httpStatus` 검사는 유지했다.
- 보완 후 Java 21 `./gradlew clean build` 성공. 판매 앱 단위 45개·통합 66개, Mock PG 단위 9개·통합 14개가 통과했으며 실패·오류·건너뜀은 모두 0개다. 로그: `/tmp/ticketing-1-7-2-review-clean-build.log`. PG 시각 처리와 마이그레이션은 변경하지 않았다.
- 이후 관리자 오류 응답도 보완했으며 최종 독립 검증 결과는 아래에 기록한다.

## 관리자 오류 응답 보완 기록

- 주 에이전트가 시나리오 설정 컨트롤러의 415·예상 밖 500에 기존 주문 예외 처리기가 적용되지 않는 문제를 발견했다. 워커는 해당 처리기의 적용 대상을 확장하고 입력 오류 전용 예외를 사용해 서비스 내부 `IllegalArgumentException`이 400으로 잘못 분류되지 않도록 했다.
- 실제 HTTP에서 `text/plain` 요청의 415와 격리 MySQL의 결제 테이블 조회 실패에 따른 500을 재현해 `httpStatus`, `code`, `data`, `message`와 내부 정보 비노출을 확인했다. MVC 서비스 예외 검사와 기존 400·409·503, ADMIN 권한·CSRF·프로필 검사도 통과했다.
- Java 21 `./gradlew clean build` 성공. 판매 앱 단위 46개·통합 68개, Mock PG 단위 9개·통합 14개가 통과했고 실패·오류·건너뜀은 각 0개다. 로그: `/tmp/ticketing-1-7-2-advice-clean-build.log`; 수정 전 회귀 실패와 집중 검사 로그는 각각 `/tmp/ticketing-1-7-2-advice-red.log`, `/tmp/ticketing-1-7-2-advice-green.log`다.

- [Mock PG 위키](../wiki/mock-pg.md)를 추가해 관리자 설정 흐름, 네 시나리오, 지연 중 종료, 직접 HTTP 실험 예시와 코드 읽는 순서를 설명했다. 관련 위키의 구현 범위를 맞추고 판매 앱의 사용자 결제 연동은 아직 1-7-3임을 명시했다.
- 관리자 설정과 지연 시나리오 도식 2개를 추가하고 서버 경계·마이그레이션 도식을 수정했다. `npm run render --prefix tools/wiki-diagrams`로 SVG 31개를 렌더링하고 변경한 그림 4개를 이미지로 직접 확인했다.

- 사용자 결제 API·PG 결과에 따른 주문 확정과 점유 해제는 1-7-3, 복구 실행기는 1-7-4에서 협의 후 진행한다. 다음 단계는 자동 시작하지 않는다.

## 추가 코드리뷰와 주 에이전트 직접 수정

사용자가 이번 리뷰의 수정은 워커 대신 주 에이전트가 직접 하도록 지시했다. 아래 두 문제를 직접 재현하고 수정했다.

- **입력 오류와 내부 장애의 분류:** PG 컨트롤러가 모든 `IllegalArgumentException`을 400으로 처리해 저장 계층의 내부 오류도 사용자 입력 오류로 반환했다. 실제 서비스와 대체 저장소를 연결한 MVC 검사에서 기대 500·실제 400으로 실패를 확인했다. 입력 검증 전용 `InvalidPaymentInput`을 도입하고 경계에서만 변환했다. 결제·조회·종료·설정 네 경로의 내부 오류는 공통 500으로, 잘못된 UUID·금액·시나리오·지연은 기존 400으로 응답하며 내부 상세는 노출하지 않는다.
- **동시 최초 생성의 설정 덮어쓰기:** 앱에서 UUID를 채운 `ScenarioEntity`는 기본 신규 판정에서 제외되어 `saveAndFlush`가 merge를 수행했다. 다른 요청이 먼저 DELAY·600초를 저장한 뒤 이전 요청의 기본 엔티티를 저장하면 SUCCESS·null로 바뀌는 것을 격리 MySQL로 재현했다. `Persistable`과 영속 콜백으로 신규 삽입을 명시해 정확한 PK 충돌을 발생시키고, 기존의 실패 트랜잭션 종료 후 재조회 경로를 사용하게 했다. 회귀 검사에서 먼저 저장한 설정의 보존과 삽입 충돌을 함께 검증한다.
- 수정 전·후 집중 검사 로그는 `/tmp/limited-sale-pg-direct-review-red.log`, `/tmp/limited-sale-pg-direct-review-green.log`, `/tmp/limited-sale-pg-insert-review-red.log`, `/tmp/limited-sale-pg-insert-review-green.log`다.
- [Mock PG 위키](../wiki/mock-pg.md)와 [영속 계층 위키](../wiki/persistence.md)에 예외 분류와 UUID 신규 삽입 처리 이유, 회귀 검사 링크를 반영했다. 기존 도식의 흐름·경계는 바뀌지 않았다.
- 직접 수정한 마지막 코드 이후 Java 21 `./gradlew clean build`가 2분 46초에 성공했다. 판매 앱 단위 46개·통합 68개, PG 단위 11개·통합 15개로 총 140개가 통과했고 실패·오류·건너뜀은 모두 0개다. 로그는 `/tmp/limited-sale-pg-primary-review-final-build.log`다. 위의 137개는 추가 리뷰 이전 기록이다.
- 위키 검사도 다시 실행해 16페이지·로컬 링크 332개·Excalidraw/SVG 31쌍이 통과했으며 `git diff --check`도 통과했다. 이번 직접 수정에서도 커밋·푸시·PR·머지는 수행하지 않았다.
