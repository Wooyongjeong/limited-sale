# 1-6 판매 이벤트 관리·조회

상태: 사용자 지시에 따라 주 에이전트가 직접 구현·코드리뷰·실제 MySQL 검증을 완료했다.

[1단계 정책](01-mysql-order.md), [기술 계약](01-contracts.md), [구조](../architecture.md)를 따른다.

## 기존 확정 정책

- 이벤트 하나에 제품 하나와 전용 재고를 설정한다. 총수량은 1~1,000,000개, 사용자 한도는 1~총수량이며 미설정 시 1개다.
- 이벤트 생성 시 product.api로 제품을 확인하고 제품명을 보관한다. 판매 가격은 관리자 지정이며 미지정 시 제품 기준 가격을 기본값으로 사용한다. 원화 정수 1~1,000,000,000원이다.
- 이벤트명 최대 100자, 설명 최대 2,000자다. 관리 API는 ADMIN 전용이며 조회는 공개한다.
- 시작 전에는 제품·가격·기간·총수량·구매 한도 수정과 삭제를 허용한다.
- 시작 후에는 이름·설명만 수정한다. 제품·가격·기간·총수량·한도 변경과 삭제는 거절한다.
- 관리자는 시작 전에도 중단·재개할 수 있다. 종료 전까지 기존 조건을 유지한 채 허용하며 기존 주문·결제·복구는 계속한다.
- 종료 후 신규 주문·재개는 불가하다. 기존 기록과 결제·복구는 유지한다.
- 시작 포함·종료 제외, UTC 저장이며 이벤트 잠금을 획득한 후 DB 시각으로 기간·운영 상태를 판정한다.
- 주문 점유·결제·복구는 1-7 이후 범위다. 이번에는 이벤트 관리·조회와 그 동시성 경계를 구현한다.

## 이번에 확정한 사항

- [x] 생성·시작 전 수정 시 미래 시작만 허용. 종료는 시작보다 뒤여야 하며 즉시 시작 기능은 제외
- [x] 전체 이벤트 최신 등록순(ID 내림차순), 선택 productId·상태 필터. 기본 20·최대 100 페이지, 검색 제외
- [x] 공개 수량은 총수량만 제공. 구매 가능·점유·확정 수량은 개별 필드로 제공하지 않음
- [x] 상태는 종료 → 중단 → 예정 → 품절 → 진행 순서로 계산
- [x] 품절은 구매 확정 수량이 총수량에 도달한 경우만 해당. 점유만 가득 차면 진행 상태일 수 있으나 주문은 재고 부족으로 거절될 수 있음
- [x] 시작 전 중단·재개 허용. 같은 운영 상태로 재요청하면 200 유지, 종료 후 중단·재개는 409
- [x] PATCH는 version 필수, 다른 관리자 작업으로 버전이 달라졌으면 409
- [x] 생성·부분 수정의 입력과 null 처리, 공개 응답 범위 확정
- [x] 시작 전 제품 교체 시 제품명 보관 값을 갱신하고 가격 생략 시 기존 판매 가격 유지

## 상태 계산과 조회

상태는 별도 DB enum 컬럼에 중복 저장하지 않고 기간·중단 표시·확정 수량에서 계산한다.

| 우선순위 | 조건 | API 상태 |
|---|---|---|
| 1 | DB 시각 >= endsAt | ENDED |
| 2 | isStopped = true | STOPPED |
| 3 | DB 시각 < startsAt | SCHEDULED |
| 4 | soldQuantity = totalQuantity | SOLD_OUT |
| 5 | 그 외 | OPEN |

시작 전 중단 이벤트는 STOPPED이며, 시작 전 재개하면 SCHEDULED다. 품절이어도 중단할 수 있고 재개 시에는 SOLD_OUT이다. 종료 후에는 중단 표시가 남아도 ENDED로 조회한다. 조회 상태는 조회 시점의 안내이며 주문·관리 작업은 잠금 후 다시 판정한다. 필터와 응답 상태에는 같은 DB 기준 시각과 계산 규칙을 적용한다.

productId와 status 필터를 함께 주면 두 조건을 모두 적용한다. productId·page·size는 기존 제품 API와 같은 양의 ID·0 이상 페이지·1~100 크기 검증을 적용하고 미지원 상태는 400이다. 유효한 필터에 맞는 데이터가 없거나 마지막 페이지를 넘으면 빈 목록 200을 반환한다.

## 입력과 API 계약

- 생성 필수: productId, name, startsAt, endsAt, totalQuantity.
- 생성 선택: description, unitPrice, perMemberLimit. 생략 시 각각 빈 문자열·제품 기준 가격·1을 사용한다.
- 이름은 앞뒤 공백 제거 후 1~100자, 설명은 원문 보존·최대 2,000자이며 null은 빈 문자열로 처리한다.
- 시각은 오프셋이 명시된 ISO 8601로 받고 UTC·DB 마이크로초 정밀도 계약을 따른다. 생성과 시작 전 기간 수정은 미래 시작 및 시작 < 종료를 지킨다. 시작 후 이름·설명 수정은 기존 시작 시각이 과거라는 이유로 거절하지 않는다.
- PATCH는 생략한 필드를 유지하며 명시적 null은 거절한다. description:null만 빈 문자열로 처리한다. productId 변경 시 새 제품명을 보관하되 unitPrice를 보내지 않으면 기존 이벤트 가격을 유지한다. 새 총수량과 사용자 한도는 병합한 최종 값으로 함께 검증한다.
- 알 수 없는 필드·중복 JSON 필드·후행 JSON 값·잘못된 타입은 400으로 거절한다. 가격·수량·ID·version에는 정수만 허용한다.
- 수정은 이벤트 행 잠금 후 version을 검사한다. 중단·재개는 행 잠금으로 경쟁을 처리하며 같은 상태 재요청은 불필요한 상태 변경 없이 200을 반환한다.

경로는 모두 `/api/v1` 기준이다. 관리 요청에는 ADMIN 세션과 CSRF가 필요하다.

| 동작 | 경로 | 성공 응답 |
|---|---|---|
| 생성 | POST /admin/sales | 201, 이벤트 상세 |
| 부분 수정 | PATCH /admin/sales/{id} | 200, 이벤트 상세 |
| 시작 전 삭제 | DELETE /admin/sales/{id} | 200, data:null |
| 중단 | POST /admin/sales/{id}/stop | 200, 이벤트 상세 |
| 재개 | POST /admin/sales/{id}/resume | 200, 이벤트 상세 |
| 공개 상세 | GET /sales/{id} | 200, 이벤트 상세 |
| 공개 목록 | GET /sales | 200, 페이지 응답 |

상세 응답은 saleId, productId, name, description, productNameSnapshot, unitPrice, startsAt, endsAt, totalQuantity, perMemberLimit, status, version, createdAt, updatedAt을 제공한다. 목록은 description을 제외한 요약 항목과 기존 items·page·size·totalElements·totalPages를 사용한다. 구매 가능·점유·확정 수량은 공개하지 않는다. ID는 숫자, 응답 시각은 UTC ISO 8601이다.

없는 제품·이벤트는 404, 잘못된 입력은 400, 시작 후 금지 작업·종료 후 운영 변경·버전 충돌은 409다. 삭제한 이벤트에 다시 삭제를 요청하면 404다. 인증·권한·CSRF·Redis 장애는 기존 공통 계약을 유지한다.

## 구현·검증 기준

- product.api의 조회 계약으로 실제 제품을 확인한다. sale이 제품 저장소·엔티티를 직접 참조하지 않는다.
- sale의 순수 도메인 모델과 JPA 엔티티를 분리하고 Spring Data JPA로 영속화한다. 적용된 Flyway 파일은 보존한다.
- 관리 작업은 이벤트 행을 잠그고 별도 DB 시각 조회 후 허용 여부를 판정한다. 같은 SQL의 NOW()를 잠금 대기 후 시각으로 가정하지 않는다.
- 시작 직전 수정이 잠금 대기로 시작 후에 실행되는 경우, 시작 후 삭제, 중단·재개 경쟁을 실제 MySQL에서 검증한다. 주문과 수량 점유의 경쟁은 1-7에서 확장한다.
- 제품 기준 정보와 이벤트의 제품명·가격 보관 값이 분리되는지 확인한다.
- 상태 우선순위·상태 필터·총수량만 공개하는 응답, 확정 수량 기준 품절과 점유 수량의 구분을 검증한다. 아직 주문 기능이 없으므로 수량 상태는 격리된 테스트 픽스처로 검증한다.
- 같은 version으로 경쟁하는 PATCH 중 하나만 성공하는지, 중단·재개 재요청과 삭제 재요청의 계약을 검증한다.
- ADMIN·USER·미인증, CSRF, 입력·가격·수량·구매 한도·기간 경계와 공개 조회의 Redis 장애 동작을 검증한다.
- 기존 회원·세션·제품·스키마 검사와 ArchUnit 경계 검사를 유지한다. Java 21 전체 build 명령·테스트 수와 미검증 제약을 기록한다.

## 이번 구현의 기술 선택

- 이번 단계에 한해 사용자가 Terra high 워커 대신 주 에이전트 직접 구현을 지시했다. 별도 워커의 독립 리뷰를 받았다고 기록하지 않는다.
- Spring Data JPA의 PESSIMISTIC_WRITE로 이벤트 행을 잠근 후 별도 SQL로 DB 시각을 읽는다. 생성 시에는 제품 조회 후 DB 시각을 판정한다.
- DB 시각은 DATE_FORMAT(UTC_TIMESTAMP(6), ...)의 UTC 문자열을 Instant로 변환한다. 초기 네이티브 시각 타입 투영에서 JDBC/JVM 시간대가 개입해 9시간 차이가 발생한 것을 실제 MySQL 테스트로 재현하고 보완했다.
- PATCH의 필드 존재 여부와 병합한 최종 조건을 모두 검사한다. 시작 후 금지 필드를 같은 값으로 보내도 거절하고, 도메인에서도 실제 핵심 조건 변경을 검사한다.
- 목록은 Spring Data PageRequest·Page를 사용한다. int 범위를 넘는 offset은 총수 확인 후 필요한 경우 typed native query에 long으로 전달한다. 상태 필터와 응답 상태의 기준 시각은 같지만 READ COMMITTED에서 동시 변경 시 count와 내용의 완전한 스냅샷 일치는 보장하지 않는다.
- 입력 시각은 DB 마이크로초 정밀도를 넘기거나 UTC 기준 MySQL DATETIME 범위를 벗어나면 400으로 거절한다. 임의 반올림이나 잘라내기는 하지 않는다. 생성 선택 항목의 기본값은 필드 생략 시 적용하며 설명 외 명시적 null은 거절한다.
- version만 보낸 PATCH 또는 실질 변경이 없는 PATCH는 현재 상세를 반환한다. 중단·재개와 마찬가지로 불필요한 버전 증가를 만들지 않는다.
- 기존 V1·V2·V3 마이그레이션을 수정하지 않았고 스키마 변경도 없다. 주문·수량 점유·결제 API는 이번 구현에 포함하지 않는다.

## 검증 근거와 한계

- 도메인 기본 테스트의 구현 전 컴파일 실패를 확인하고 구현 후 통과했다. 모든 API 동작마다 독립적인 red 단계를 수행한 것은 아니다.
- 실제 MySQL 시각 회귀 테스트가 초기 JDBC 시각 타입 투영에서 실패한 뒤 UTC 문자열 투영으로 통과했다. 도메인에서 실제 핵심 조건 변경을 직접 검사하는 회귀도 실패 후 보완했다.
- 잠금 대기 테스트는 SHOW FULL PROCESSLIST로 요청이 실제 SELECT FOR UPDATE에서 대기 중임을 확인한다. DB 시각이 시작을 넘은 뒤 잠금을 풀어 수정·삭제가 거절되고 가격·버전·행이 보존됨을 검증했다. 최초 SHOW PROCESSLIST는 SQL을 100자로 잘라 대기 쿼리를 찾지 못해 실패했으며 전체 SQL 조회로 바로잡았다.
- 단일 version의 동시 PATCH는 하나만 성공하고 나머지는 VERSION_CONFLICT다. 반복 중단·재개·삭제의 응답, 제품 교체와 가격·이름 보관, 공개 필드·상태별 필터 및 입력 경계도 검증했다.
- 기존 세션 통합 테스트의 가짜 판매 엔드포인트를 실제 이벤트 생성·조회로 교체했다. 따라서 기존 Redis 장애·다중 인스턴스 세션 검사가 실제 판매 조회를 통과한다.
- 최종 Java 21 ./gradlew clean build: 1분 33초, 작업 17개 실행, 일반·구조 33개와 실제 MySQL·Redis 통합 46개 성공(첫 전체 검사). 실패·오류·건너뜀은 모두 0개다. 최종 검토에서 네이티브 필터 시각 바인딩을 추가 보완했으며 아래 최종 검사로 다시 확인한다.
- 큰 offset이 총수보다 작아 실제 네이티브 조회를 수행하는 40억 건 규모 분기는 단위 테스트로 long 전달·필터·기준 시각을 검증했다. 해당 크기의 데이터를 실제 MySQL에 적재하지는 않았다.
- 현재 주문 기능이 없으므로 수량 경쟁 및 결제·복구와의 연동 검증은 1-7 이후 수행한다. 기존 Flyway MySQL 8.4 지원 경고는 남아 있다.
- 커밋·푸시·PR·머지는 아직 수행하지 않았다. 다음 단계는 1-7 정책·구현 범위 점검 후 별도 시작한다.

### 최종 시각 바인딩 재검토

큰 offset 네이티브 조회의 시각을 LocalDateTime으로 바인딩했을 때 `2030-01-01T00:00:00.123456Z`가 실제 MySQL에서 `2029-12-31T15:00:00.123456Z`로 전달되는 것을 회귀 테스트로 재현했다. UTC Instant를 직접 바인딩하도록 수정했고 동일 테스트가 통과했다. 큰 페이지의 offset·필터 전달은 단위 테스트, JDBC 시각 바인딩은 실제 MySQL 테스트로 각각 검증한다.

최종 보완 후 Java 21 `./gradlew clean build`를 다시 실행해 1분 29초에 성공했다. 일반·구조 33개와 실제 MySQL·Redis 통합 47개, 총 80개가 실패·오류·건너뜀 없이 통과했다. 이는 위의 첫 전체 검사 기록을 대체하는 최종 결과다. 변경 문서의 상대 링크·펜스·공백 검사와 위키 Mermaid 도식 16개 렌더링도 통과했다.
