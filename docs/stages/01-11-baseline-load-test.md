# 1-11 기준 부하 실험

상태: 정책 확정·구현·리허설 완료, 공식 측정 대기. 사용자가 "1-9 부터 1-11까지도 마찬가지로 정책 협의들 너가 생각하는 추천안으로 확정하고 개발 및 테스트"하라고 지시해 주 에이전트 추천안으로 확정하고 구현을 시작했다.

[1단계 정책](01-mysql-order.md), [1-9 관측](01-9-basic-observability.md), [1-10 여러 인스턴스](01-10-multi-instance-consistency.md)를 따른다. 이 문서는 1-11의 새 합의를 우선한다.

## 범위

- k6 시나리오, 데이터 준비, 결과 수집, DB 대조를 한 명령으로 다시 실행할 수 있게 만든다.
- 이후 단계(Redis, Kafka)와 비교할 MySQL 단계 기준값을 기록한다.
- 성능 목표와 알림 임계값은 정하지 않는다. 기준값을 본 뒤 정한다.

## 확정한 정책과 이유

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| 실행 환경 | 1-10 격리 환경. 판매 앱 2개, Caddy 로드 밸런서, Mock PG 전체 성공, 요청 제한 없음 | 운영 형태와 같다. 개발 DB와 서버를 건드리지 않는다 |
| 기준 시나리오 | 서로 다른 사용자 10,000명이 수량 1개씩 재고 1,000개에 요청. 생성된 주문은 같은 반복에서 결제 | 1단계 완료 기준 |
| 한도 미만 시나리오 | 서로 다른 사용자 800명이 수량 1개씩 재고 1,000개에 요청 | 재고가 충분하면 모든 정상 요청이 확정되어야 한다 |
| 로그인 분리 | 가입·로그인은 부하 전에 준비 단계에서 끝낸다. k6는 준비된 세션으로 주문·결제만 보낸다 | 1단계 정책. Argon2 로그인 비용이 주문 측정에 섞이지 않는다 |
| 세션 파일 | 쿠키·CSRF는 실행 중 임시 파일로만 k6에 넘기고 실행 후 지운다. 증거에 저장하지 않는다 | 비밀값을 남기지 않는다 |
| k6 실행 모델 | `shared-iterations` 10,000회, 동시 VU 500. 반복 하나가 사용자 한 명 | 동시 요청 수를 고정한 닫힌 모델이다. 열린 도착률 모델은 같은 컴퓨터에서 부하 생성기 한계를 재기 쉽다 |
| 반복 횟수 | 기준 시나리오 3회, 한도 미만 1회. 중앙값과 최소·최대를 보고 | 한 번의 값은 잡음과 구분되지 않는다 |
| 기록 지표 | k6의 요청 수·처리량·엔드포인트별 p50/p95/p99, 상태·업무 코드별 건수. 부하 전후 관리 포트 지표 스냅샷(HTTP, Hikari, JVM, 업무 카운터). 부하 전후 MySQL 관측 스냅샷. 실행 환경 | 처리량·지연·오류·병목을 한 결과물로 남긴다 |
| 정합성 판정 | 실행마다 스냅샷 검증기와 대조 SQL. 기준은 확정 1,000·잔여 0, 한도 미만은 확정 800. 위반 0 | 지표가 아니라 DB로 판정한다 |
| 오류 판정 | 5xx와 연결 오류는 0이어야 한다. 품절 409는 정상 업무 거절로 따로 센다 | 업무 거절과 시스템 오류를 구분한다 |
| 결과 보관 | 실행별 요약 JSON과 합계 요약을 `benchmarks/load-baseline/`에 커밋. 원본 로그와 k6 원본 출력은 커밋하지 않음 | 다시 비교할 숫자만 남긴다 |
| 병목 기록 | 측정값에서 먼저 포화되는 자원을 찾아 근거와 함께 적는다. 추정은 추정이라고 표시한다 | 숫자가 무엇에 막혔는지 설명해야 비교가 의미 있다 |
| 측정 JAR | 공식 기준값은 Spring Boot 관리 버전 의존성으로 만든 JAR로만 측정 | 버전을 바꾼 JAR의 숫자는 기준값이 아니다 |

## 검증 기준

- 기준 시나리오 3회 모두 확정 1,000·잔여 0·대조 위반 0, 5xx와 연결 오류 0.
- 한도 미만 시나리오에서 확정 800, 위반 0.
- 결과물에 환경, 처리량, 엔드포인트별 지연 백분위, 상태·업무 코드 건수, 관리 포트 지표 전후 차이, MySQL 관측 전후 차이가 있다.
- 같은 명령으로 처음부터 다시 실행할 수 있고, 실행은 자기 자원만 정리한다.
- 병목 설명이 측정값을 근거로 한다.

## 리허설 결과

공식 기준값이 아니다. 1-9의 Micrometer 관리 버전을 내려받지 못해 캐시에 있던 1.17.2로 만든 JAR로 실행했다. 실행 방식과 판정이 동작하는지 확인하는 용도다.

| 항목 | 기준(1만 명, 재고 1,000) | 한도 미만(800명, 재고 1,000) |
|---|---|---|
| 판정 | 17개 검사 통과 | 17개 검사 통과 |
| 확정 / 잔여 | 1,000 / 0 | 800 / 200 |
| 검증기·대조 SQL 위반, 5xx·연결 오류 | 0 | 0 |

리허설에서 본 병목 후보는 판매 이벤트 행 잠금과 인스턴스당 커넥션 풀 10개다. 주문 생성이 모두 같은 이벤트 행을 `FOR UPDATE`로 잠그고, 잠금 대기 중인 트랜잭션이 커넥션을 쥐고 있다. 공식 측정에서 같은 경향인지 확인한다.
