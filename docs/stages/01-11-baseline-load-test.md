# 1-11 기준 부하 실험

상태: 정책 확정·구현·공식 측정·독립 검증·위키 갱신 완료. 사용자가 "1-9 부터 1-11까지도 마찬가지로 정책 협의들 너가 생각하는 추천안으로 확정하고 개발 및 테스트"하라고 지시해 주 에이전트 추천안으로 확정하고 구현을 시작했다.

[1단계 정책](01-mysql-order.md), [1-9 관측](01-9-basic-observability.md), [1-10 여러 인스턴스](01-10-multi-instance-consistency.md)를 따른다. 이 문서는 1-11의 새 합의를 우선한다.

## 범위

- k6 시나리오, 데이터 준비, 결과 수집, DB 대조를 한 명령으로 다시 실행할 수 있게 만든다.
- 이후 단계(Redis, Kafka)와 비교할 MySQL 단계 기준값을 기록한다.
- 성능 목표와 알림 임계값은 정하지 않는다. 기준값을 본 뒤 정한다.

## 확정한 정책과 이유

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| 실행 환경 | 1-10 격리 환경. 판매 앱 2개, Caddy 로드 밸런서, Mock PG 전체 성공, 요청 제한 없음 | 운영 형태와 같다. 개발 DB와 서버를 건드리지 않는다 |
| 기준 시나리오 | 서로 다른 사용자 10,000명이 수량 1개씩 재고 1,000개에 요청. 생성된 주문은 같은 반복에서 결제 | 1단계 완료 기준 |
| 한도 미만 시나리오 | 서로 다른 사용자 800명이 수량 1개씩 재고 1,000개에 요청 | 재고가 충분하면 모든 정상 요청이 확정되어야 한다 |
| 로그인 분리 | 가입·로그인은 부하 전에 준비 단계에서 끝낸다. k6는 준비된 세션으로 주문·결제만 보낸다 | 1단계 정책. Argon2 로그인 비용이 주문 측정에 섞이지 않는다 |
| 세션 파일 | 쿠키·CSRF는 실행 중 임시 파일로만 k6에 넘기고 실행 후 지운다. 증거에 저장하지 않는다 | 비밀값을 남기지 않는다 |
| k6 실행 모델 | `shared-iterations` 10,000회, 동시 VU 500. 반복 하나가 사용자 한 명 | 동시 요청 수를 고정한 닫힌 모델이다. 열린 도착률 모델은 같은 컴퓨터에서 부하 생성기 한계를 재기 쉽다 |
| 반복 횟수 | 기준 시나리오 3회, 한도 미만 1회. 중앙값과 최소·최대를 보고 | 한 번의 값은 잡음과 구분되지 않는다 |
| 기록 지표 | k6의 요청 수·처리량·엔드포인트별 p50/p95/p99, 상태·업무 코드별 건수. 부하 전후 관리 포트 지표 스냅샷(HTTP, Hikari, JVM, 업무 카운터). 부하 전후 MySQL 관측 스냅샷. 실행 환경 | 처리량·지연·오류·병목을 한 결과물로 남긴다 |
| 정합성 판정 | 실행마다 스냅샷 검증기와 대조 SQL. 기준은 확정 1,000·잔여 0, 한도 미만은 확정 800. 위반 0 | 지표가 아니라 DB로 판정한다 |
| 오류 판정 | 5xx와 연결 오류는 0이어야 한다. 품절 409는 정상 업무 거절로 따로 센다 | 업무 거절과 시스템 오류를 구분한다 |
| 결과 보관 | 실행별 요약 JSON과 합계 요약을 `benchmarks/load-baseline/`에 커밋. 원본 로그와 k6 원본 출력은 커밋하지 않음 | 다시 비교할 숫자만 남긴다 |
| 병목 기록 | 측정값에서 먼저 포화되는 자원을 찾아 근거와 함께 적는다. 추정은 추정이라고 표시한다 | 숫자가 무엇에 막혔는지 설명해야 비교가 의미 있다 |
| 측정 JAR | 공식 기준값은 Spring Boot 관리 버전 의존성으로 만든 JAR로만 측정 | 버전을 바꾼 JAR의 숫자는 기준값이 아니다 |

## 검증 기준

- 기준 시나리오 3회 모두 확정 1,000·잔여 0·대조 위반 0, 5xx와 연결 오류 0.
- 한도 미만 시나리오에서 확정 800, 위반 0.
- 결과물에 환경, 처리량, 엔드포인트별 지연 백분위, 상태·업무 코드 건수, 관리 포트 지표 전후 차이, MySQL 관측 전후 차이가 있다.
- 같은 명령으로 처음부터 다시 실행할 수 있고, 실행은 자기 자원만 정리한다.
- 병목 설명이 측정값을 근거로 한다.

## 구현 중 정한 세부 사항

- 실행기는 새 디렉터리 대신 `tools/order-regression/run_baseline.py`에 두었다. 격리 환경, 사용자 준비, 스냅샷, 검증기, 대조 SQL, 접근 로그 파서를 그대로 쓴다.
- k6는 요청별 기록을 남기지 않는다. 그래서 검증기의 시도별 결과는 서버의 `order_request_results`로 만든다. k6가 센 생성·품절 건수가 DB의 생성·거절 건수와 같은지 따로 대조한다.
- 문서 기준 외에 다음도 실패로 처리한다. 200·201·202·409 밖의 상태, k6 종료 코드, 빠진 반복, 한쪽 인스턴스만 처리한 경우, MySQL 관측 누락이다.
- HikariCP는 풀 통계를 1초 동안 캐시하므로 부하 후 한 번 찍은 값은 믿을 수 없다. 1초 간격으로 읽은 최댓값만 기록한다.
- 사용자 준비 동시성은 16이다. 기존 HTTP 클라이언트가 요청마다 연결을 닫아, 1만 명 준비 중 TIME_WAIT 소켓이 약 14,000개까지 늘었다(임시 포트 16,384개). 이번 실행에서는 문제가 없었지만 여유가 크지 않다.
- 리허설은 임시 대체 버전 JAR로 먼저 돌려 실행 방식만 확인했다. 아래 숫자는 관리 버전 JAR의 공식 측정이다.

## 공식 측정 결과

깨끗한 커밋 `fa2cd8c`에서 관리 버전 의존성(Micrometer 1.15.12, prometheus-metrics 1.3.10, HikariCP 6.3.3)으로 만든 JAR로 측정했다. 환경은 Apple M4 Pro 14코어, 메모리 48GB, macOS 26.7, Java 21.0.10, MySQL 8.4.7, k6 2.1.0이다. 부하 생성기와 서버가 같은 컴퓨터를 쓴다. 실행별 결과와 합계는 [benchmarks/load-baseline](../../benchmarks/load-baseline/)에 있다.

| 항목 | 기준 3회 중앙값 (최소~최대) | 한도 미만 1회 |
|---|---|---|
| 판정 | 3회 모두 통과 | 통과 |
| 확정 / 잔여 | 1,000 / 0 | 800 / 200 |
| 검증기·대조 SQL 위반, 5xx·연결 오류 | 0 | 0 |
| 상태 | 201 1,000, 409 9,000, 200 1,000 | 201 800, 200 800 |
| HTTP 처리량 | 295 req/s (286~302) | 128 req/s |
| 부하 시간 | 37.2초 (36.4~38.5) | 12.5초 |
| 주문 생성 p50 / p95 / p99 | 1,297 / 2,406 / 3,020ms | 2,584 / 3,516 / 3,878ms |
| 결제 p50 / p95 / p99 | 4,044 / 6,275 / 6,640ms | 4,273 / 6,724 / 6,874ms |
| 커넥션 대기 평균 / 최대 | 1,065ms / 3,373ms | 1,284ms / 3,229ms |
| 커넥션 활성 최대 / 대기 최대 | 10 / 191 (인스턴스당) | 10 / 191 |
| InnoDB 행 잠금 대기 횟수 / 총 대기 | 10,998회 / 664초 | 1,598회 / 204초 |
| 데드락·잠금 시간 초과 | 0 | 0 |
| 판매 앱 JVM CPU | 48.5 CPU초 (약 1.3코어) | 26.8 CPU초 |

## 병목 분석

측정값으로 확인한 것:

- 판매 앱 CPU는 한계가 아니다. 두 JVM이 37초 동안 약 1.3코어를 썼고 GC 정지는 합계 0.014초다. k6는 0.13코어를 썼다.
- 커넥션 풀이 포화됐다. 인스턴스당 최대 10개가 모두 쓰였고 최대 191개 요청이 커넥션을 기다렸다. 주문 생성 평균 지연 1,403ms 중 커넥션 대기 평균이 1,065ms다.
- 같은 이벤트 행의 잠금 대기가 쌓였다. 37초 동안 행 잠금 대기가 10,998번, 합계 664초다. 평균 약 18개 트랜잭션이 동시에 잠금을 기다린 셈이다.

추정한 것:

- 처리량 상한은 판매 이벤트 행 하나의 `SELECT ... FOR UPDATE` 직렬화가 정한다. 주문 생성 1만 건과 결제 확정 1,000건이 모두 같은 행을 잠근다. 37초에 약 11,000번이면 잠금 한 번에 약 3.4ms로, 커밋을 포함한 한 트랜잭션 시간과 맞는다. 인스턴스나 VU를 늘려도 이 행을 기다리는 줄만 길어질 것이다.
- 커넥션 대기는 잠금 대기의 결과다. 잠금을 기다리는 트랜잭션이 커넥션을 쥐고 있어 다음 요청이 커넥션을 받지 못한다. 풀만 키우면 MySQL 쪽 잠금 대기열이 길어질 뿐 처리량은 크게 늘지 않을 것이다.
- 결제 지연이 주문 생성보다 긴 이유는 결제가 짧은 트랜잭션 두 번과 PG 호출로 이뤄지고, 두 트랜잭션 모두 같은 커넥션 줄에 서기 때문이다. 결제 확정도 이벤트 행을 잠근다.
- 한도 미만 시나리오의 주문 생성 지연이 더 긴 이유는 800건이 모두 INSERT까지 하는 전체 트랜잭션이라 잠금 보유 시간이 길기 때문이다. 기준 시나리오는 대부분이 품절 판정 후 바로 끝난다. 처리량이 낮은 것은 부하가 12초로 짧고 VU 500개가 처음에 한꺼번에 몰렸기 때문이다.
- 측정 중 시스템 CPU 평균은 74%였다. 판매 JVM과 k6만으로는 설명되지 않는다. Docker VM(MySQL, Redis, Caddy), Mock PG, macOS 보안 에이전트가 나머지를 쓴 것으로 보인다. 컨테이너별 CPU는 측정하지 않았다. 같은 컴퓨터 안의 잡음이므로 다른 컴퓨터와 숫자를 직접 비교하지 않는다.

이 결과는 2단계 Redis 재고 처리와 비교할 기준선이다. 성능 목표와 알림 임계값은 아직 정하지 않았다.

## 검증 결과

- Sonnet high 워커가 구현과 리허설을 했다. 주 에이전트가 diff를 리뷰하고 공식 측정을 직접 실행했으며 결과 파일을 확인했다. 결과 파일에는 세션·비밀번호·API 키가 없다.
- 관리 버전으로 `./gradlew clean build` 성공. 판매 앱 단위 94개, 통합 132개, Mock PG 11개·15개 모두 실패 0개. Python 실험 도구 테스트 77개 통과.
- `python3 scripts/check-wiki-diagrams.py`와 `git diff --check` 통과.
