# 1단계: MySQL 기반 주문·Mock PG 결제와 관측

작성일: 2026-11-10

[전체 기획](../project-plan.md) · [구조 설계](../architecture.md)

## 상태

1-1 기획·정책과 기본 기술 계약 확정 완료. 1-2 구현·주 에이전트 독립 검증 완료. 업무 API 구현은 아직 시작하지 않았다. 아래 확정 정책은 사용자와 합의한 내용이며 미정 사항은 구현 전에 함께 결정한다.

## 확정한 기획·정책

| 항목 | 합의한 내용 |
|---|---|
| 서비스 | 선착순 한정 수량 제품 판매 |
| 결제 수단 | 앞으로도 Mock PG 사용. 실제 PG 연동은 계획하지 않음 |
| 제품 구성 | 판매 이벤트 하나당 제품 하나 |
| 재고 범위 | 이벤트별 전용 수량. 제품별 공용 창고 재고·이벤트 간 배분은 제외 |
| 구매 한도 | 이벤트마다 사용자별 구매 수량 한도 설정. 미설정 시 기본 1개 |
| 주문 방식 | 한 번에 여러 개 구매와 여러 번 나눠 주문 허용. 사용자별 이벤트 누적 수량으로 제한 |
| 주문 요청 키 | 클라이언트가 사용자별 UUID 키를 필수 전달하고 주문 보관 기간 동안 함께 보관. 같은 키·같은 입력은 기존 결과 반환, 이벤트·수량이 다르면 충돌 거절. PG에는 주문에 고정된 결제 키로 재시도·재조회 |
| 재고·한도 점유 | 주문 시 요청 수량만큼 전체 판매 재고와 사용자 구매 한도를 함께 임시 점유 |
| 결제 성공 | 점유 수량을 확정 구매 수량으로 전환하고 주문 확정. 같은 수량을 다시 차감하지 않음 |
| 명확한 결제 실패 | 해당 주문의 재고·구매 한도 점유 해제 |
| 타임아웃 | 결제 실패로 단정하지 않음. 결과 확인 전까지 점유 유지, 결과에 따라 확정 또는 해제 |
| 요청 수량 부족 | 남은 재고 또는 사용자 구매 한도가 요청 수량보다 적으면 요청 전체 거절. 자동으로 일부 수량만 구매하지 않음 |
| Mock PG 재현 범위 | 기본은 성공. 명확한 실패·처리 지연·결제 성공 후 응답 유실은 로컬/테스트 ADMIN 제어로 명시 지정. 랜덤 실패 없음 |
| Mock PG 실행 형태 | 판매 서버와 별도 프로세스의 HTTP 서버로 실행. 독립적인 지연·응답 유실·중단 재현 |
| Mock PG 저장소 | 로컬 MySQL 인스턴스는 공유하되 별도 스키마·계정에 결제 키·결과·종료 기록 영속 저장. 판매 서버는 HTTP로만 접근 |
| 주문·결제 API | 주문 생성과 결제 요청을 분리. 생성 시 점유하고 결제 요청 API에서 Mock PG 호출. 미결제 주문도 생성 후 5분 정리 대상 |
| Mock PG 결제 키 계약 | 같은 키·같은 금액은 기존 결과 반환. 정리 시 이미 성공이면 성공 반환, 미결제면 종료 확정. 종료 확정 키는 늦게 도착한 결제도 성공시키지 않음 |
| 가격 단위·범위 | 원화 정수, 개당 1원~1,000,000,000원. 무료·소수점·다중 통화 제외 |
| 이벤트 판매 수량 | 1~1,000,000개. 사용자 구매 한도는 1~이벤트 총수량 |
| 입력 길이 | 이메일 최대 254자, 제품명·이벤트명 최대 100자, 설명 최대 2,000자 |
| 목록 조회 | 페이지 방식. 기본 20개·최대 100개. 구체적 필터·정렬은 조회 소단계에서 확인 |
| 판매 가격 | 이벤트 생성 시 관리자가 지정하며 제품 기준 가격을 기본값으로 제공. 주문에는 해당 판매 가격을 별도 보관 |
| 주문 가능 시간 | 시작 시각 이상~종료 시각 미만. 종료 전에 재고를 점유한 주문은 종료 후에도 결제 처리 가능 |
| 시간·중단 판정 | MySQL의 수량 점유 트랜잭션에서 잠금 획득 후 DB 시각·이벤트 상태로 판정. 시각은 UTC 저장 |
| 인증·Redis 도입 | 1단계에 이메일·비밀번호와 Redis 세션 도입. 2단계에 캐시·분산 요청 제한 확장 |

예를 들어 구매 한도가 3개인 이벤트에서 2개를 구매한 사용자는 1개를 추가 구매할 수 있다. 2개를 결제 대기 중인 사용자도 남은 구매 가능 수량은 1개다. 새 주문과 같은 요청의 재시도는 구분한다.

수량 관련 기준은 다음과 같다.

- 이벤트의 확정 판매 수량 + 임시 점유 수량은 판매 한도 이하이다.
- 사용자의 이벤트별 확정 구매 수량 + 임시 점유 수량은 사용자 구매 한도 이하이다.
- 동시 주문·중복 결과 처리·서버 재시작에도 초과 차감이나 중복 확정·해제가 없어야 한다.
- 동일 요청 재시도는 새 주문이나 새 결제를 만들지 않는다. 한도 내에서 새 요청으로 추가 구매하는 것은 허용한다.

## 확정한 결제 결과 확인·복구 정책

| 항목 | 기본값과 처리 |
|---|---|
| 결제 응답 대기 | 3초. 초과 시 실패로 단정하지 않고 결제 확인 중으로 처리 |
| 결과 미확인 재조회 | 10초 간격으로 Mock PG에 결과 조회 |
| 장기 결제 정리 | 주문 생성 후 5분 경과 시 아직 미결제라면 Mock PG에 결제 종료·취소 요청 |
| 점유 해제 조건 | 명확한 실패 또는 취소 확정을 확인한 뒤 재고·사용자 구매 한도 점유 해제 |
| PG 계속 무응답 | 점유 유지, 운영 확인 대상으로 표시. 시간 경과만으로 점유 해제하지 않음 |
| 서버 재시작 | DB에 보관한 미완료 주문·결제 상태를 찾아 결과 확인·정리 작업 재개 |

3초·10초·5분은 설정으로 변경할 수 있는 기본값이다. 5분은 무조건 재고를 해제하는 시간이 아니라 결제 정리를 시작할 기준이다. 결과 조회에서 이미 성공한 결제는 주문 확정으로 수렴시킨다. 종료·취소와 결제 성공이 경쟁하면 PG가 키별로 하나의 최종 결과를 결정하고 유지한다. 종료 확정 후에는 같은 키의 결제가 뒤늦게 성공하지 않는다. 이미 성공한 결제의 종료 요청은 성공 결과를 반환하며 결제를 취소·환불하지 않는다. 이 내부 정리 기능은 사용자 주문 취소·환불 기능과 구분한다.

재시작 복구는 영속 주문·결제 상태를 조회하는 복구 작업이다. Outbox 도입 여부와 별개로 필요하다. Outbox는 업무 데이터와 외부에 보낼 메시지 기록을 같은 DB 트랜잭션에 저장한 뒤 전달하는 패턴이며, Kafka 전달 방식 선택은 3-1에서 별도로 확정한다. 두 작업 모두 중복 실행에 안전해야 한다. 주문·결제 상태와 DB 임대 기반 작업 선점은 기술 계약으로 합의했으며, 임대 시간·배치 크기 등 실행 설정은 1-7에서 검증한다.

## 확정한 이벤트 운영 정책

| 항목 | 정책 |
|---|---|
| 시작 전 수정·삭제 | 제품·가격·기간·판매 수량·구매 한도 수정과 이벤트 삭제 허용 |
| 이벤트명·설명 | 시작 후에도 관리자가 수정 가능 |
| 제품·가격·시작 시각·사용자 구매 한도 | 시작 후 변경 금지 |
| 판매 수량·종료 시각 | 초기 범위에서는 시작 후 변경 금지. 증량·기간 연장은 후속 검토 |
| 판매 중단 | 관리자가 신규 주문을 중단할 수 있음. 기존 주문·결제와 결과 복구는 계속 처리 |
| 시작 후 삭제 | 금지. 종료·중단 상태로 기록 보존 |
| 중단 후 재개 | 판매 기간 안이면 관리자가 재개 가능. 기존 판매 조건은 유지 |
| 종료 후 | 신규 주문·재개 불가. 기존 주문 조회와 결제·복구는 계속 처리 |

여기서 이벤트명·설명 수정은 판매 제품의 교체나 주문에 보관한 제품명·가격의 변경을 뜻하지 않는다. 판매 중단은 기존 주문 취소·결제 취소와 구분한다.

중단과 신규 주문의 판정은 MySQL 수량 점유 트랜잭션에서 잠금 획득 후 이벤트 상태와 DB 시각을 확인한다. 잠금 범위와 SQL 순서는 기술 설계에서 검증한다. 시작 전 변경과 시작·중단·재개가 경쟁하는 경우의 트랜잭션·검증 경계는 기술 설계에서 정한다. 3단계에서 접수만 되고 주문·점유가 생성되지 않은 요청의 중단 후 처리 정책도 따로 확인한다.

## 확정한 인증 범위

이메일·비밀번호 인증과 Redis 세션을 1단계에 구현하기로 확정했다. 아래 기능 범위는 합의한 내용이며 시간·비용 등 명시적으로 남긴 세부 설정은 구현 전에 함께 결정한다. 정책 확정은 구현 시작 지시와 구분한다.

| 항목 | 확정 범위와 남은 설정 |
|---|---|
| 기본 기능 | 이메일·비밀번호 회원가입, 로그인, 로그아웃, 내 로그인 정보 조회 |
| 이메일 식별 | 앞뒤 공백 제거·대소문자 구분 없이 식별. 제공업체별 점·별칭 변환은 하지 않음 |
| 인증 구현 | Spring Security + Spring Session Data Redis. 세션 ID는 쿠키로 전달하고 회원·비밀번호 해시는 MySQL에 저장 |
| 비밀번호 | 8~64자, 영문 대소문자·숫자·출력 가능한 ASCII 특수문자만 허용. 공백·한글·기타 유니코드·제어문자 불허. 숫자·특수문자 등 문자 조합을 강제하지 않음. 입력을 자르거나 공백을 제거하지 않고 검증. Spring Security PasswordEncoder의 Argon2id 사용, 비용값은 별도 확정 |
| 권한·관리자 생성 | 공개 회원가입은 USER만 생성. ADMIN은 환경변수 입력의 별도 초기화 명령으로 최초 생성. 기존 ADMIN은 변경 없이 종료, 같은 이메일 USER는 오류로 종료. 초기 정책이며 추후 변경 가능 |
| API 접근 권한 | 제품·이벤트 목록과 상세는 공개, 주문·결제·내 정보·내 주문은 로그인 및 본인 소유 확인, 제품·이벤트 관리는 ADMIN 전용 |
| PG 시뮬레이션 제어 | ADMIN 전용이며 로컬·테스트 환경에만 노출 |
| 로그인 실패·시도 제한 | 이메일 존재 여부와 무관한 동일 메시지. 정규화 이메일+IP 조합별 5분 내 실패 5회면 구간 만료까지 429. 횟수·시간 설정 가능. 로그인 보호는 1단계 구현 |
| 세션 수명 | 마지막 요청 후 30분 유휴 만료. 설정으로 변경 가능 |
| 동시 로그인 | 여러 기기·세션의 동시 로그인 허용 |
| 로그아웃 | 현재 세션만 종료. 전체 기기 로그아웃은 초기 범위에서 제외 |
| 인증 오류·Redis 장애 | 인증 실패 401, 권한 부족 403. Redis 장애로 인증을 확인할 수 없으면 로그인·보호 API는 503. 공개 조회는 가능한 범위에서 제공 |
| 쿠키·요청 보호 | HttpOnly·SameSite=Lax. HTTPS에서는 Secure 적용, 로컬 HTTP에서는 Secure만 해제. 변경 요청은 CSRF 토큰 검증. 교차 사이트 프런트엔드 배치는 초기 제외 |
| 초기 제외 | 소셜 로그인, JWT·리프레시 토큰, 이메일 인증·비밀번호 재설정 메일 |

이메일 인증을 제외하면 이메일 소유권을 검증한 계정이라고 설명하지 않는다. 정규화한 이메일의 동시 중복 가입 방어, 비밀번호 허용 문자 경계와 해시 비용, 로그인 제한 카운터·IP 판정·동시 요청 처리와 Redis 장애의 상세 오류 응답은 기술 설계에서 정한다.

1-2의 스키마 범위에 회원을 포함하고, 1-3에서 회원·비밀번호·권한을, 1-4에서 Redis 세션 로그인·로그아웃을 구현한다. 제품 등록은 1-5부터 진행한다. 회원 도메인과 인증 어댑터의 패키지·공개 인터페이스는 1-1에서 함께 확정한다. 주문 로직에는 세션 객체 대신 인증된 사용자 ID를 전달한다.

Redis는 1단계에 세션 저장소로 도입한다. 2단계에서는 조회 캐시·분산 요청 제한으로 활용을 확장한다. 주문 재고·구매 한도 정합성의 기준은 계속 MySQL이다. 성능 비교에서는 인증 경로·사용자 수·로그인 방식과 세션 조건을 동일하게 유지하고, 부하 테스트 준비 과정의 로그인과 주문 부하를 분리한다. 동일 사용자 세션 하나로 여러 사용자 주문을 흉내 내지 않는다.

인증 검증에는 로그인·로그아웃·30분 유휴 만료와 요청에 따른 만료 갱신, 여러 기기 로그인과 현재 세션 로그아웃 후 다른 세션 유지, 다른 사용자 주문 접근 거절, 관리자 권한, API 인스턴스 2개 사이의 세션 공유, Redis 장애를 포함한다. 장애 시 세션을 무시하고 요청 사용자 ID를 신뢰하는 경로는 두지 않는다.

참고: [Spring Session Redis 연동](https://docs.spring.io/spring-session/reference/guides/boot-redis.html), [비밀번호 저장](https://docs.spring.io/spring-security/reference/6.5/features/authentication/password-storage.html), [CSRF](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html). 라이브러리 버전은 프로젝트 Spring Boot의 의존성 관리에 맞추며 최신 문서의 의존성 예시를 그대로 복사하지 않는다.

Argon2id 선택 근거는 [OWASP 비밀번호 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)을 참고한다. 합의한 비밀번호 길이·문자 정책과 해시 비용은 별개이며, 해시 비용은 공식 권장 최소값을 확인하고 로컬 자원과 로그인 시간을 측정해 설계안으로 제시한다.

## 확정한 공통 API 응답 방향

모든 API 응답의 공통 템플릿을 다음 필드로 구성한다. Java 응답 DTO는 제네릭 `ApiResponse<T>` 형태로 설계하며 필드 이름은 `httpStatus`, `code`, `data`, `message`로 사용한다.

| 필드 | 의미 |
|---|---|
| `httpStatus` | 실제 HTTP 응답과 같은 숫자 상태 코드 |
| `code` | 도메인별 enum이 정의한 성공 코드 또는 오류 코드 |
| `data` | 제네릭 타입 `T`에 해당하는 응답 데이터 |
| `message` | 사람이 읽는 설명 |

실패·본문 없는 성공은 `data: null`을 반환한다. 입력 검증 실패는 `data`에 필드별 오류 목록을 담는다. `code`는 고정된 기계 판독 문자열이고 `message`는 사람이 읽는 설명이다.

성공·오류 코드는 각 도메인 패키지에서 관리한다. 내부 도메인 모델이나 도메인 간 계약에 HTTP 응답 형식을 노출하지 않는다. enum 배치와 공통 인터페이스는 아래 원칙에 맞춰 기술 설계에서 확정한다.

- 공통 `ApiResponse<T>`와 `ResponseCode` 인터페이스는 `common.web`에 둔다. 인터페이스는 HTTP 상태, 코드 문자열, 기본 메시지의 공통 계약을 정의한다.
- 도메인별 성공·오류 enum은 해당 도메인의 웹 경계 패키지에서 관리한다. 예: `order.presentation.code.OrderSuccessCode`, `OrderErrorCode`.
- Java enum끼리 상속하지 않고 도메인별 성공·오류 enum이 공통 `ResponseCode`를 구현한다. 실제 JSON의 `code`에는 enum 객체가 아닌 코드 문자열을 넣는다.
- 요청 파싱·알 수 없는 시스템 오류의 공통 enum도 `common.web`에서 같은 인터페이스를 구현한다. Spring Security 필터의 인증·인가 오류도 동일 응답 템플릿을 사용하며 구체적인 핸들러 배치는 기술 설계에서 정한다.

## 확정한 초기 제외 범위

장바구니, 배송, 사용자 주문 취소·환불, 회원 탈퇴·비밀번호 변경은 초기 범위에서 제외한다. 결제 미진행·실패·타임아웃의 서버 내부 종료·복구와 관리자 판매 중단은 포함한다. 소셜 로그인·JWT·이메일 인증·비밀번호 재설정 메일도 앞서 정한 제외 범위를 유지한다.

운영 정책에 따른 API·상태·DB·트랜잭션과 Mock PG 계약은 [1-1 기술 계약](01-contracts.md)에 정리하고 기본안으로 합의했다. 입력 길이·구매 한도·목록 크기는 확정했으며, 이를 반영한 테이블·인덱스 상세는 1-2에서 점검한다. 계약 확정과 구현 시작 지시는 별개다.

## 검증 기준

- 실제 MySQL에서 마이그레이션과 트랜잭션·동시성 검증을 수행한다.
- 시작 직전·정각, 종료 직전·정각의 신규 주문과 종료 전 점유 후 종료 후 결제를 검증한다.
- 관리자가 지정한 판매 가격과 주문에 보관한 가격·금액을 대조하고 제품 정보 변경이 기존 주문을 바꾸지 않는지 확인한다.
- 구매 한도 기본값 1개와 별도 설정값, 여러 수량·여러 번 주문, 같은 사용자의 동시 요청을 검증한다.
- Mock PG 성공 시 확정, 명확한 실패 시 해제, 타임아웃 시 점유 유지 후 조회 결과에 따른 처리를 검증한다.
- 결제 성공 후 DB 반영 실패와 응답 유실 후 재시도를 포함해 주문·결제·수량이 수렴하는지 확인한다.
- 서버 재시작 후 복구 재개, 기본 10초 재조회, 5분 경과 후 종료·취소 확인, PG 무응답 시 점유 유지를 검증한다. 시간 기반 검증은 제어 가능한 시계·설정으로 수행한다.
- API 인스턴스 1개·2개에서 위 수량 규칙을 검증한다.
- Mock PG 전체 성공·요청 제한 없음·유효 기간 내 요청 조건에서 제품 1,000개에 서로 다른 사용자 10,000명이 수량 1개씩 요청하면 1,000건 확정, 잔여 수량 0이어야 한다.
- 여러 수량 주문에서는 주문 건수와 판매 수량을 구분한다. 재고 또는 사용자 잔여 한도가 부족하면 요청 전체를 거절하고 일부 수량을 자동 주문하지 않는지 검증한다.
- 관측 구성 후 처리량·지연·오류·잠금 경합을 측정하고 DB 대조 결과를 남긴다.
