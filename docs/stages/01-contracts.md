# 1-1 기술 계약

작성일: 2026-11-10

상태: 사용자와 기획·운영 정책, API 응답·가입 계약, DB·프로젝트 기본안 및 주문 상태·트랜잭션·복구 구조를 합의했다. 입력 길이·구매 한도·목록 크기도 합의했으며, 테이블·인덱스·매핑 등 구현 상세는 1-2와 해당 소단계에서 점검한다. 계약 확정은 구현 시작 지시를 의미하지 않는다. [확정 정책](01-mysql-order.md)과 함께 관리한다.

## 구성과 소유권

판매 서버는 루트 Spring Boot 프로젝트를 유지하고 `mock-pg` Gradle 하위 프로젝트를 별도 실행 애플리케이션으로 추가하는 안이다. 판매 서버는 `com.wooyongjeong.limitedsale`, Mock PG는 `com.wooyongjeong.mockpg` 패키지를 제안한다. Mock PG에 판매 서버 코드를 의존시키거나 판매 서버가 PG 테이블을 직접 조회하지 않는다.

| 도메인 | 데이터·기능 소유권 | 공개 계약 초안 |
|---|---|---|
| member | 이메일·비밀번호 해시·권한, 인증 어댑터 | MemberRegistration, MemberAuthentication, MemberQuery |
| product | 제품 이름·설명·기준 가격 | ProductCommand, ProductQuery |
| sale | 이벤트 조건·상태, 전체 수량, 사용자별 수량, 주문별 점유 | SaleCommand, SaleQuery, SaleReservation |
| order | 주문·요청 키, 주문 시점 제품·가격, 전체 주문 처리 조합 | OrderCommand, OrderQuery |
| payment | 판매 서버의 결제 기록, PG 요청·조회·종료, 결제 결과 복구 | PaymentCommand, PaymentQuery, PaymentRecovery |

도메인별로 api/application/domain/infrastructure/presentation을 둔다. 외부 도메인은 api만 참조한다. 공통 응답·ResponseCode와 공통 시스템 오류는 common.web에, 업무별 성공·오류 enum은 각 도메인의 presentation.code에 둔다. member의 인증 필터·핸들러도 공통 응답을 사용한다.

order.application이 sale.api와 payment.api를 호출한다. sale은 이벤트 생성 때 product.api를 조회한다. 인증 경계가 넘기는 사용자 ID를 사용하며, 주문마다 member 저장소를 직접 읽지 않는다. payment에서 order 구현을 역호출하지 않는다. payment는 결제 상태를 복구하고, order의 복구 작업은 payment.api에서 결과를 확인해 주문과 수량을 마무리한다.

## 합의한 주문·결제 상태

| 주문 상태 | 의미 | 수량 처리 |
|---|---|---|
| AWAITING_PAYMENT | 생성 완료, 아직 결제 요청 전 | 임시 점유 유지 |
| PAYMENT_PENDING | 결제 요청 시작, 처리 중 또는 결과 미확인 | 임시 점유 유지 |
| CONFIRMED | 결제 성공 확인 및 주문 확정 | 점유를 확정 구매로 전환 |
| PAYMENT_FAILED | 명확한 결제 실패 확인 | 점유 해제 |
| EXPIRED | 5분 정리 과정에서 PG 종료 확정 확인 | 점유 해제 |

판매 서버의 결제 상태는 READY/PROCESSING/UNKNOWN/SUCCEEDED/FAILED/CLOSED를 제안한다. UNKNOWN은 통신 실패 등으로 결과를 모르는 판매 서버 상태이며 PG의 실패 상태가 아니다. PG는 키별 최종 결과를 영속 보관하며 성공·실패·종료를 나중에 반대로 바꾸지 않는다.

주문 생성과 결제 요청은 서로 다른 API다. 결제 실패·만료가 최종 확정된 주문은 새 결제 키로 되살리지 않고, 다시 구매하려면 새 주문 요청 키로 새 주문을 생성하는 안을 제안한다. 새 주문은 현재 이벤트 상태·재고·구매 한도를 다시 검사한다.

## 트랜잭션과 복구

1. 주문 생성 시 기존 사용자+요청 UUID를 확인한다. 같은 입력이면 기존 주문을 반환하고 다른 입력이면 409로 거절한다.
2. 신규 주문에는 요청 입력과 UUID, 주문 식별자, 서버가 정한 제품명·단가·수량·금액을 보관한다.
3. 같은 MySQL 트랜잭션에서 이벤트 잠금, 잠금 후 DB 시각·상태 검사, 사용자 수량 검사, 주문별 점유와 주문·결제 READY 기록 생성을 처리한다.
4. 결제 요청 API는 본인 주문과 상태를 확인하고 결제 시작 상태를 커밋한 뒤 PG HTTP를 호출한다. PG 네트워크 응답을 기다리는 동안 재고·주문 DB 잠금을 유지하지 않는다.
5. PG 결과는 payment가 보관한다. order는 확정된 결과를 확인하고 주문 상태와 sale의 점유 확정·해제를 하나의 로컬 트랜잭션으로 반영한다.
6. PG 결과 저장 후 주문 반영에 실패하면 복구 작업이 다시 적용한다. 이미 확정·해제된 점유를 다시 변경하지 않는다.

기존 점유의 확정·해제는 이벤트 종료·중단이나 사용자 세션 만료로 막지 않는다. 신규 수량 점유와 기존 주문 정리는 다른 작업이다.

주문이 이미 존재하는 작업은 주문 → 이벤트 → 사용자 수량 → 점유 순서로 잠금을 획득하는 안이다. 이벤트 관리자 작업도 같은 이벤트 행 잠금을 사용한다. 생성 시 사용자+요청 키 중복은 DB 유니크 제약으로 막고, 충돌한 트랜잭션 종료 후 보관된 요청 결과를 새 트랜잭션에서 조회한다. SQL 순서는 실제 MySQL 동시성 테스트로 확인한다.

격리는 READ COMMITTED, 핵심 수량 행은 명시적 쓰기 잠금으로 관리하는 안이다. 초기에는 이벤트 행에서 수량 작업을 직렬화하고, 성능 병목을 관측한 후 대안을 비교한다. JPA의 영속 엔티티는 infrastructure.persistence에 두고 domain의 규칙과 분리한다.

복구 대상에는 결제 미요청, 결제 처리 중, 결과 미확인, 결제 결과와 주문의 불일치를 포함한다. 전체 작업의 다음 실행 시각과 임대 토큰·만료·버전 정보를 purchase_orders에 모아 여러 서버가 같은 작업을 무제한 중복 처리하지 않게 한다. 서버가 죽으면 임대 만료 후 다른 서버가 이어서 처리한다. 중복 실행 자체를 완전히 없앤다고 가정하지 않고 상태 전이와 PG 키로 방어한다.

기본 10초 재조회는 영속적인 다음 실행 시각으로 관리한다. PG가 계속 응답하지 않으면 5분 이후 운영 확인 대상으로 표시하고 점유를 유지하며 재확인을 이어가는 안이다. 구체적인 임대 시간·배치 크기·실패 로그 주기는 테스트 환경에서 검증할 설정값으로 둔다.

## DB 테이블 기본안

| 스키마·테이블 | 주요 데이터와 제약 |
|---|---|
| 판매 members | 내부 ID, 정규화 이메일과 닉네임 비교 키 각각 유니크, 닉네임, 비밀번호 해시, USER/ADMIN |
| 판매 products | 제품 이름·설명·기준 가격 |
| 판매 sales | 제품 ID·정보 보관, 판매 가격·기간, 중단 여부, 총수량·점유 수량·판매 수량, 사용자 구매 한도 |
| 판매 sale_buyer_quantities | (sale_id, member_id) 유니크, 사용자 점유·확정 구매 수량 |
| 판매 sale_reservations | order_id 유니크, 이벤트·사용자·수량·점유 상태 |
| 판매 purchase_orders | 주문 공개 ID 유니크, (member_id, request_key) 유니크, 이벤트·제품명·단가·수량·금액·상태, 마감·다음 복구·임대 정보 |
| 판매 order_request_results | 회원별 요청 키와 원본 입력, 생성 주문 참조 또는 영속 업무 거절 사유 |
| 판매 payments | order_id와 PG 키 각각 유니크, 금액·결제 상태·요청·확인 시각. 복구 예약은 주문 테이블이 소유 |
| PG mock_payments | PG 키 유니크, 금액·처리 시나리오·최종 결과·종료 기록 |

사용 가능한 재고는 총수량-점유-판매 수량으로 계산하고 별도의 변경 가능한 잔여 수량을 중복 저장하지 않는 안이다. 사용자 구매 한도는 기본 1, 허용 범위는 1~이벤트 총수량이다.

DB 내부 PK는 BIGINT, 외부 주문 ID·결제 키는 UUID를 제안한다. 금액은 signed BIGINT와 Java long을 사용하고 음수·범위·곱셈 오버플로를 검증한다. 개당 최대 10억원×최대 100만개는 10^15원이다. 시각은 UTC 마이크로초 정밀도로 저장하며 API 입출력에는 오프셋이 명시된 ISO 8601을 사용한다.

같은 도메인의 테이블에만 JPA 연관관계를 두고 다른 도메인은 식별값만 보관한다. 판매 스키마의 참조는 물리 FK와 RESTRICT로 보호하며 UUID는 BINARY(16), 상태는 VARCHAR+CHECK로 저장한다. PG 스키마·계정은 판매 DB와 분리하고 각 앱이 자신의 Flyway 이력을 관리한다. PG 초기화는 판매 앱의 트랜잭션에 참여하지 않는다.

확정 입력 길이: 이메일 최대 254자, 제품명·이벤트명 100자, 설명 2,000자. 가격·수량·비밀번호 등 이미 정한 정책을 따른다. 확정 길이값을 적용한 테이블·인덱스 상세는 1-2 진입 시 점검한다.

## HTTP API 기본안

기본 경로는 `/api/v1`을 제안한다. 회원가입은 USER 생성까지만 처리하고 로그인은 별도 API로 수행하는 안이다.

| 대상 | API 초안 | 결과 |
|---|---|---|
| CSRF | GET /csrf | 200, CSRF 토큰. 신규 로그인·로그아웃 후 토큰 갱신 처리 |
| 회원가입 | POST /members | 201, 이메일·닉네임·권한. 내부 ID와 비밀번호 해시는 반환하지 않음 |
| 로그인·로그아웃 | POST /sessions, DELETE /sessions/current | 200, 로그인 정보 또는 data:null |
| 내 정보 | GET /members/me | 200, 본인 정보 |
| 공개 조회 | GET /products, /products/{id}, /sales, /sales/{id} | 200, 목록·상세 |
| 제품 관리 | POST /admin/products | 201, 생성한 제품 |
| 이벤트 관리 | POST /admin/sales, PATCH /admin/sales/{id}, DELETE /admin/sales/{id} | 201 또는 200, 앞서 합의한 변경·삭제 정책 적용 |
| 중단·재개 | POST /admin/sales/{id}/stop, /resume | 200, 이벤트 상태 |
| 주문 생성 | POST /orders, Idempotency-Key 필수 | 최초 201, 기존 요청 재시도 200. 본문 saleId·quantity |
| 결제 요청 | POST /orders/{id}/payment | 결과 확인 완료 200, 3초 내 미확인 또는 처리 중 202 |
| 내 주문 | GET /orders, /orders/{id} | 200, 본인 목록·상세. 타인의 주문은 404로 취급하는 안 |

결제 요청에 금액이나 PG 키를 클라이언트가 지정하지 않는다. 서버가 주문에 저장한 금액·키를 사용한다. 결제 요청에서 PG가 명확히 거절하면 409/PAYMENT_DECLINED와 data:null을 응답하는 안이다. 결과 미확인은 202/PAYMENT_PENDING이다. 주문 조회 자체는 성공하면 200이며 data의 주문·결제 상태로 실패·대기·확정을 표현한다.

응답은 ApiResponse<T>를 사용한다. 예시 코드값은 MEMBER_CREATED, ORDER_CREATED, PAYMENT_PENDING, SALE_SOLD_OUT, PURCHASE_LIMIT_EXCEEDED, IDEMPOTENCY_CONFLICT 등이며 도메인별 성공·오류 enum에서 고정한다. common.web의 ResponseCode는 HTTP 상태·코드 문자열·기본 메시지 계약을 제공한다. 프레임워크 예외나 내부 비밀번호·결제 인증값을 message에 그대로 노출하지 않는다.

| 상황 | 상태 초안 |
|---|---|
| JSON 파싱·입력 검증 오류, UUID 헤더 누락·형식 오류 | 400 |
| 미인증·로그인 실패 | 401 |
| 권한 부족·CSRF 실패 | 403 |
| 없음 또는 다른 사용자의 주문 | 404 |
| 품절·구매 한도 초과·이벤트 기간 외·중단·요청 키 입력 충돌·결제 명확 거절 | 409 |
| 로그인 시도 제한 | 429 |
| 예상하지 못한 서버 오류 | 500 |
| Redis 장애로 인증 불가 | 503 |

400 검증 오류의 data는 field/reason 항목 목록을 제안한다. 그 밖에 데이터가 없는 오류·성공은 data:null이다. 공개 목록과 내 주문 목록은 page/size 방식으로 시작하고 기본 20, 최대 100을 적용한다. 정렬 기준과 허용 필터는 각 조회 소단계에서 확정한다.

요청 키는 사용자별로 TTL 없이 보관한다. 같은 키·입력의 성공은 최신 주문 상태를, 없는 이벤트·기간 외·중단·한도 초과·재고 부족의 업무 거절은 원래 결과를 반환한다. 다른 입력은 409이며 입력·인증·CSRF 오류와 시스템 장애는 보관하지 않는다. HTTP 응답 유실 후 같은 키로 재시도할 수 있다. 상세 계약은 [1-7-1](01-7-1-order-reservation.md)을 따른다.

## Mock PG HTTP 기본 계약

기본 동작은 결제 성공이다. 실패·처리 지연·결제 성공 후 응답 유실은 로컬·테스트 ADMIN 제어에서 명시적으로 지정하며 랜덤 실패를 사용하지 않는다.

판매 서버 전용 인증값을 설정으로 주입해 기계 간 호출을 제한하는 안이다. PG 시뮬레이션 변경은 로컬·테스트 환경의 판매 서버 ADMIN 경계를 통해 호출하며 공개 사용자가 PG 결과를 선택하지 못하게 한다. 계정·비밀번호·내부 인증값은 저장소에 커밋하지 않는다.

| 작업 | 동작 초안 |
|---|---|
| 결제 요청 | 고정 키·주문 금액. 새 키면 처리 시작, 같은 키·같은 금액은 기존 결과, 다른 금액은 409 |
| 결과 조회 | 키의 현재·최종 결과 반환. 없는 키는 404이며 이것만으로 점유를 해제하지 않음 |
| 종료 요청 | 같은 키·금액 기준으로 이미 성공이면 성공 반환, 미결제면 CLOSED 확정. 아직 없는 키도 CLOSED 기록을 먼저 생성해 뒤늦은 결제를 차단 |

5분 전 조회에서 PG 키가 없으면 같은 키로 결제 요청을 재개할지는 판매 서버 결제 시작 이력을 확인한다. 사용자가 결제 API를 호출하지 않은 주문을 복구 작업이 임의로 결제하지 않는다. 5분이 지나면 미결제 정리로 진입한다.

## 보안·성능 설정 기준

Argon2id는 OWASP 최소 권장값인 메모리 19MiB·반복 2·병렬도 1 이상을 기준으로 설정하고 실제 JDK·자원에서 검증한다. 해시 비용을 줄여 주문 부하 테스트 수치를 높이지 않는다. 로그인·세션 준비와 주문 부하는 분리한다. 참고: [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Spring PasswordEncoder](https://docs.spring.io/spring-security/reference/6.5/features/authentication/password-storage.html).

쿠키·CSRF·30분 세션 만료와 로그인 제한은 확정 정책을 따른다. 로그인 제한 구간은 정규화 이메일+IP 조합의 첫 실패부터 기본 5분이며 추가 실패로 연장하지 않는다. 1~4번째 실패는 401, 5번째부터 구간 만료까지 429다. 차단 전 로그인 성공 시 해당 조합의 실패 기록을 초기화하고 다른 IP의 기록은 유지한다. 현재는 직접 연결한 IP를 사용하고 전달 헤더는 무시한다. 프록시 도입 시 신뢰 범위를 별도로 정한다. 알 수 없는 이메일과 비밀번호 불일치는 같은 코드·메시지를 반환한다. 선택 이유와 남은 설계는 [1-4 상세 협의](01-4-session-auth.md)에 기록한다.

1-2에서 합의한 저장 방식과 복구 예약 책임은 [상세 설계](01-2-mysql-schema-and-boundaries.md)에 기록한다.
