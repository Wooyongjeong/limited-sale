# 1-7-1 주문 생성·수량 점유·멱등성

상태: 1-7-1 구현·워커 보완·주 에이전트 검증·위키 갱신 완료.

[1-7 작업 분할](01-7-order-payment.md), [기존 계약](01-contracts.md), [1단계 정책](01-mysql-order.md)을 따른다. 요청 결과 보관과 최소 상세 조회는 이 문서의 새 합의를 우선한다.

## 범위와 협업

Terra high 워커가 구현하고 주 에이전트가 독립 리뷰·실행 검증한다. 발견한 문제는 같은 워커의 보완과 재검증을 반복한 뒤 위키를 갱신·검증한다. 이번에는 주문 생성·수량 점유·요청 결과 보관·본인 주문 상세만 구현한다. Mock PG HTTP·결제 요청·확정·해제·복구 스케줄러는 후속 단위이며 내 주문 목록은 1-8이다.

## API 계약

- `POST /api/v1/orders`: 로그인·CSRF 필수, UUID `Idempotency-Key` 헤더와 `{saleId, quantity}` 본문. 수량은 정수 1~1,000,000이다. 금액·PG 키는 서버가 정한다. 잘못된 JSON·타입·UUID·중복/미지 필드는 400이다.
- `GET /api/v1/orders/{orderId}`: 외부 UUID로 본인 주문만 조회한다. 없는 주문·타인 주문은 404다.
- 생성·재시도·상세의 data는 `orderId, saleId, productId, productNameSnapshot, quantity, unitPrice, totalAmount, status, createdAt, updatedAt, expiresAt`이다. 내부 PK·회원 ID·요청 키·PG 키는 노출하지 않는다.
- 최초 생성은 201, 같은 키·입력의 성공 재조회는 최신 주문 상태와 200이다. 상세는 200이다.
- 사용자별 UUID 키를 TTL 없이 보관한다. 같은 키로 이벤트·수량을 바꾸면 409이며 기존 결과를 변경하지 않는다.
- 품절·기간 외·중단·한도 초과뿐 아니라 없는 이벤트 404도 키별로 저장한다. 같은 키·입력은 조건이 바뀌어도 원래 HTTP 상태·업무 코드와 `data:null`을 반환한다. 새 구매 시도에는 새 키를 사용한다.
- 판정 우선순위는 기존 키 결과 → 없는 이벤트 → 기간 외 → 중단 → 사용자 한도 → 가용 재고다. 공개 이벤트 상태 표시 순서와 구분한다.
- 입력 오류·인증/CSRF 실패·시스템/DB 장애는 결과로 보관하지 않는다.

## 영속 설계

order 소유의 `order_request_results`를 새 Flyway 버전으로 추가한다. 적용된 마이그레이션은 수정하지 않는다.

- 회원 ID·요청 UUID(BINARY(16))·원본 이벤트 ID·수량·CREATED/REJECTED 결과·주문 참조 또는 안정적인 업무 거절 사유·시각을 저장한다.
- `(member_id, request_key)` 유니크, 실제 회원·주문 참조에는 FK RESTRICT를 적용한다. 없는 이벤트 요청도 저장하므로 원본 요청 이벤트 ID에는 FK를 두지 않는다.
- CHECK로 CREATED는 주문 참조만, REJECTED는 거절 사유만 갖도록 제한한다. 상태는 VARCHAR·CHECK와 명시적 Java enum 매핑이다.
- 성공은 주문 참조로 최신 상태를 읽는다. 거절에 가짜 주문·점유·결제를 만들거나 프레임워크 예외·응답 메시지를 그대로 저장하지 않는다.

## 트랜잭션과 동시성

1. order가 로컬 트랜잭션을 시작한다. sale.api가 이벤트 및 기존 사용자 수량 행을 잠근 뒤 별도 쿼리로 최신 MySQL UTC 시각을 읽는다.
2. 수량 쓰기 전에 기간·중단·사용자 한도·재고를 모두 판정한다. 허용하면 전체·사용자 수량을 점유하고 잠긴 이벤트 스냅샷과 판정 시각을 반환한다.
3. order가 스냅샷으로 AWAITING_PAYMENT 주문을 만든 뒤 sale.api로 주문별 점유를 연결하고 payment.api로 고정 PG UUID의 READY 결제를 준비한다. 성공 요청 결과까지 같은 트랜잭션에서 커밋한다.
4. 업무 거절은 수량·주문·결제 변경 없이 거절 결과만 커밋한다. 트랜잭션 메서드가 타입으로 거절을 반환하고 HTTP 변환은 밖에서 수행해 예외 롤백으로 기록을 지우지 않는다.
5. 주문 요청 키 또는 요청 결과 키의 정확한 유니크 충돌은 패배한 트랜잭션 전체를 종료한 뒤 새 컨텍스트에서 승자의 결과를 조회한다. rollback-only 트랜잭션 안에서 재조회하지 않는다. 무관한 DB 오류는 전체 롤백·기존 공통 500이며 무한 자동 재시도하지 않는다.

sale.api·payment.api는 외부 트랜잭션에 참여하며 REQUIRES_NEW나 PG HTTP를 사용하지 않는다. 다른 도메인의 엔티티·저장소를 참조하지 않는다. 로그인 ID도 member.api 계약으로 전달한다.

총액은 서버에서 정수로 계산한다. 기본 만료는 생성 후 5분으로 설정 가능하며 주문에 복구 예약을 저장한다. 이번에는 예약만 남기고 자동 정리·복구는 1-7-4에서 구현한다.

## 검증 기준

- 실제 MySQL에서 정상 생성·다수 수량·한도 내 여러 주문 및 모든 업무 거절을 검증한다.
- 전체·사용자 한도 초과 방지와 정상 조건에서 가용 수량을 실제 소진하는지 확인한다.
- 같은 키·입력 동시 요청, 같은 키·다른 이벤트/수량 경쟁, 사용자별 동일 UUID, 응답 유실 후 재시도를 검사한다.
- 거절 후 조건이 바뀌어도 같은 결과를 반환하며 없는 이벤트 404도 보존되는지 확인한다.
- 중간 DB 실패를 주입해 주문·전체 수량·사용자 수량·점유·결제·성공 요청 결과가 모두 롤백되는지 확인한다.
- 시작 포함·종료 제외, 잠금 대기 중 종료 경과, 중단과 점유 경쟁을 확인한다.
- 상세 소유권·UUID·인증·CSRF·엄격 JSON·내부 값 비노출을 검사한다.
- 기존 회원·세션·제품·이벤트·스키마·패키지 경계 회귀 검사와 전체 build를 수행한다. 실패·건너뜀을 숨기지 않는다.

## 구현 내용과 검증 범위

- `limited-sale.order.expiration`은 양의 기간이며 기본값은 `PT5M`이다. 점유 판정에 사용한 DB 시각을 주문 생성 시각으로 사용하고 만료 시각을 다음 복구 예약 시각으로 저장한다.
- 판매 점유는 이벤트와 기존 회원 수량 행을 잠근 뒤 별도로 DB UTC 시각을 읽어 순서대로 판정한다. 결과 레코드·주문·점유·READY 결제는 주문 트랜잭션에서 함께 처리하며, 키 유니크 충돌은 해당 트랜잭션 종료 뒤 새 트랜잭션에서 승자의 결과를 조회한다.
- 거절 코드는 `SALE_NOT_FOUND`, `SALE_OUTSIDE_PERIOD`, `SALE_STOPPED`, `PURCHASE_LIMIT_EXCEEDED`, `SALE_SOLD_OUT`이며 키와 입력이 충돌하면 `IDEMPOTENCY_CONFLICT`다. 최초 생성은 `ORDER_CREATED`, 상세 및 성공 재생은 `ORDER_FOUND`를 반환한다.
- 실제 MySQL 테스트는 전체 재고가 충분한 상태에서 동일 사용자의 서로 다른 키가 구매 한도를 놓고 경쟁하는 경우를 포함한다. 같은 키 경쟁과 종료 경계·중단 경쟁은 MySQL 프로세스 목록의 잠금 대기 SQL을 확인한 뒤 잠금을 해제한다.
- 실제 MySQL 테스트는 수량과 사용자 한도, 각 거절의 재생, 같은 키·다른 사용자·다른 입력의 동시 요청, 재고 소진, 결제 기록 오류 롤백, 잠금 대기 중 종료 및 중단을 검증한다. 주 에이전트의 독립 검증과 위키 갱신은 아래 체크리스트에서 별도로 관리한다.
- 워커 환경에서 Java 21과 격리된 MySQL 8.4.7·Redis Testcontainers로 `./gradlew clean build`를 실행해 단위 37개와 통합 62개가 통과했다(실패·건너뜀 0). 응답 유실 재시도는 첫 응답을 버리고 같은 요청을 다시 보내는 방식으로, 중단 경쟁은 잠긴 이벤트 행을 다른 DB 트랜잭션에서 중단하는 방식으로 검증했다.

## 주 에이전트 검증과 완료 근거

2026-11-12 주 에이전트 리뷰에서 새 영속 작업을 Spring Data JPA 저장소로 통일하고, Hibernate 제약 예외 분류를 infrastructure로 옮기도록 요청했다. 같은 워커가 보완했으며 사용자 한도 경쟁 및 실제 DB 잠금 대기 확인 테스트도 추가했다. 보완 후 소스·트랜잭션 경계·정확한 유니크 제약 분류·롤백 후 조회를 다시 검토했다.

- 주 에이전트가 Java 21에서 `./gradlew clean build`를 독립 실행했다. 단위 37개·통합 62개가 모두 통과했으며 실패·오류·건너뜀은 0개다. 로그는 `/tmp/limited-sale-1-7-1-primary-build.log`이고 테스트 근거는 `build/test-results/test/`, `build/test-results/integrationTest/`다.
- [주문 위키](../wiki/orders.md)를 추가하고 위키 목차·구조·판매 이벤트·DB·운영 설명을 현재 구현과 맞췄다. 위키의 모든 로컬 링크가 존재하며 Mermaid 도식 20개를 PNG로 렌더링했다. 새 주문 흐름 도식도 이미지로 확인했다. 임시 렌더 결과는 `/tmp/limited-sale-wiki-render/1-7-1/`에 있다.
- `git diff --check`와 변경 문서 링크 검사를 수행했다. 이후 사용자가 직접 추가 리뷰·수정과 PR·main 머지를 지시했다.
- 응답 유실 검사는 첫 응답을 버린 재요청이며, 네트워크 장애 주입은 아니다. 중단 경쟁은 잠긴 행을 별도 DB 트랜잭션에서 중단시켜 검증한다. PG 결제 실행·확정·해제·복구 실행기·주문 목록은 후속 범위로 남는다.

### 머지 전 추가 리뷰

사용자 지시에 따라 주 에이전트가 직접 보완했다. enum 이름 문자열에 의존하는 변환을 빠짐없는 switch로 바꿔 상태 변경 시 컴파일러가 누락을 확인하도록 했다. 단가 10억 원·수량 100만 개의 총액이 주문·결제 DB와 HTTP 응답에 long 정수로 정확히 유지되는 통합 검사도 추가했다. 외부 HTTP 계약 DTO 분리는 다음 별도 refactor 브랜치에서 진행한다.

추가 리뷰 후 Java 21 `./gradlew clean build`를 실행해 단위 37개·통합 63개, 총 100개가 통과했다(실패·오류·건너뜀 0). 최종 코드 검증 로그는 `/tmp/limited-sale-1-7-1-merge-build.log`다.
