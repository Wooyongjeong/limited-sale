# 1-8 주문 결과 조회

상태: 정책 확정·구현·독립 검증·위키 갱신 완료. 사용자가 "1-8 정책 협의 너가 추천안으로 다 하고, 완료되면 구현도 시작"하라고 지시해 주 에이전트 추천안으로 확정했다.

[1단계 정책](01-mysql-order.md), [기존 계약](01-contracts.md), [1-7-1 주문 생성](01-7-1-order-reservation.md)을 따른다. 이 문서는 내 주문 목록의 새 합의를 우선한다.

## 범위

- 새로 만드는 기능은 `GET /api/v1/orders` 내 주문 목록 하나다.
- 상세 `GET /api/v1/orders/{orderId}`는 1-7-1에서 만들었고 계약을 바꾸지 않는다.
- 종료 후 재시도와 응답 유실 후 재시도는 이미 기존 주문으로 수렴한다. 주문 생성이 요청 키 결과를 이벤트 기간 판정보다 먼저 읽기 때문이다. 1-8은 이 동작을 목록과 함께 검증한다.
- 사용자 주문 취소·환불, 관리자 주문 조회는 범위 밖이다.

## 확정한 정책과 이유

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| 접근 | 로그인 필수. 세션 회원의 주문만 반환. 미로그인은 401 | 기존 계약의 본인 주문 조회 원칙 |
| 페이지 | `page` 0 이상 기본 0, `size` 1~100 기본 20. 형식·범위 오류는 400 | 공개 이벤트 목록과 같은 검증 규칙 |
| 정렬 | 최신 주문 먼저. 내부 주문 ID 내림차순 | 생성 순서와 같고 `INDEX(member_id, id)`를 그대로 쓴다. 생성 시각은 같은 값이 생길 수 있어 기준으로 쓰지 않는다 |
| 필터 | 1-8에서는 두지 않음 | 회원별 주문 수는 구매 한도로 작다. 상태·이벤트 필터는 필요가 확인되면 추가한다 |
| 포함 상태 | 결제 대기·확인 중·확정·실패·만료 모두 포함 | 사용자가 실패·만료도 확인해야 같은 이벤트에 다시 주문할지 판단한다 |
| 업무 거절 요청 | 목록에 넣지 않음 | 품절·기간 외 등 거절은 주문을 만들지 않았다. 같은 키 재시도로만 확인한다 |
| 항목 형식 | 상세와 같은 필드. 결제 상태 포함 | 클라이언트가 목록과 상세를 같은 모델로 다룬다. 큰 필드가 없어 요약형을 따로 둘 이유가 없다 |
| 가격 | 주문에 저장한 판매 가격·총액 반환 | 제품 기준 가격이나 현재 이벤트 값을 다시 읽지 않는다 |
| 페이지 응답 | `items, page, size, totalElements, totalPages` | 공개 목록과 같은 모양 |
| 빈 결과 | 주문이 없거나 마지막 페이지를 넘으면 빈 목록 200 | 공개 목록과 같음 |
| 결제 상태 조회 | 한 페이지의 결제 상태를 `payment.api`로 한 번에 조회 | 주문마다 결제를 따로 읽으면 페이지당 최대 100번 추가 조회가 생긴다 |
| 일관성 | READ COMMITTED에서 총수와 내용의 완전한 스냅샷 일치는 보장하지 않음 | 공개 목록과 같은 선택. 복구 작업이 동시에 상태를 바꿀 수 있다 |

## 검증 기준

- 다른 회원의 주문은 목록에 나오지 않는다. 미로그인 요청은 401이다.
- 여러 주문이 최신순으로 나오고, `page`·`size` 경계와 기본값, 잘못된 값의 400이 동작한다.
- 이벤트 판매 가격을 제품 기준 가격과 다르게 만든 뒤, 목록이 주문에 저장한 가격과 총액을 반환한다.
- 결제 성공·거절 후 목록의 주문 상태와 결제 상태가 상세와 같다.
- 판매 종료 후 같은 키로 재시도하면 200과 기존 주문을 받고, 목록에는 주문이 하나만 있다.
- 첫 응답을 버리고 같은 키로 재시도해도 목록에는 주문이 하나만 있다.
- 업무 거절된 요청은 목록에 나오지 않는다.
- 실제 MySQL·Redis 통합 테스트로 검증한다.

## 구현 중 정한 세부 사항

워커가 문서에 없던 다음 사항을 정했고 주 에이전트가 리뷰에서 받아들였다.

- 성공 코드는 `ORDERS_FOUND`(200)다. 기존 `SALES_FOUND`·`PRODUCTS_FOUND`와 같은 이름 규칙이다.
- `page`·`size` 검사는 `OrderJson`에 있다. 메시지·검사 순서·응답 본문은 판매 목록과 같고 테스트가 두 본문을 비교한다.
- 오프셋이 회원의 주문 수 이상이면 페이지 조회 없이 빈 목록을 반환한다. Spring Data가 int 범위를 넘는 오프셋을 적용하지 못하는 경우도 이 경로로 처리한다.
- 결제 행이 없는 주문은 상세 조회와 같이 오류로 처리한다. 결제 상태를 null로 숨기지 않는다.

## 검증 결과

Opus high 워커가 구현하고 주 에이전트가 diff를 리뷰한 뒤 독립 실행했다.

- `./gradlew clean build` 성공. 판매 앱 단위 76개, 실제 MySQL·Redis 통합 101개, Mock PG 단위 11개·통합 15개 모두 실패·오류·건너뜀 0개.
- 통합 테스트는 소유권과 401, 최신순과 페이지 경계, 잘못된 값 400, 저장 가격 유지, 결제 성공·거절 후 목록과 상세의 일치, 종료 후 재시도와 응답 유실 후 재시도의 주문 1건 수렴, 업무 거절 미포함을 HTTP로 검사한다.
- 페이지당 결제 조회가 한 번이라는 점은 코드로 확인했고 SQL 실행 횟수는 측정하지 않았다. 목록 쿼리의 인덱스 사용도 EXPLAIN으로 확인하지 않았다.
- `python3 scripts/check-wiki-diagrams.py`와 `git diff --check` 통과.
