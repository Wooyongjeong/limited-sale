## 상태

착수 전. 아래 내용은 단계별 도입 계획이며 Redis의 세부 정책은 아직 확정하지 않았다.

## 확정한 방향

Redis 활용 경험을 포트폴리오에 포함하고 MySQL 기반 결과와 비교한다. 1단계에서 확정한 제품·구매 한도·Mock PG 정책을 이어받는다.

## 구현 계획

조회 캐시와 분산 요청 제한을 기본안으로 한다. 1단계에서 도입한 Redis 세션을 유지하며 이 단계에서 캐시·분산 요청 제한을 추가한다. 측정한 병목과 보호할 자원을 먼저 확인하고 2-1에서 적용 범위를 함께 확정한다.

|---|---|---|
| 2-1. 도입 목적과 장애 정책 | 1-11 결과로 캐시 대상과 요청 제한 목적을 결정. 키 소유권·TTL·제한 단위·거절 응답·Redis 장애 시 동작을 기록 | 무엇을 줄이거나 보호할지 측정 지표로 정의하고, 캐시 실패와 요청 제한 실패의 처리 정책을 각각 정함 |

| 2-5. 장애와 데이터 대조 | Redis 중단·재시작·키 만료 시나리오, 캐시 재생성과 DB 대조 | 2-1의 장애 정책이 동작하고 기존 DB 정합성 검증을 통과함. 캐시 복구 후 다시 조회 가능 |
| 2-6. 비교 실험 | 조회 캐시 켜기·끄기, 요청 제한 켜기·끄기를 분리해 실험 | 인증·세션 조건을 고정한 상태에서 지연·DB 부하·캐시 적중률·거절률·실제 주문 처리량을 보고하고 1-11 결과와 비교함 |

## 검증 기준

조회 캐시 효과와 요청 제한 효과를 분리해 측정한다. 요청을 많이 거절한 결과를 주문 처리량 향상으로 설명하지 않는다. 동일 조건에서 지연·DB 부하·실제 주문 처리량·거절률을 비교한다. Redis 장애·재시작·키 만료 후에도 재고·구매 한도·주문·결제의 규칙을 유지하는지 DB 기록과 대조한다.

## 미정 사항

- 캐시 대상·키·TTL·무효화와 캐시 실패 시 동작
- 요청 제한 알고리즘·단위·임계값·거절 응답과 Redis 장애 시 동작
- 기존 주문 조회와 재시도에 제한을 적용할지 여부
- Redis 관측 지표와 비교 실험 조건
- 세션·캐시·요청 제한의 키 구분과 메모리·만료·장애 영향 분리

Redis 수량 사전 판정은 미확정 확장안이다. 2-6에서 필요성이 확인되면 MySQL과의 불일치 복구 설계를 별도로 논의한다.
