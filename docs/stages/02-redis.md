## 2-1 확정 정책

### 출발점이 된 사실

- 1-11의 병목은 판매 이벤트 행 하나의 `SELECT ... FOR UPDATE` 직렬화다. 커넥션 대기는 그 결과다([1-11 병목 분석](01-11-baseline-load-test.md#병목-분석)). 조회 캐시도 요청 제한도 이 잠금을 없애지 않는다.
- 1-11은 조회 API에 부하를 주지 않았다. 캐시 효과는 새 시나리오로만 보일 수 있다.
- 판매 이벤트 응답에는 잔여 수량이 없다. 상태는 `SaleService`가 조회 시각으로 계산한다(`statusAt(now)`). 2-3에서 바로잡음: 상태 중 `SOLD_OUT`은 확정 수량으로 정해지고, 조회 시각은 MySQL `NOW()`에서 읽는다(아래 "2-3 확정 정책").
- 1-11 기준선은 Java 21·Spring Boot 3.5.16에서 측정했다. 지금 코드는 Java 25·Spring Boot 4.1.2다.

|---|---|---|---|

| 4 | 캐시 장애 | Redis 실패·타임아웃이면 DB에서 조회해 응답한다. 짧은 명령 타임아웃을 두고 실패 지표를 남긴다 | 캐시는 최적화다. 캐시 장애가 조회 실패가 되면 안 된다 |

| 6 | 알고리즘·임계값 | Lua 스크립트로 원자적으로 증가·만료하는 고정 창. 기본 회원당 1초 5회, 설정으로 변경 | 보여줄 핵심은 여러 인스턴스가 한 카운터를 원자적으로 공유하는 것이다. 창 경계의 순간 2배 허용은 알려진 한계로 기록한다 |
| 7 | 거절 응답 | HTTP 429, 코드 `ORDER_RATE_LIMITED`, `Retry-After` 헤더. 요청 키를 기록하지 않고 수량을 차감하지 않는다. 같은 요청 키의 재시도도 횟수에 포함한다 | 거절된 요청은 주문이 아니므로 같은 키로 다시 보내면 정상 처리된다. 재시도를 빼면 제한을 우회할 수 있다 |

| 10 | 관측 | 앱의 Redis 명령 지연·실패 지표, 캐시 적중·미적중·실패 카운터, 요청 제한 허용·거절·통과(장애) 카운터, `redis_exporter`로 메모리·연결 수 | 캐시·제한의 효과와 장애를 지표로 구분해야 한다. 회원 ID는 지표 라벨로 쓰지 않는다 |

- 2-6에는 조회·주문 혼합 시나리오와 남용 사용자 혼합 시나리오를 추가한다. 세부 부하 조건은 2-6에서 정한다.

## 2-4 확정 정책

2026-11-23 사용자와 선택지로 확정했다. 2-1 #5~#8을 그대로 따른다. 대상은 `POST /api/v1/orders`와 `POST /api/v1/orders/{id}/payment`, 단위는 인증된 회원, 기본 1초 5회(설정 가능)다. 거절은 429 `ORDER_RATE_LIMITED`와 `Retry-After`이며 요청 키를 기록하지 않고 수량을 차감하지 않는다. 같은 요청 키의 재시도도 횟수에 포함한다. Redis 장애 시에는 제한 없이 통과시킨다. 조회 GET에는 적용하지 않는다.

| # | 항목 | 확정 내용 | 이유 |
|---|---|---|---|
| 1 | 카운터 | 주문 생성과 결제를 따로 센다. 각각 회원당 기본 1초 5회 | 주문 요청을 몰아 보내도 이미 받은 주문의 결제를 막지 않는다 |

| 5 | 지표 | `order.rate.limit{operation=create\|payment, result=allowed\|rejected\|bypassed}`. `bypassed`는 Redis 장애로 통과시킨 경우다. 회원 ID를 라벨로 쓰지 않는다 | 어느 요청이 막혔는지와 장애 통과를 구분한다 |

### 완료 기준

- 실제 Redis에서 회원당 6번째 요청이 429 `ORDER_RATE_LIMITED`와 `Retry-After`를 받고, 창이 지나면 다시 허용된다. 주문 생성과 결제가 따로 세어진다. 다른 회원은 영향을 받지 않는다.
- 거절된 요청은 요청 키를 기록하지 않고 수량을 바꾸지 않는다. 같은 키로 창이 지난 뒤 다시 보내면 정상 처리된다.
- API 인스턴스 두 개가 하나의 카운터를 공유한다(합산 제한).
- 조회 GET은 제한되지 않는다. 400 입력 오류는 횟수에 들어가지 않는다.
- Redis 장애(명령 실패) 시 주문이 통과하고 `bypassed`가 늘어난다. 인증 자체가 Redis에 의존하는 한계는 2-1 #8대로 기록한다.
- 설정으로 끄면 제한하지 않는다. 기준선 실행기가 끈 상태로 실행된다.
- 기존 `./gradlew clean build`와 Python 도구 테스트가 통과한다.

## 2-3 확정 정책

2026-11-23 사용자와 선택지로 확정했다. 2-1 #2~#4(대상 `GET /api/v1/sales/{id}`, 저장 값만 캐시하고 상태는 읽을 때 계산, TTL 60초, 수정·중단·재개·삭제는 커밋 후 삭제, 장애 시 DB 조회)를 그대로 따른다.

### 출발점이 된 사실

- `SaleService.get`은 상태 계산에 `store.now()`(MySQL `NOW()`)를 쓴다. 캐시에 적중해도 DB 시각을 읽으면 커넥션을 쓰므로 2-1의 캐시 목적이 사라진다.
- `Sale.statusAt`은 확정 수량이 총수량과 같으면 `SOLD_OUT`이다. 확정 수량은 결제 확정마다 바뀐다. 2-1의 "응답에 잔여 수량이 없어 재고 불일치가 없다"는 판단은 `SOLD_OUT` 표시를 놓쳤다. 주문 판정은 MySQL이 하므로 초과 판매와는 무관하다.
- 캐시 미적중 중에 수정이 커밋되면 커밋 후 삭제 뒤 옛 값이 다시 채워질 수 있다. 2-1 #3에서 허용한 TTL 이내 지연에 포함한다.

| # | 항목 | 확정 내용 | 이유 |
|---|---|---|---|
| 1 | 조회 시각 | 상세 조회(`GET /api/v1/sales/{id}`)의 상태는 캐시 적중·미적중 모두 앱 시계(UTC)로 계산한다. 주문 접수 판정은 계속 MySQL 잠금 후 시각을 쓴다. 목록·관리자 응답은 바꾸지 않는다 | DB를 타지 않아야 캐시가 커넥션을 아낀다. 같은 요청의 두 경로가 같은 시계를 써야 결과가 일관된다. 표시 상태와 주문 판정은 시작·종료 경계에서 시계 차이만큼 다를 수 있다(로컬은 ms 수준). 주문 결과는 DB 판정을 따른다 |

## 2-2 확정 정책

2026-11-23 사용자와 확정했다. 2-2는 Redis 연결·설정·관측만 다루고 업무 기능을 Redis에 새로 의존시키지 않는다.

### 출발점이 된 사실

- 1-4의 로그인 실패 제한은 이미 `limited-sale:login-failure:{해시}`를 쓴다. 2-1 #9의 `ls:` 접두사와 달랐다. 세션은 Spring Session 기본 `spring:session`이었다.
- Redis 명령·연결 타임아웃이 설정되지 않아 Lettuce 기본 60초가 적용됐다. Redis가 응답하지 않으면 인증 요청이 최대 60초 동안 Tomcat 스레드를 붙잡는다.
- Compose Redis에 `maxmemory`가 없고, 이미지 기본 RDB 스냅샷만 있으며 명시적 볼륨이 없다.
- Prometheus는 판매 앱만 수집하고 Redis exporter가 없다.

| # | 항목 | 확정 내용 | 이유 |
|---|---|---|---|

### 완료 기준

- 위 설정이 Compose·격리 실험 환경·앱 설정에 적용되고, 세션 키가 `limited-sale:session` 아래에 생긴다.
- Redis 재시작 후 앱이 자동으로 다시 연결되고 health가 복구된다.
- Redis를 멈추면 지표(`redis_up`, 503 건수)에서 장애가 보이고, 인증 요청이 60초가 아니라 타임아웃 근처에서 503으로 끝난다.
- 기존 `./gradlew clean build`와 Python 도구 테스트가 통과한다.

### 2-2 구현과 검증

- 설정: `application.yml`의 `spring.data.redis.timeout: 2s`, `spring.data.redis.connect-timeout: 2s`, `spring.session.data.redis.namespace: limited-sale:session`. Compose Redis와 `tools/order-regression/isolated.py`의 Redis에 `--maxmemory 256mb --maxmemory-policy noeviction`. Compose `monitoring` 프로필에 `oliver006/redis_exporter:v1.98.0`(127.0.0.1:9121)과 Prometheus `redis` job. 대시보드에 Redis 행과 패널 4개를 추가했고 기존 패널은 바꾸지 않았다.
- Lettuce 지표는 Spring Boot 4.1.2의 `LettuceObservationAutoConfiguration`이 자동으로 내며 새 코드는 없다. 이름은 `lettuce_seconds_*`, 라벨은 `db_operation`·`db_system`·`error`·`net_sock_peer_addr`·`net_sock_peer_port`·`net_transport`다. 히스토그램 버킷은 켜지 않아 대시보드는 평균과 최대만 보인다.
- 테스트: `RedisConnectionIntegrationTest` 5개. 실제 `application.yml`을 덮어쓰지 않고 로드해 세션·로그인 실패 키가 `limited-sale:` 아래에만 생김, 바인딩된 타임아웃 2초, Redis pause 중 인증 요청이 약 2초(실측 2,008~2,020ms) 뒤 503, Redis stop/start 후 앱 재시작 없이 health UP과 새 로그인 성공, Lettuce 지표 라벨에 회원·세션 값이 없음을 확인한다. 워커가 `application.yml`을 이전 상태로 되돌리면 설정 관련 4개가 실패함을 확인했다.
- 워커 실측: Compose Redis `maxmemory` 268435456·`noeviction`, Prometheus `redis` 대상 up, `redis_up` 1. 앱 실행 중 Redis를 멈추면 `redis_up` 0, health DOWN, CSRF 조회 503(2,238ms), 다시 켜면 복구.
- 주 에이전트 독립 검증: diff 리뷰, `./gradlew clean build` 직접 실행(판매 앱 단위 97·통합 138, Mock PG 11·15, Python 77, 실패·오류·건너뜀 0), `docker compose --profile monitoring config` 유효, 대시보드 JSON의 Redis 패널·질의 확인, `git diff --check` 통과. 저장소에 `spring:session`을 가정한 코드가 남지 않았음을 확인했다.
- 한계: redis_exporter는 앱→Redis 경로만 끊긴 경우를 보지 못한다. Redis 중단 중 연결 실패는 `lettuce_seconds`의 `error` 라벨에 나타나지 않았다. 장애 감지는 `redis_up`과 503 건수에 의존한다. 타임아웃 2초는 2-5에서 확정한다. 격리 실험 전체는 새 Redis 인자로 다시 돌리지 않았고 단독 `docker run`으로 인자 적용만 확인했다.

- 처리량은 5% 높고 지연·JVM CPU는 낮다. 그러나 기준 run-1(277 req/s)이 다른 두 실행(311·313)보다 느렸고, 1-11의 범위(286~302)와도 겹친다. 반복 3회의 같은 컴퓨터 측정이므로 Java 25·Boot 4의 성능 개선으로 결론 내리지 않는다.
- 검증 근거: 워커가 `./gradlew clean build`(판매 앱 단위 97·통합 133, Mock PG 11·15, 실패·건너뜀 0)와 Python 도구 테스트 77개 통과를 보고했다. 주 에이전트가 실행별 JSON의 `status`, 검사 17개, 위반 수, 인스턴스 분배(약 5,000/5,000), 커밋·JAR 해시를 직접 확인했고, 결과 파일에 세션·비밀번호·API 키가 없고 `raw/`가 Git에서 제외되는지 확인했다. 도구는 Boot 4에서 지표 이름이 깨지지 않아 수정하지 않았다.

## 검증 기준

조회 캐시 효과와 요청 제한 효과를 분리해 측정한다. 요청을 많이 거절한 결과를 주문 처리량 향상으로 설명하지 않는다. 동일 조건에서 지연·DB 부하·실제 주문 처리량·거절률을 비교한다. Redis 장애·재시작·키 만료 후에도 재고·구매 한도·주문·결제의 규칙을 유지하는지 DB 기록과 대조한다.
