## 2-1 확정 정책

### 출발점이 된 사실

- 1-11의 병목은 판매 이벤트 행 하나의 `SELECT ... FOR UPDATE` 직렬화다. 커넥션 대기는 그 결과다([1-11 병목 분석](01-11-baseline-load-test.md#병목-분석)). 조회 캐시도 요청 제한도 이 잠금을 없애지 않는다.
- 1-11은 조회 API에 부하를 주지 않았다. 캐시 효과는 새 시나리오로만 보일 수 있다.
- 판매 이벤트 응답에는 잔여 수량이 없다. 상태는 `SaleService`가 조회 시각으로 계산한다(`statusAt(now)`). 2-3에서 바로잡음: 상태 중 `SOLD_OUT`은 확정 수량으로 정해지고, 조회 시각은 MySQL `NOW()`에서 읽는다(아래 "2-3 확정 정책").
- 1-11 기준선은 Java 21·Spring Boot 3.5.16에서 측정했다. 지금 코드는 Java 25·Spring Boot 4.1.2다.

### 목적과 측정 지표

| 기능 | 목적 | 측정 지표 | 주장하지 않는 것 |
|---|---|---|---|
| 조회 캐시 | 오픈 직전 판매 이벤트 상세 조회가 DB 커넥션을 쓰지 않게 해 주문 경로의 커넥션 경쟁을 줄인다 | 조회와 주문을 섞은 부하에서 조회 지연, 캐시 적중률, Hikari 커넥션 대기, 주문 생성 지연 | 주문 처리량 상한 개선(이벤트 행 잠금이 정한다) |
| 분산 요청 제한 | 회원 한 명의 과도한 주문·결제 요청을 막아 잠금 대기열과 커넥션 풀을 보호한다 | 허용·거절 수, 거절률, 남용 사용자가 섞인 부하에서 정상 사용자의 주문 지연과 확정 수 | 거절이 늘어 짧아진 응답 시간을 주문 성능 향상으로 해석 |

### 결정과 이유

| # | 항목 | 확정 내용 | 이유 |
|---|---|---|---|
| 1 | 기준선 재측정 | 2-2 착수 전에 별도 작업으로 1-11 기준 시나리오를 Java 25·Spring Boot 4.1.2에서 다시 측정한다 | 2-6 비교의 기준이다. Redis 변경과 섞지 않아야 차이의 원인을 구분할 수 있다 |
| 2 | 캐시 대상 | `GET /api/v1/sales/{id}`만 | 오픈 시점에 몰리는 조회다. 목록은 페이지·필터 조합마다 키가 생기고 무효화가 복잡하다. 제품 조회는 몰리지 않는다 |
| 3 | 캐시 내용·TTL·무효화 | 판매 이벤트의 저장 값만 캐시하고 상태는 읽을 때 현재 시각으로 계산한다. TTL 60초(설정 가능). 수정·중단·재개·삭제는 커밋 후 키를 삭제한다 | 상태를 캐시하면 시작·종료 경계가 TTL만큼 늦어진다. 커밋 전 삭제는 다른 요청이 옛 값을 다시 채울 수 있다. 커밋 후 삭제가 실패하면 최대 TTL 동안 옛 값이 보일 수 있으나, 주문 판정은 MySQL이 하므로 정합성은 깨지지 않는다. 이 지연은 허용한다 |
| 4 | 캐시 장애 | Redis 실패·타임아웃이면 DB에서 조회해 응답한다. 짧은 명령 타임아웃을 두고 실패 지표를 남긴다 | 캐시는 최적화다. 캐시 장애가 조회 실패가 되면 안 된다 |
| 5 | 요청 제한 대상·단위 | `POST /api/v1/orders`와 `POST /api/v1/orders/{id}/payment`에 인증된 회원 단위로 적용한다. 조회 GET은 제외한다. 이벤트 전체 제한은 이번 범위에서 뺀다 | 목적이 남용 방지다. 전역 제한은 정상 요청도 거절해 "제한이 없으면 1,000건 확정" 기준과 충돌하기 쉽다 |
| 6 | 알고리즘·임계값 | Lua 스크립트로 원자적으로 증가·만료하는 고정 창. 기본 회원당 1초 5회, 설정으로 변경. 2-6 결과로 기본값을 1초 1회로 낮췄다 | 보여줄 핵심은 여러 인스턴스가 한 카운터를 원자적으로 공유하는 것이다. 창 경계의 순간 2배 허용은 알려진 한계로 기록한다 |
| 7 | 거절 응답 | HTTP 429, 코드 `ORDER_RATE_LIMITED`, `Retry-After` 헤더. 요청 키를 기록하지 않고 수량을 차감하지 않는다. 같은 요청 키의 재시도도 횟수에 포함한다 | 거절된 요청은 주문이 아니므로 같은 키로 다시 보내면 정상 처리된다. 재시도를 빼면 제한을 우회할 수 있다 |
| 8 | 요청 제한 장애 | Redis 실패·타임아웃이면 제한 없이 통과시키고 지표를 남긴다 | 정합성은 MySQL이 지킨다. Redis가 완전히 중단되면 세션 인증이 먼저 실패해 주문할 수 없으므로 이 정책은 일시 지연·타임아웃에 적용된다. 인증 실패를 DB로 우회하지 않는 기존 정책은 유지한다 |
| 9 | 키·인스턴스 | 기존 Redis 인스턴스 하나에 접두사로 구분한다. 2-2에서 접두사를 `limited-sale:`로 모으기로 수정했다(아래 "2-2 확정 정책"). 캐시 `limited-sale:cache:sale:v1:{id}`(2-3에서 버전 추가), 요청 제한 `limited-sale:rate-limit:order:{create|payment}:{memberId}`(2-4에서 첫 요청 기준 창으로 바꿔 창 번호를 뺐다), 세션 `limited-sale:session`, 기존 로그인 실패 `limited-sale:login-failure:`. 모든 캐시·제한 키에 TTL을 둔다. `maxmemory-policy noeviction` | 메모리가 부족할 때 세션이 밀려나 삭제되는 일을 막는다. 인스턴스 분리는 장애 격리가 낫지만 로컬 포트폴리오에는 과하다 |
| 10 | 관측 | 앱의 Redis 명령 지연·실패 지표, 캐시 적중·미적중·실패 카운터, 요청 제한 허용·거절·통과(장애) 카운터, `redis_exporter`로 메모리·연결 수 | 캐시·제한의 효과와 장애를 지표로 구분해야 한다. 회원 ID는 지표 라벨로 쓰지 않는다 |

### 후속 소단계에 미친 영향

- 2-2에서 #9의 접두사를 `limited-sale:`로 수정했다.

- 2-2 전에 기준선 재측정을 별도 작업으로 한다.
- 2-3은 #2~#4, 2-4는 #5~#8, 2-2는 #9~#10의 연결·관측 부분을 따른다.
- 2-6에는 조회·주문 혼합 시나리오와 남용 사용자 혼합 시나리오를 추가한다. 세부 부하 조건은 2-6에서 정한다.

## 2-7 확정 정책

2026-11-24 사용자와 선택지로 확정했다. 2-6에서 처리량 상한은 이벤트 행 잠금이었다. 기준 시나리오에서는 요청 1만 건 중 9천 건이 품절 거절인데, 이 거절도 `SELECT FOR UPDATE` 대기열을 거친 뒤에 판정된다. 2-7은 품절이 확실한 요청을 잠금 전에 돌려보낸다. 재고의 최종 판단은 계속 MySQL이 한다.

| # | 항목 | 확정 내용 | 이유 |
|---|---|---|---|
| 1 | Redis 값 | 판매 이벤트별 품절 표시 키를 둔다(값 하나, TTL 5초). 점유로 구매 가능 수량(총수량 − 점유 − 확정)이 0이 된 트랜잭션과, MySQL이 `SALE_SOLD_OUT`으로 판정한 트랜잭션이 커밋 뒤에 표시를 둔다. 결제 실패·종료로 점유가 해제된 트랜잭션은 커밋 뒤에 표시를 지운다. 커밋 전이나 롤백 때는 Redis를 바꾸지 않는다. 수량 카운터와 MySQL 잠금 없는 조회는 채택하지 않는다 | 차감·보상이 없어 어긋남이 생겨도 TTL로 저절로 낫는다. 이 시나리오에서는 재고가 0이 된 뒤의 요청만 거르면 되므로 카운터와 효과가 거의 같다 |
| 2 | 판정 위치와 순서 | 기존 요청 키 조회를 항상 먼저 한다. 기존 키면 지금처럼 재생한다. 새 키이고 표시가 있으면 판매 행을 잠그지 않고 `SALE_SOLD_OUT` 거절 결과를 `order_request_results`에 저장해 같은 409를 돌려준다. 표시가 없으면 지금 경로로 MySQL이 판정한다. Redis 조회는 판매 행 잠금을 잡은 상태에서 하지 않는다 | 이미 성공한 키를 다시 보낸 요청을 품절로 거절하지 않고, 업무 거절은 키별로 고정한다는 1단계 계약을 지킨다 |
| 3 | 판정 순서 차이 | 표시가 있으면 중단·기간 외·구매 한도보다 품절을 먼저 응답한다. 기간 외·중단이면서 품절인 이벤트나 한도를 넘은 회원도 `SALE_SOLD_OUT`을 받을 수 있다. 이 차이는 위키와 계약 문서에 적는다 | 어느 경우든 구매할 수 없다는 결과는 같다. 정확한 사유를 위해 잠금을 다시 잡으면 이 단계의 목적이 사라진다 |
| 4 | TTL | 5초(설정 `limited-sale.sale.sold-out-gate.ttl`) | 표시를 지우지 못하면 해제된 재고가 최대 5초 동안 안 팔린다(거짓 품절). 점유 해제는 결제 실패와 5분 만료 때만 생겨 드물다. 품절이 계속되는 동안에는 5초마다 요청 하나가 MySQL까지 가서 표시를 다시 둔다 |
| 5 | 스위치 | `limited-sale.sale.sold-out-gate.enabled`(기본 `true`). 끄면 Redis를 호출하지 않고 1단계 경로만 쓴다. 실험 도구가 실행마다 지정하고 기록한다 | 2-6의 캐시 스위치와 같은 이유다 |
| 6 | 장애 | Redis 조회가 실패하거나 타임아웃이면 표시가 없는 것으로 보고 MySQL로 판정한다. 표시를 두거나 지우다 실패해도 요청은 성공하고, 로그와 지표를 남긴다. 거짓 품절은 TTL이 막는다 | 사전 판정은 최적화다. Redis 장애가 주문 거절이 되면 안 된다. 이 방향의 어긋남은 초과 판매를 만들지 않는다 |

### 2-6 실험 결과와 검증

- 캐시 스위치: `limited-sale.sale.cache.enabled=false`면 `RedisSaleCache` 대신 `DisabledSaleCache`(같은 패키지, 조회는 항상 미적중, 저장·무효화는 하지 않음)가 등록된다. `SaleCacheDisabledIntegrationTest` 4개가 Redis `INFO commandstats` 변화 없음과 키·지표 부재를 확인한다.
- 실험 도구: `tools/order-regression/run_comparison.py`(+ `comparison.py`, `tests/load/comparison-order.js`). 조회는 로그인 사용자의 쿠키를 붙여 보낸다. 쿠키가 있으면 공개 조회도 세션용 Redis 호출(`PING`·세션 조회)을 하므로 `a-off`는 "Redis 호출 없음"이 아니라 "판매 이벤트 캐시 없음"이다. 남용 사용자는 같은 k6 실행의 별도 시나리오로, 같은 회원의 VU들이 세션을 공유한다. 기다리지 않고 새 요청 키로 주문 생성을 반복하고, 429의 `Retry-After`는 무시하며, 201이면 결제를 한 번 한다. 남용 시도의 검증기 입력은 서버 `order_request_results`로 만든다. 조건은 실행마다 한도를 명시 전달하고 환경에 기록한다.

### 완료 기준

- 실제 Redis에서 회원당 6번째 요청이 429 `ORDER_RATE_LIMITED`와 `Retry-After`를 받고, 창이 지나면 다시 허용된다. 주문 생성과 결제가 따로 세어진다. 다른 회원은 영향을 받지 않는다.
- 거절된 요청은 요청 키를 기록하지 않고 수량을 바꾸지 않는다. 같은 키로 창이 지난 뒤 다시 보내면 정상 처리된다.
- API 인스턴스 두 개가 하나의 카운터를 공유한다(합산 제한).
- 조회 GET은 제한되지 않는다. 400 입력 오류는 횟수에 들어가지 않는다.
- Redis 장애(명령 실패) 시 주문이 통과하고 `bypassed`가 늘어난다. 인증 자체가 Redis에 의존하는 한계는 2-1 #8대로 기록한다.
- 설정으로 끄면 제한하지 않는다. 기준선 실행기가 끈 상태로 실행된다.
- 기존 `./gradlew clean build`와 Python 도구 테스트가 통과한다.

### 2-4 구현과 검증

- 구조: 포트 `order.domain.OrderRateLimit`(`hit`이 `Allowed`·`Rejected(retryAfter)`·`Unavailable`을 반환), 구현 `order.infrastructure.redis.RedisOrderRateLimit`, 정책 적용 `order.application.OrderRateLimiter`. 검사는 `OrderService.create`와 `OrderPaymentService.pay`의 첫 줄이다. 거절은 `OrderResult.Kind.RATE_LIMITED`로 돌아가 컨트롤러가 429와 `Retry-After`를 만든다.
- Lua: `INCR` → `PTTL` → 첫 요청이거나 만료가 없으면 `PEXPIRE(창)` → `{횟수, 남은 ms}` 반환. 거절 판정(횟수 > 허용)은 Java에서 한다.
- 설정: `limited-sale.order.rate-limit.enabled`(기본 true), `limited-sale.order.rate-limit.max-requests`(기본 5), `limited-sale.order.rate-limit.window`(기본 1s). 허용 횟수·창의 프로퍼티 이름은 워커가 정했다.
- 실험 도구: `tools/order-regression`의 `Isolated`가 기본으로 판매 JVM을 `LIMITED_SALE_ORDER_RATE_LIMIT_ENABLED=false`로 띄우고 `resources.json`·기준선 환경 기록에 남긴다. 같은 클래스를 쓰는 모든 실행기에 적용된다. 셸 환경변수로는 바꿀 수 없고 2-6에서 `Isolated(order_rate_limit=True)`로 켠다. 워커가 제한을 끈 기준선 스모크(사용자 200·재고 50·VU 50)가 통과함을 확인했다.
- 테스트: `OrderRateLimitIntegrationTest` 10개(실제 MySQL·Redis·Mock PG, 판매 앱 2개). 6번째 429와 `Retry-After`, 같은 키 재시도도 계산, 거절 후 요청 기록·주문·점유 수량 불변, 창이 지난 뒤 같은 키로 201, 결제의 별도 카운터, 다른 회원 무영향, 두 인스턴스 합산, 동시 20건 중 정확히 201 5건·429 15건·주문 5건, GET·400은 세지 않음, Redis 명령 실패(WRONGTYPE 키) 시 통과와 `bypassed`, 비활성 시 키 없음, 만료 없는 키 복구, 지표 라벨. 단위 테스트로 거절 시 트랜잭션·게이트웨이 무호출, `Retry-After` 올림 경계, 설정 검증을 확인한다. 한 회원이 연속 요청을 보내는 기존 통합 테스트 5개는 제한을 끄고 실행한다.

- 한계: redis_exporter는 앱→Redis 경로만 끊긴 경우를 보지 못한다. Redis 중단 중 연결 실패는 `lettuce_seconds`의 `error` 라벨에 나타나지 않았다. 장애 감지는 `redis_up`과 503 건수에 의존한다. 타임아웃 2초는 2-5에서 확정한다. 격리 실험 전체는 새 Redis 인자로 다시 돌리지 않았고 단독 `docker run`으로 인자 적용만 확인했다.

## 검증 기준

조회 캐시 효과와 요청 제한 효과를 분리해 측정한다. 요청을 많이 거절한 결과를 주문 처리량 향상으로 설명하지 않는다. 동일 조건에서 지연·DB 부하·실제 주문 처리량·거절률을 비교한다. Redis 장애·재시작·키 만료 후에도 재고·구매 한도·주문·결제의 규칙을 유지하는지 DB 기록과 대조한다.
