# 1-7-5 주문·결제·복구 통합 정합성 및 장애 회귀

상태: 도구 구현, 독립 리뷰, 전체 실험, 전체 build, 위키 갱신과 검증 완료.

[작업 분할](01-7-order-payment.md)과 [자동 복구](01-7-4-order-recovery-and-leases.md), [결제 계약](01-7-3-order-payment-integration.md)을 따른다.

## 확정 범위

- 주문 생성·결제·복구를 통합해 요청 결과, 주문, 결제, 이벤트·사용자 수량, 주문별 점유, PG 결과를 대조한다.
- 입력 프로필은 사용자 100명/재고 30개/동시 전송 상한 100개와 사용자 1,000명/재고 300개/동시 전송 상한 1,000개다. 실제 고유 사용자 세션을 준비하고 동시 출발 지점에서 요청을 보낸다. 실제 도달·누락·예외도 집계하며 설정한 동시 수를 서버에서 관측한 동시 처리량으로 표현하지 않는다.
- 가입·로그인은 실험 전 준비한다. 사용자 세션 하나로 서로 다른 사용자를 흉내 내지 않는다. 요청 키·입력·시나리오 배정은 기록해 재현한다.
- 일반 정합성·실제 강제 종료 시나리오는 각 3회 반복한다. PG 실제 11분 중단은 1회다.
- 장애 해제·재기동 후 최종 수렴 기한은 기본 120초다. 초과 주문을 제외하거나 기한을 자동 연장해 통과시키지 않는다. 11분 장애 시간에는 수렴을 요구하지 않고 점유 유지·운영 경고·재시도 간격을 검사한다.
- 실험 도구는 전용 DB·Redis·PG와 전용 판매 서버 JVM을 만든다. 소유한 PID·포트·컨테이너만 종료·정리한다. 개발 DB 볼륨과 사용자가 실행 중인 서버는 건드리지 않는다.
- 장기·프로세스 강제 종료·대규모 실험은 명시적 별도 실행 명령으로 분리하고, 일반 build에는 빠른 회귀·검증기 테스트를 포함한다.
- k6 기준 처리량·지연, Prometheus/Grafana와 운영 다중 인스턴스 실행 구성은 기존 1-9~1-11 범위다. 이번 전용 다중 프로세스 실행은 복구 정합성 실험용이다.

사용자는 정합성 집중, 실제 강제 종료·11분 중단, 두 사용자 규모, 각각의 동시 전송, 일반 3회·장기 1회와 120초 수렴 기한을 선택했다. 로컬 부하 생성기와 서버가 CPU·메모리를 공유한다는 한계를 결과에 남긴다.

## 시나리오와 기대 결과

| 시나리오 | 기준 입력·예상 결과 |
|---|---|
| 초과 수요·PG 전체 성공 | 고유 사용자당 수량 1·한도 1. 100/30이면 30건, 1,000/300이면 300건 구매 확정. 나머지 정상 요청은 재고 부족으로 거절. 시스템 오류를 재고 거절로 합산하지 않음 |
| 같은 요청 키 재시도 | 같은 사용자·키·입력 재전송은 같은 주문 또는 보관한 거절. 중복 주문·PG 결제·수량 반영 없음. 다른 입력은 충돌 |
| 같은 사용자·다른 키 경쟁 | 사용자별 복수 키로 경쟁해도 점유+확정은 한도 1 이하. 새 주문 성공과 한도 거절을 구분 |
| 재고 미만 정상 수요 | 100/30 프로필은 20명, 1,000/300 프로필은 200명 요청. 요청 전부 확정하고 나머지 재고 유지. 모두 거절돼 수량만 맞는 경우 실패 |
| 결제 실패·수량 재사용 | 고정한 일부 주문은 DECLINE으로 종료·점유 해제. 다른 사용자·새 키가 해제 수량을 구매할 수 있어야 함. 최종 기대 수량을 실행 전에 고정 |
| 지연·성공 응답 유실 혼합 | PG 시나리오를 주문별로 고정. 미확인 동안 점유 유지, 자동 복구 후 PG 최종 결과와 주문·수량 일치 |
| 판매 JVM 강제 종료 | 임대 커밋 직후, PG 성공 저장 뒤 판매 응답 확인 전, 판매 결제 저장 뒤 주문 마무리 전의 경계를 관찰한 뒤 전용 JVM 강제 종료. 생존 서버 또는 재시작 서버가 임대 만료 후 기한 내 수렴. 각 경계를 3회 실행 |
| PG 11분 중단 | 결제 요청 이력이 있는 미완료 주문을 둔 뒤 PG를 실제 중단. DB 시각·기간·임대·예약을 조작하지 않음. 5분 이후 운영 확인, 이후 반복 경고, 점유 유지와 재확인을 관찰하고 PG 재시작 뒤 120초 내 최종 정리 |

재시도·한도·혼합 결제 시나리오의 주문별 입력과 기대 합계는 도구의 실행 명세에 고정한다. 과부하에서 발생한 500·타임아웃·미전송도 원본 결과에 남긴다. 장애 시나리오에서 기대한 통신 오류와 정상 전체 성공 시나리오의 시스템 오류는 별도로 판정한다.

## 구현 계획

1. 원본 요청 결과와 DB 대조 결과를 받는 재실행 가능한 검증기를 만든다. 주문 수·수량·금액·PG 키의 유일성과 상태별 불변식을 검사하고 의도적으로 틀린 자료에서 실패하는 테스트를 먼저 만든다.
2. 격리 자원과 실제 판매 JVM 2개·별도 PG를 시작하는 실험 하네스를 구현한다. 고유 계정·세션·CSRF를 준비하고 두 판매 서버로 요청을 분산하며 각 서버가 요청을 처리한 근거를 남긴다. 사용자 준비는 주문·이벤트 생성보다 먼저 끝내 만료 시간을 소모하지 않게 한다.
3. 두 입력 규모·3회 반복·동시 출발을 지원하는 일반 시나리오를 실행한다. 실험별 새 이벤트·요청 키·명세를 사용하고 결과를 섞지 않는다. 입력 사용자 수, 요청 수, 실제 전송 수와 상태별 결과를 구분한다.
4. 강제 종료 경계는 DB 상태·PG 저장·테스트 전용 제어 가능한 HTTP 중계 등 외부 관측으로 확인하고 PID를 강제 종료한다. 단순 sleep 후 종료하고 원하는 경계에 도달했다고 가정하지 않는다. 필요한 제어는 실험 도구에 한정하며 일반 서비스에 공개 장애 API를 추가하지 않는다.
5. 11분 PG 중단을 실제 벽시계로 실행한다. 최초·반복 경고 시각, DB requiresReview·점유·재시도 흔적과 PG 재기동 결과를 수집한다. 중단 중 로그만으로 정합성을 판정하지 않는다.
6. 판매 앱은 PG DB를 읽지 않는 경계를 유지한다. 별도 검증 도구만 판매 DB와 PG DB를 읽어 결과를 대조한다. 수행 중 표본과 최종 정지·수렴 시점의 스냅샷을 구분해 서로 다른 시점의 값으로 허위 불일치를 만들지 않는다.
7. 발견한 코드 문제는 재현 테스트 후 수정하고, 전체 clean build와 독립 검증을 통과한 뒤 위키·도식·실험 보고서를 갱신한다. 정책 변경이 필요하면 사용자와 협의한다.

## 불변식과 보고서

- 이벤트 점유·확정 수량은 음수가 아니며 합계는 총수량 이하. 이벤트 수량은 주문별 점유의 RESERVED·CONFIRMED 합계와 일치.
- 사용자별 점유·확정 수량은 주문별 기록 합계와 일치하고 이벤트별 구매 한도 이하.
- 확정 주문의 점유는 CONFIRMED, 실패·만료 주문은 RELEASED. 미확인 주문의 점유는 유지. 결제 최종 결과가 저장됐지만 주문 정리가 남은 중간 상태와 최종 불일치를 구분.
- 주문·판매 결제·PG 금액은 고정 단가×수량과 일치하며 주문별 PG 키·결제 기록은 하나. PG 성공과 주문 확정, FAILED/CLOSED와 실패/만료를 최종 대조.
- 보관된 요청 결과·주문·전송 결과를 함께 대조하고, 정해진 모든 대상의 최종 상태를 집계한다. 오류·미완료·전송 누락을 성공 비율 분모에서 빼지 않는다.
- 보고서에 커밋·dirty 상태·Java/DB 버전·OS·CPU·메모리·실행 프로세스 수·설정·입력·반복 회차·벽시계·예상/실제 결과·오류·수렴 시간과 제한을 기록한다. 세션·비밀번호·인증값은 산출물에서 제외한다.
- 원본 산출물 경로와 실행 명령을 남기고 실패 시 명령은 비정상 종료한다. 개발 데이터에 대한 초기화 명령은 포함하지 않는다.

## 초기 워커 진행 기록 (아래 실행 기록으로 대체)

- 교차 데이터 검증기 초안과 손상된 가상 자료에 대한 빠른 회귀 검사를 추가했다. 검증기의 입력은 아직 수동 JSON이며 실제 DB 수집기나 실험 결과가 아니다. 제한과 실행 방법은 `tools/order-regression/README.md`에 명시했다.
- 격리 실험 하네스, 실제 사용자·동시 요청, 강제 종료, 11분 PG 중단은 아직 수행하지 않았다. 위의 실험 및 구현 체크 항목을 완료로 처리하지 않는다.

## 실행 도구와 중간 근거

- `tools/order-regression/`에 전용 자원 수명주기, 고유 사용자 인증, 비동기 출발 장벽, HTTP 원본·두 DB 대조, PG 응답 제어 중계, 실제 프로세스 종료·장기 중단 실행기와 독립 감사 도구를 추가했다. 빠른 Python 검사는 Gradle `check`에 포함했다. 외부 PG DB 조회는 실험 도구에서만 수행한다.
- 100명 프로필 일반 시나리오 18회는 초기 `/tmp/175-audit-matrix-100.json` 검사에서 모두 통과했으며, 혼합 장애는 PG 통신 중단 여부를 추가로 기록하며 재실행 중이다. 초과 수요는 회차마다 확정 30·재고 부족 70, 미달 수요는 20건 모두 확정했다. 동일 사용자 경쟁은 확정 1·한도 거절 99, 거절 수량 재사용은 결제 실패 3건 후 다른 사용자가 3건을 확정했다. 혼합 장애의 중간 단일 SQL 표본에서는 지연·응답 유실 양쪽에 `PAYMENT_PENDING`과 `RESERVED`가 함께 남았다.
- 100명·재고 30 환경에서 단일 대상 주문의 임대 커밋, PG 성공 응답 보류, 판매 결제 저장 후 주문 마무리 잠금 대기 경계를 각각 세 차례 관찰하고 소유 판매 JVM에 SIGKILL을 보냈다. `/tmp/175-forcekill-100-run2`의 9건은 모두 120초 안에 최종 상태에 도달했고 `python3 -B tools/order-regression/audit_forcekill.py /tmp/175-forcekill-100-run2`가 통과했다.
- PG를 실제 660.001초 중단했다. 주문은 요청 이력이 있는 `PAYMENT_PENDING`, 점유는 `RESERVED`, PG에는 성공이 저장된 상태에서 중단했다. 66개 DB 표본에서 점유가 유지됐고 만료 뒤 운영 확인 표시와 두 경고를 확인했다. PG 재기동 시작 뒤 7.994초에 주문이 확정됐으며 `/tmp/175-outage-run1`의 스냅샷과 경고·재시도 감사가 통과했다. 실제 장애 중 DB 시각·만료·임대·경고 예약을 변경하지 않았다.
- 기준 커밋은 `4140dcbbd1a17f3e9ddd5a98b4d155fdb64583f7`, 작업 트리는 dirty다. 실행은 Java 21.0.10, MySQL 8.4.7, Redis 7.4, macOS Darwin arm64, Apple M4 Pro 논리 CPU 14개와 메모리 48 GiB에서 수행했다. 일부 실행은 다른 격리 실험과 CPU·메모리를 공유했으며 성능 목표를 판정하지 않았다.
- 초기 실험 도구는 컨테이너 삭제 때 익명 볼륨 삭제 옵션을 빠뜨렸다. 이후 소유 컨테이너의 마운트 ID를 기록하고 익명 볼륨을 함께 제거하도록 수정했다. 초기 실행에서 남았을 수 있는 볼륨은 컨테이너와 정확히 대응시키지 못해 보존했다. 전체 볼륨 정리 명령은 실행하지 않았다.
- 1,000명 프로필의 강화 실행에서는 혼합 회차 2건이 실패했다. 하나는 비교 스냅샷 변화이며 당시 전후 스냅샷이 없어 차이를 복원하지 못했다. 다른 하나는 DB 요청 기록 시각이 이벤트 시작 전이어서 1,002건이 `SALE_OUTSIDE_PERIOD`로 거절됐다. 실패를 보존하고 DB 시각 관찰·PG 통신 관측·전후 스냅샷 기록을 추가해 재실행한다. 재실행 중 설정 API 503도 두 회차에 발생했으며 시뮬레이션 설정 요청과 중계 오류 기록을 보강해 원인을 확인한다. 조사 기록은 `/tmp/175-mixed-failure-investigation.md`다.

### 실패·무효 실행과 보완

- 첫 번째 전체 실행에서 강제 종료 `lease-1`이 `snapshot changed during quiescence check`로 실패해 나머지 8건이 실행되지 않았다. 앱은 판매 수량과 주문 상태를 한 트랜잭션으로 커밋하지만 수집기는 테이블을 별도 연결로 읽어 커밋 전후 값이 섞일 수 있었다. 당시 전후 스냅샷을 저장하지 않아 이 실패의 원인으로 확정하지는 못했다. 수집기가 판매 DB를 하나의 일관된 스냅샷으로 읽도록 고치고, 강제 종료·장기 중단 실행기가 불일치 시 전후 스냅샷을 남기도록 보강했다. 이후 실행에서 불일치는 발생하지 않았다.
- 주 에이전트 독립 리뷰에서 세 가지 결함을 재현하고 회귀 테스트와 함께 수정했다. 실험 JVM이 셸 환경 변수를 그대로 물려받아 `SPRING_DATASOURCE_URL`·`REDIS_HOST` 같은 값이 export되어 있으면 개발 DB·Redis로 연결될 수 있었다. 이제 허용 목록의 변수만 전달한다. `audit_outage.py`는 복구 수렴과 최종 스냅샷을 검사하지 않아 수렴에 실패한 결과도 통과시켰다. PG 연결이 실패하면 중계가 호출자 연결을 닫지 않아 즉시 실패할 호출이 타임아웃까지 대기했다. 당시 셸에는 해당 환경 변수가 없어 이전 실행 결과는 영향을 받지 않았다.
- 세 번째 전체 실행은 점심시간에 Mac이 유휴 잠자기에 들어가 무효로 처리하고 중단했다. 잠자기 중에는 단조시계가 멈추고 DB 시각은 흐른다. 그래서 임대가 30초인 강제 종료 회차가 20.51초 만에 수렴한 것으로 기록됐고, PG 중단은 벽시계 23분 동안 단조시계로 101초만 흘렀다. 잠자기 전에 끝난 일반 시나리오는 통과했지만 최종 근거로 쓰지 않았다.
- 이 사례를 막으려고 Sonnet 서브에이전트가 `clock_guard.py`를 구현했다. 각 실행기는 측정 구간의 벽시계·단조시계 차이를 `clock-guard.json`에 남기고 5초를 넘으면 실패한다. 감사 도구는 기록이 없거나 차이가 크면 통과시키지 않는다. 주 에이전트가 구현을 검토했고, 기준값을 바꾼 변형 2종을 테스트가 잡아내는지 확인했다. 실제 잠자기 상황에서 실패하는지는 실행해 보지 않았다.
