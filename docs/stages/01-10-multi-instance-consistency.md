# 1-10 여러 인스턴스 정합성

상태: 정책 확정·구현·실험·독립 검증·위키 갱신 완료. 사용자가 "1-9 부터 1-11까지도 마찬가지로 정책 협의들 너가 생각하는 추천안으로 확정하고 개발 및 테스트"하라고 지시해 주 에이전트 추천안으로 확정하고 구현을 시작했다.

[1단계 정책](01-mysql-order.md), [1-7-5 회귀 실험](01-7-5-order-payment-recovery-regression.md)을 따른다. 이 문서는 1-10의 새 합의를 우선한다.

## 범위

- 판매 앱 두 개 앞에 로드 밸런서를 두는 로컬 실행 구성을 만든다.
- 로드 밸런서를 거쳐 인스턴스 1개와 2개에서 같은 동시 주문 실험을 돌리고, DB 대조 쿼리로 수량 규칙을 검사한다.
- 1-7-5 도구는 판매 JVM 두 개에 클라이언트가 직접 나눠 보냈다. 1-10은 클라이언트가 인스턴스를 모르는 운영 형태를 검증한다.
- 1-9 관측 구성은 아직 머지 전이다. 1-10은 main 기준으로 진행하고, 1-9 머지 후 두 번째 인스턴스의 관리 포트를 맞춘다.

## 확정한 정책과 이유

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| 로드 밸런서 | Caddy 컨테이너(`caddy:2.11.2-alpine`). Compose `multi-instance` 프로필, `127.0.0.1:8000` | 설정 파일 하나로 끝나고 접근 로그에 처리한 인스턴스를 남길 수 있다. 작업 환경에서 이미지 레지스트리에 접속할 수 없어 로컬에 있는 Caddy를 골랐다. nginx와 역할은 같다 |
| 분산 방식 | 라운드 로빈, 고정 세션 없음 | 같은 사용자의 요청이 두 인스턴스를 오가야 Redis 세션·CSRF 공유가 실제로 검증된다 |
| 로컬 인스턴스 | 판매 앱 JAR 두 개를 `8080`, `8082`로 실행. Mock PG·MySQL·Redis는 공유 | 운영과 같은 공유 저장소 구조. 실행 방법은 README에 적는다 |
| 처리 인스턴스 확인 | Caddy 접근 로그의 upstream 주소로 인스턴스별 요청 수를 센다 | 응답에 내부 토폴로지를 노출하지 않는다 |
| 자동 복구 | 두 인스턴스 모두 복구 스케줄러를 돌린다 | 임대가 단일 처리자를 보장한다. 1-7-5에서 검증했다 |
| 실험 실행 | 격리 환경에 Caddy를 추가하고 `--instances 1` 또는 `2`로 같은 시나리오를 돌린다 | 인스턴스 수만 바꿔 비교한다 |
| 실험 시나리오 | 서로 다른 사용자 1,000명이 수량 1개씩 재고 300개에 동시 주문. 생성된 주문은 모두 결제. 같은 사용자의 동시 중복 요청 묶음 포함 | 초과 판매, 사용자 한도, 요청 키 중복을 함께 본다 |
| 대조 쿼리 | 위반 행만 돌려주는 SQL 파일. 빈 결과가 정합 | 실험 밖에서도 개발 DB에 그대로 돌릴 수 있다. 기존 스냅샷 검증기와 함께 쓴다 |
| 통과 기준 | 두 모드 모두 확정 300건, 잔여 0, 대조 위반 0. 2개 모드는 두 인스턴스가 각각 주문 요청을 처리 | 1단계 완료 기준 |

## 검증 기준

- 1개 모드와 2개 모드에서 초과 판매·중복 주문·수량 불일치가 없다.
- 2개 모드에서 두 인스턴스가 모두 주문 생성 요청을 처리했다는 것을 Caddy 접근 로그로 보인다. 분배 비율을 기록한다.
- 로그인한 세션으로 다른 인스턴스에서 주문·결제가 된다.
- 대조 SQL이 정합 DB에서 빈 결과를, 일부러 수량을 틀어 놓은 DB에서 위반 행을 돌려준다.
- 실험은 소유한 자원만 만들고 정리한다.

## 구현 중 정한 세부 사항

- 10번째 사용자마다(100명) 같은 키 재요청 2개와 다른 키 요청 2개를 더해 시도는 모두 1,400개다. 출발 순서는 기록한 시드로 섞는다. 섞지 않으면 항상 첫 키가 이겨 다른 키 경쟁이 검증되지 않았다.
- 어느 키가 이기는지는 실행마다 달라 생성·거절 건수는 범위로 검사한다. 확정 300건은 정확히 검사한다. 이를 위해 `verify.py`가 기대값으로 정수 또는 `[최소, 최대]` 범위를 받는다.
- HTTP 증거 위반, 로드 밸런서 로그의 401·403, 요청 오류, 로그의 주문 생성 수와 시도 수 불일치도 실패로 처리한다.
- 대조 SQL은 결제 중 주문을 상태 짝 검사에서 뺀다. `OrderPaymentTransaction.finish`에서 결제 성공이 주문 확정보다 먼저 보일 수 있기 때문이다.
- `mysql` CLI 세션의 문자셋이 latin1이라 비교 컬럼을 utf8mb4로 변환한다. 첫 실제 실행에서 이 문제로 실패했고 수정 후 두 모드를 다시 돌렸다.

## 검증 결과

Sonnet high 워커가 구현하고 실험을 실행했다. 주 에이전트가 diff·실험 산출물을 확인하고 빌드를 다시 실행했다.

| 항목 | 인스턴스 1개 | 인스턴스 2개 |
|---|---|---|
| 결과 | 통과 | 통과 |
| 확정 / 잔여 | 300 / 0 | 300 / 0 |
| 검증기·HTTP 증거·대조 SQL 위반 | 0 / 0 / 0 | 0 / 0 / 0 |
| 주문 생성 요청 분배 | 1,400 | 700 / 700 |
| 결제 요청 분배 | 300 | 150 / 150 |
| 401·403, 요청 오류 | 0, 0 | 0, 0 |

- 사용자마다 로드 밸런서로 한 번 로그인하고 세션을 유지했다. 라운드 로빈이라 같은 세션의 요청이 두 인스턴스를 오갔고 인증 실패가 없었다. 한 사용자를 두 인스턴스에 걸쳐 따로 추적하지는 않았다.
- 소요 시간은 기록만 한다. 클라이언트와 서버가 같은 컴퓨터를 쓰므로 성능 비교 근거가 아니다.
- 실험은 자신이 만든 컨테이너·프로세스만 정리했고 남은 자원이 없다.
- `./gradlew --offline clean build` 성공. 판매 앱 단위 76개, 통합 123개(대조 SQL 정상 1건과 의도적 손상 21건 포함), Mock PG 11개·15개 모두 실패 0개. 새 의존성이 없어 오프라인 빌드와 일반 빌드의 의존성은 같다. Python 실험 도구 테스트 52개 통과.
- `python3 scripts/check-wiki-diagrams.py`와 `git diff --check` 통과.
