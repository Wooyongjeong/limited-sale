# 1-5 제품 등록·조회

상태: 정책·구현 범위·완료 기준 확정. 사용자로부터 구현 시작 지시를 받았으며 지정 워커가 구현과 자체 검증을 마쳤다. 기존 구현은 주 에이전트 독립 검증까지 완료했다. 이후 JSON 파싱 재검토 보완도 주 에이전트 독립 검증을 완료했다.

[1단계 정책](01-mysql-order.md), [기술 계약](01-contracts.md), [구조](../architecture.md)를 따른다.

## 기존 확정 정책

- 제품 등록은 ADMIN 전용이다. 목록·상세는 공개 조회다.
- 제품명 최대 100자, 설명 최대 2,000자, 기준 가격은 원화 정수 1~1,000,000,000원이다. 무료·소수점·다중 통화는 제외한다.
- 제품명 중복을 허용한다. 제품별 공용 재고는 두지 않고 이벤트가 전용 수량을 소유한다.
- 목록은 페이지 방식으로 기본 20개·최대 100개다.
- 이벤트 생성 시 product.api로 제품 정보를 조회하고 제품명·판매 가격을 별도 보관한다. 제품 기준 가격은 판매 가격의 기본 제안값이다.
- 공통 ApiResponse<T>와 product 소유의 성공·오류 enum을 사용한다. 순수 도메인과 JPA 엔티티를 분리한다.

## 이번에 확정한 정책

- 이번에는 등록·목록·상세만 구현한다. 수정·삭제·검색 기능은 포함하지 않는다.
- 목록은 ID 내림차순이다. page는 0부터, size는 기본 20·최대 100이다. 음수 page·1~100 밖의 size·정수가 아닌 입력은 400, 마지막 이후 페이지는 빈 목록 200이다.
- 제품명은 앞뒤 공백 제거 후 1~100자로 검증한다. 내부 공백과 문자 종류는 제한하지 않는다. 설명은 선택 입력이며 생략·null이면 빈 문자열, 입력 시 원문을 보존하고 최대 2,000자로 제한한다.

- 등록 성공은 201, 상세·목록 조회는 200이다. 등록·상세 data는 productId·name·description·basePrice·createdAt·updatedAt을 반환한다. 목록 items에서는 description을 제외한다. ID는 숫자, 시각은 UTC ISO 8601 문자열이다.
- 목록 data는 items·page·size·totalElements·totalPages다. 없는 제품은 404, 잘못된 ID·입력은 400이다. 알 수 없는 등록 JSON 필드는 400으로 거절한다.
- 이미지·카테고리·등록 요청 멱등성 키는 이번 범위에서 제외한다. 동일 입력 재등록은 별도 제품을 만들 수 있다.

## 확정한 구현·검증 계획

- product.api 공개 인터페이스·계약, application 유스케이스, 순수 domain·저장소 계약, infrastructure 영속 어댑터, presentation HTTP 진입점을 구성한다.
- POST /api/v1/admin/products, GET /api/v1/products, GET /api/v1/products/{id}를 기본 경로로 한다.
- Spring Data Pageable·Page는 영속 어댑터에서 사용하며 domain·product.api에 노출하지 않는다. 외부 입력은 page>=0·1<=size<=100·정수 여부를 검증한 뒤 변환하고 정렬은 ID 내림차순으로 고정한다. 조회 인덱스 계산은 오버플로 없이 처리한다.
- 기존 공통 응답과 세션·권한·CSRF 정책을 재사용한다. 공개 조회의 Redis 장애 동작도 확인한다.
- 입력 경계·금액 범위·동일 제품명 등록과 목록 순서·페이지 경계를 검증한다.
- 실제 MySQL 저장·조회와 HTTP 응답을 검증한다. ADMIN 성공·USER 거절·미인증 거절·CSRF 오류를 확인한다.
- 외부 도메인이 product.api만 참조할 수 있도록 기존 ArchUnit 검사를 유지한다.
- 기존 회원·세션·스키마 검증을 포함한 Java 21 전체 build 결과와 남은 제약을 기록한다.

## 워커 구현 내용

- `ProductCommand`·`ProductQuery`와 불변 결과 계약을 제공하고, 순수 도메인 검증과 별도 JPA 엔티티·저장소를 연결했다.
- 관리자 등록과 공개 목록·상세를 연결하고 기존 세션·CSRF 설정을 재사용한다. 알 수 없는 JSON 필드, 정수가 아닌 금액, 페이지·ID 오류를 거절한다.
- 목록은 ID 내림차순이며 일반 조회는 Pageable·Page를 사용한다. JPA 정수 오프셋을 넘으면 총수를 확인하고 범위 안인 경우 MySQL 쿼리에 long 오프셋을 전달한다. READ COMMITTED에서 목록과 총수 조회 사이에 삽입이 일어나면 서로 다른 시점의 결과가 보일 수 있다. 설명은 상세에만 포함한다.
- 주 에이전트가 확인한 계약 차이에 따라 입력 검증 오류에 안전한 field·reason 목록을 제공한다. JSON 구문 분석 실패는 기존 회원 처리처럼 data가 null이다. 예상하지 못한 IllegalArgumentException은 400으로 분류하지 않는다.
- 기존 세션 통합 테스트의 제품 테스트 엔드포인트를 실제 제품 조회로 교체했다.

## 워커 검증 근거

- Java 21의 `./gradlew clean build`: 재검토 보완 후 단위·구조 22개와 실제 MySQL·Redis 통합 36개 성공, 실패·오류·건너뜀 각각 0개. XML 결과로 수를 확인했다.
- HTTP 등록·조회와 역할·CSRF, 잘못된 입력 및 Redis 장애를 격리된 Testcontainers로 검증했다. 기존 세션·스키마 검증도 같은 빌드에 포함했다.
- `git diff --check`가 통과했다. 주 에이전트가 당시 코드·계약·테스트와 빌드를 독립 확인했다. 이후 JSON 파싱 보완은 별도 독립 검증이 필요하다.

## 주 에이전트 독립 검증

- 실제 구현을 검토해 Pageable 미적용과 필드별 오류 누락을 발견했고 지정 워커가 보완했다. 보완 후 도메인 경계·타입·권한·CSRF·목록 계약과 테스트 근거를 재검토했다.
- Java 21에서 ./gradlew clean build를 별도로 실행해 1분 25초에 성공했다. XML 집계는 일반·구조 22개, MySQL·Redis 통합 36개이며 실패·오류·건너뜀은 모두 0개다.
- 변경 문서의 파일 링크·코드 블록과 git diff --check를 확인했다.
- JPA int 범위를 넘고 총수보다 작은 오프셋 분기는 40억 건을 실제 적재하지 않고 단위 테스트로 검증했다. 동시 등록 중 페이지 총수와 내용은 READ COMMITTED의 서로 다른 조회 시점을 반영할 수 있다.
- 커밋·푸시·PR·머지는 아직 수행하지 않았다. 다음 1-6은 별도 정책 협의와 구현 지시 후 진행한다.


## JSON 파싱 재검토 보완

- 독립 재검토 요청에 따라 실제 ADMIN·CSRF HTTP 요청을 재현했다. 객체 뒤에 추가 객체·숫자·잘못된 문자열이 있거나 같은 필드를 반복한 다섯 요청이 기존에는 201로 저장됐다.
- 제품 등록 전용 역직렬화에서 중복 필드와 첫 JSON 값 뒤의 내용을 거절한다. 파싱 오류는 `400 INVALID_INPUT`과 `data:null`이며 정상 JSON 앞뒤 공백, UTF-8, 기존 입력 검증 및 콘텐츠 형식 처리를 유지한다.
- 보완 후 Java 21 `./gradlew clean build`에서 단위·구조 22개와 실제 MySQL·Redis 통합 37개가 성공했고 실패·오류·건너뜀은 각각 0개다. 실제 HTTP 테스트에서 다섯 잘못된 요청의 400과 저장 건수 불변, 정상 UTF-8·공백 요청과 빈 본문·415 처리를 확인했다.
- 위의 이전 독립 검증과 빌드 기록은 이번 보완 전 기준이다. 이번 변경은 주 에이전트가 전용 파서·회귀 테스트를 직접 검토하고 독립 검증을 완료했다.

- 재검토 보완 독립 검증: Java 21 ./gradlew integrationTest --tests '*ProductIntegrationTest'를 별도로 실행해 16초에 성공했다. 제품 통합 테스트 3개가 실패·오류·건너뜀 없이 통과했다. 워커의 최종 전체 빌드 로그와 XML(일반·구조 22개, 통합 37개, 모두 성공)도 확인했다. 전역 ObjectMapper와 다른 도메인은 변경하지 않았다.
