# 4단계: 장애 검증과 포트폴리오 정리

작성일: 2026-11-10

[전체 기획](../project-plan.md) · [구조 설계](../architecture.md)

## 상태

착수 전. 구체적인 장애 시나리오와 복구 기대 결과는 앞 단계 구현을 바탕으로 함께 확정한다.

## 확정한 방향

기능 수보다 동시성·정합성·장애 복구를 재현하고 검증한 근거를 포트폴리오에 남긴다. 개발자는 설계 판단과 실험 해석을 맡고, AI가 만든 구현과 실험 도구를 검증한다.

## 구현·정리할 사항

- API 2개와 MySQL·Redis·Kafka·Mock PG의 전체 흐름에서 장애를 재현한다.
- Redis·Kafka 중단, 소비자 강제 종료, DB 저장 실패, 결제 응답 유실과 재시도를 실험한다.
- 재고·구매 한도·주문·결제·접수 상태를 대조하고 복구 절차를 정리한다.
- 재현 명령, 대시보드, 실행 환경, 원본 결과와 분석을 남긴다.
- 선택한 설계·대안·한계, AI 제안에서 발견한 문제와 수정 근거를 기록한다.

## 실행 체크리스트

- [ ] 사용자와 장애 시나리오·복구 기대 결과·검증 기한·범위 확정
- [ ] 사용자로부터 해당 실험 도구·복구 기능 구현 시작 지시 받음
- [ ] Orca `gpt-6.1-terra / high` 워커가 합의한 도구·기능 구현 및 실행 근거 보고
- [ ] 주 에이전트가 변경 사항·실험 산출물·검증 근거 확인
- [ ] 재고·구매 한도·주문·결제·접수 결과 대조 및 실패 원인 기록
- [ ] 재현 명령·대시보드·성능 비교·AI 협업 기록 정리
- [ ] 개발자와 결과·한계 확인 후 단계 완료 기록

완료 근거와 남은 문제는 이 문서에 누적한다. 실험을 나눠 진행할 때도 각 범위를 먼저 확정하며, 지정 워커의 보고만으로 완료 처리하지 않는다.

## 검증 기준

실험 전에 예상 결과와 검증 기한을 정한다. 복구 후 초과 판매·구매 한도 초과·중복 주문·중복 결제가 없어야 한다. 모든 접수 요청은 최종 상태와 대조하고, 처리 실패도 원인을 보고한다. 모두 실패하거나 미완료 요청을 제외한 결과를 성공으로 설명하지 않는다.

## 미정 사항

장애 주입 지점, 실험별 검증 기한·복구 목표·예상 수량, 관측 임계값과 포트폴리오 공개 범위는 단계 시작 시 함께 확정한다.
