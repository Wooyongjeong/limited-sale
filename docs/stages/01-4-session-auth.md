# 1-4 Redis 세션 인증 상세 협의

상태: 정책·설계·구현 범위·완료 기준 확정, 사용자 구현 시작 지시, 지정 워커 구현·보완과 주 에이전트 독립 검증을 완료했다. 작업 브랜치는 `feat/1-4-redis-session-auth`다. 1-5는 시작하지 않았다.

기존 정책은 [1단계 정책](01-mysql-order.md)과 [기술 계약](01-contracts.md)을 따른다. 세션 유휴 만료 30분, 여러 기기 로그인 허용, 현재 세션만 로그아웃, 쿠키·CSRF 보호와 Redis 장애 시 인증 불가 503은 기존 합의다.

## 로그인 실패 제한 확정 정책

2026-11-11 AI가 아래 네 가지를 제안했고 사용자가 모두 선택했다.

- 정규화 이메일+IP 조합의 첫 로그인 실패부터 기본 5분을 계산한다. 추가 실패로 만료를 연장하지 않는다. 종료 시각을 명확히 하기 위해 선택했으며 구간 경계에서는 시도가 몰릴 수 있다.
- 해당 구간의 1~4번째 실패는 401, 5번째 실패부터 429를 반환한다. 차단 중에는 비밀번호가 맞아도 구간 만료까지 로그인 요청을 거절한다. 제한 도달 시점부터 동일하게 차단하기 위해 선택했다.
- 차단 전에 로그인이 성공하면 해당 이메일+IP 조합의 실패 기록을 초기화한다. 다른 IP의 실패 기록은 유지한다. 정상 로그인 뒤 과거 실패가 누적되지 않게 하기 위해 선택했다.
- 현재는 직접 연결한 클라이언트 IP를 사용하며 X-Forwarded-For 등 전달 헤더는 IP 판정에 사용하지 않는다. 프록시를 도입하면 신뢰 범위를 별도로 정한다. 현재 프록시 구성이 없는 환경에서 임의 헤더를 신뢰하지 않기 위해 선택했다.

예: 12:00 첫 실패 후 12:02 다섯 번째 실패가 발생하면 12:05까지 차단한다. 횟수와 구간 길이는 설정으로 변경할 수 있다.

## CSRF·Redis 장애 처리 확정 정책

2026-11-11 AI가 아래 네 가지를 제안했고 사용자가 모두 선택했다.

- `GET /api/v1/csrf`에서 토큰을 받고 변경 요청의 `X-CSRF-TOKEN` 헤더로 전달한다. 회원가입·로그인 전에도 토큰을 조회한다. 호출 규칙을 명확히 하기 위해 선택했으며 사전 조회가 필요하다.
- 로그인·로그아웃 성공 후 다음 변경 요청 전에 CSRF 토큰을 다시 조회한다. 인증 상태 변경 후 사용할 토큰을 명확히 하기 위해 선택했으며 조회 요청이 추가된다.
- Redis 장애로 로그인 실패 횟수 확인·기록이 불가능하면 로그인은 503으로 거절한다. 제한 우회를 막기 위해 선택했으며 장애 동안 정상 로그인도 불가능하다.
- 로그아웃 시 Redis 세션 삭제를 확인하지 못하면 503을 반환하고 성공으로 응답하지 않는다. 서버 세션이 남아 있을 수 있음을 응답에 반영하기 위해 선택했으며 복구 후 재시도가 필요하다.

## 세션·응답 경계 확정 정책

2026-11-11 AI가 아래 네 가지를 제안했고 사용자가 모두 선택했다.

- 세션 만료 후 보호 API는 401을 반환한다. 자동 로그인하지 않는다. 만료를 명확히 알리는 방식을 선택했으며 사용자는 다시 로그인해야 한다.
- 이미 로그아웃됐거나 만료된 세션의 로그아웃은 CSRF 검증을 통과하면 200과 `data:null`을 반환한다. 재시도 결과를 일정하게 하기 위해 선택했다. 유효한 CSRF 토큰이 없으면 토큰을 다시 조회해야 한다.
- Redis 장애로 CSRF 토큰 생성·저장이 불가능하면 CSRF 조회는 503을 반환한다. 사용할 수 없는 토큰을 성공으로 반환하지 않기 위해 선택했다.
- 로그인·내 정보 응답에는 이메일·닉네임·권한을 반환한다. 회원가입 응답과 일관되게 내부 회원 ID와 비밀번호 해시는 노출하지 않는다.

## 동시 로그인 확정 정책

2026-11-11 AI가 동시 요청의 결과 반영 순서를 제안했고 사용자가 선택했다.

- 로그인 시작 시 차단 여부를 확인하고 비밀번호 확인 뒤 결과를 반영할 때 다시 확인한다.
- 비밀번호가 맞더라도 결과 반영 전에 다른 요청으로 차단이 시작됐다면 429로 거절한다.
- 성공·실패는 Redis에 결과가 반영되는 순서로 처리한다. 성공으로 실패 기록을 초기화한 뒤 늦게 끝난 실패는 새로운 실패로 계산한다. HTTP 요청 도착 순서를 보장하지 않는다.
- 실패 횟수 증가·최초 만료 설정·차단 판정은 하나의 원자 작업으로 처리한다. 성공 시에도 차단 재확인과 실패 기록 초기화를 원자적으로 처리해야 위 규칙을 유지할 수 있다.

실패 4회 상태에서 실패 결과가 먼저 반영되면 함께 진행 중이던 정상 요청도 429다. 정상 결과가 먼저 반영되면 기록을 초기화하고 뒤의 실패는 1회로 계산한다. 여러 인스턴스에서 일관된 판정 기준을 갖기 위해 선택했으며 먼저 보낸 요청이 먼저 처리된다는 보장은 없다.

## 구현 범위·설계 제안

아래 내용은 주 에이전트가 현재 소스를 확인해 제안했고 사용자가 2026-11-11 확정한 설계·범위다. 사용자가 작업 브랜치 생성과 구현 시작도 지시했다.

### API

모든 응답은 기존 `ApiResponse<T>`를 사용한다.

| API | 성공 코드·데이터 제안 |
|---|---|
| GET /api/v1/csrf | 200 / CSRF_TOKEN_ISSUED, data는 token·headerName |
| POST /api/v1/sessions | 200 / LOGIN_SUCCEEDED, data는 email·nickname·role. 입력은 email·password |
| DELETE /api/v1/sessions/current | 200 / LOGOUT_SUCCEEDED, data:null |
| GET /api/v1/members/me | 200 / MEMBER_RETRIEVED, data는 email·nickname·role |

오류 코드는 401의 `AUTHENTICATION_REQUIRED`·`INVALID_CREDENTIALS`, 403의 `ACCESS_DENIED`·`CSRF_INVALID`, 429의 `LOGIN_RATE_LIMITED`, Redis 인증 인프라 장애 503의 `AUTHENTICATION_UNAVAILABLE`을 제안한다. 입력·미디어 타입 등 기존 공통 계약은 유지한다. 알 수 없는 이메일과 비밀번호 불일치는 같은 코드·메시지를 사용한다.

### 책임과 흐름

현재 `Member`는 이메일·닉네임·권한만 가진 응답 데이터이며 `PasswordHasher`에는 hash만 있다. 인증용 내부 식별자·비밀번호 검증 기능을 추가하되 기존 회원 응답에 내부 ID나 해시를 추가하지 않는다.

- `member.presentation`은 인증 API와 HTTP 응답 변환을 맡는다.
- `member.application`은 회원 조회·비밀번호 검증·로그인 제한 결과를 조합한다. 가입 서비스와 인증 유스케이스의 책임을 나눈다.
- `member.domain`은 회원 인증에 필요한 저장소·비밀번호 검증·로그인 제한 계약을 소유한다. Spring·Redis 타입은 노출하지 않는다.
- `member.infrastructure.security`는 Spring Security 인증 어댑터를, `member.infrastructure`의 Redis 구현은 원자적인 로그인 제한 저장을 맡는다. 해시는 회원 내부에서만 사용하고 세션에 저장하지 않는다.
- `common`은 보안·세션의 기술 설정과 공통 응답 처리에 한정한다. 회원 인증 규칙을 옮기지 않는다.
- 다른 도메인이 인증된 회원을 참조할 때는 `member.api`의 불변 식별 계약을 사용한다. 세션·Spring Security 객체를 업무 유스케이스로 전달하지 않는다. 실제 호출이 없는 공개 API는 미리 만들지 않는다.

로그인 흐름은 입력 정규화·검증 → 제한 확인 → MySQL 회원 조회 → DB 트랜잭션 밖에서 비밀번호 검증 → Redis의 결과 원자 반영 → 세션 저장 → 응답이다. 로그인 성공 시 세션 ID를 교체하고 세션 저장 실패를 성공으로 반환하지 않는다. 비밀번호 해시·원문을 세션이나 응답·로그에 넣지 않는다.

Redis Compose·환경변수·연결 설정, Spring Security·Spring Session 의존성, 쿠키·CSRF·유휴 만료 설정을 추가한다. 세션 생성·공유와 로그인 제한까지만 다루며 조회 캐시·주문 요청 제한은 포함하지 않는다. Redis 장애 시 공개 경로가 불필요하게 세션에 의존하지 않도록 검증한다.

## 워커 구현과 검증 (2026-11-11)

Spring Security와 Spring Session Redis로 로그인·로그아웃·내 정보·CSRF 조회를 구현했다. 로그인 실패 제한은 정규화 이메일과 직접 연결 IP의 해시를 Redis 키로 사용하며 Lua 연산으로 제한 재확인, 성공 초기화 또는 실패 증가와 최초 만료를 원자 처리한다. 비밀번호 검증은 회원 도메인 내부에서 수행하고 세션에는 내부 ID와 응답용 회원 정보만 저장한다.

Java 21과 Docker 29.9.2에서 `./gradlew test integrationTest`와 `./gradlew clean build`를 실행했다. 격리된 MySQL 8.4.7·Redis 7.4와 두 HTTP 서버를 사용해 세션 공유, CSRF·세션 고정 보호, 유휴 만료와 갱신, 다섯 번째 실패와 고정 만료, 동시 결과 반영, 전달 IP 헤더 무시, Redis 장애·복구를 검증했다. clean build XML은 단위 테스트 11개, 통합 테스트 28개이며 각각 실패·오류·건너뜀은 0개다. Flyway의 MySQL 8.4 지원 경고는 기존과 같이 남는다. 주 에이전트의 독립 검증은 아직 완료하지 않았다.

## 독립 소스 리뷰에 따른 워커 보완 (2026-11-11)

리뷰에서 실패 횟수 설정 누락, 관리자 권한 경계와 공개 조회 경로의 누락, 세션 API의 응답 형식 협상 시점 문제를 확인했다. 로그인과 로그아웃에 XML 응답을 요청하면 406을 반환하고도 각각 세션 ID 교체와 세션 무효화가 일어나는 것을 수정 전 실패 테스트로 재현했다. `produces` 선언으로 컨트롤러 실행 전에 요청을 거절하고, 로그인 실패 기록도 초기화되지 않는 것을 검증했다.

실패 횟수와 구간을 양수 설정으로 검증하고 Redis의 확인·완료 Lua 연산에 같은 횟수 설정을 전달한다. 기본 5회 외에 3회·3초 설정으로 실제 HTTP 차단과 구간 만료 후 로그인을 확인했다. 관리자 경로는 ADMIN 전용이며 제품·이벤트 목록과 상세 GET은 공개로 설정했다. 테스트 전용 엔드포인트와 두 실제 HTTP 서버를 사용해 미인증 401, USER 403, ADMIN 200 및 공개 조회를 확인했다.

실제 HTTP 세션 쿠키의 HttpOnly·SameSite=Lax와 Secure 미설정, 앱이 실제 사용하는 세션 ID resolver에서 HTTPS 요청으로 Secure가 설정되는 것을 검증했다. ## 재리뷰 발견과 워커 보완 (2026-11-11)

인증 처리 중 예상하지 못한 예외가 공통 500 응답으로 변환되지 않는 문제를 회귀 테스트로 재현했다. 인증 예외 처리 경계에서 내부 상세를 감춘 `INTERNAL_ERROR`를 반환하고, 프레임워크 4xx와 Redis 연결·시스템 오류는 기존 처리기로 넘기도록 수정했다. 가입 오류 경계는 별도로 유지했으며 Redis 오류 판정은 외부 필터와 인증 예외 처리기가 공유한다.

실제 Redis 중단 시 공개 조회는 익명으로 성공했지만 유효 세션 쿠키가 있으면 503이 발생하는 문제도 재현했다. 제품·이벤트 공개 GET에 세션 쿠키가 있으면 Redis 연결을 확인하고, 연결 실패 시 해당 요청에서만 세션 쿠키를 숨겨 공개 조회를 처리한다. Redis가 정상일 때는 기존 세션을 읽어 유휴 시간을 갱신하며 장애 중 브라우저 쿠키를 삭제하지 않는다. 이 방식은 쿠키가 있는 공개 GET에 Redis 확인 요청을 추가하며, 확인 직후 세션 접근 전에 Redis가 중단되는 경우에는 해당 요청이 503이 될 수 있다.
