# 1-7-4 DB 기반 자동 복구와 작업 임대

상태: 워커 구현·주 에이전트 독립 리뷰와 검증·위키 갱신 완료. 커밋·푸시·PR·머지는 미진행.

[작업 분할](01-7-order-payment.md), [주문·결제 계약](01-contracts.md), [사용자 결제](01-7-3-order-payment-integration.md)를 따른다.

## 확정 정책

- 복구 대상은 결제 미요청·처리 중·결과 미확인과 결제 결과 저장 후 주문 마무리가 남은 주문이다. 주문의 next_recovery_at·lease_token·lease_until을 DB에 영속 저장한다.
- 결제를 요청하지 않은 주문을 자동으로 결제하지 않는다. 미요청 주문은 만료 전에는 기다리고, 주문 생성 후 기본 5분에 PG 종료 확인으로 진입한다.
- 결제 시작 이력이 있는 주문은 만료 전 조회 우선이다. PG 조회 404이면 같은 키로 결제를 재개할 수 있다. 만료 이후에는 새 결제를 시작하지 않고 종료를 확인한다.
- PG 결과를 모르면 점유를 유지한다. PG 성공은 주문 확정, 실패는 PAYMENT_FAILED, CLOSED는 EXPIRED로 마무리한다. 결제 결과가 이미 최종이면 PG 없이 주문·수량 마무리를 재적용한다.
- 5분 이후 PG 결과를 확인하지 못한 주문은 requiresReview로 표시하고 기본 10초 간격으로 계속 재확인한다. 횟수 소진에 따른 자동 실패·강제 해제는 없다.
- 운영 확인 대상으로 처음 전환할 때 경고 로그를 남기고, 미해결 상태가 계속되면 기본 5분 간격으로 반복 경고한다. 관리자 수동 처리 API·외부 알림 연동은 이번 범위에서 제외한다.
- 사용자 결제 요청과 자동 복구가 동일한 주문별 임대를 공유한다. 다른 작업의 임대가 유효하면 사용자 요청은 저장된 상태로 202를 반환한다. 만료 도달은 10초 간격은 건너뛰지만 유효 임대를 빼앗지 않는다.
- 기본 스케줄 간격 1초, 회당 최대 20건, 서버당 동시 4건, 주문별 임대 30초다. 모두 설정 가능하게 한다. 실제 실행 직전에만 임대를 획득해 실행 대기열에서 임대가 만료되지 않게 한다.
- 소유권은 DB 시각과 토큰으로 검사한다. 만료되거나 다른 토큰으로 교체된 이전 작업은 뒤늦은 결제 결과 저장·주문 마무리·임대 해제·다음 예약 변경을 할 수 없다. PG 자체는 고정 키와 최종 상태 불변으로 보호한다.
- 3초 PG 통신 예산, 10초 재조회 간격, 상태·수량의 멱등성 및 DB 잠금 밖 HTTP 원칙은 유지한다. 자동 복구의 만료 후 실패 재예약도 기본 10초이며 매 스케줄 틱마다 PG를 호출하지 않는다.

사용자는 계속 재확인·운영 경고, 사용자와 복구의 임대 공유, 제안한 실행 기본값과 토큰 검증을 선택했다. 서버 중단 뒤 재개 가능성과 다중 서버 중복 처리 제어를 함께 검증하기 위한 선택이다.

## 구현 계획

1. 주문 도메인의 임대·복구 계약과 순수 판정 규칙을 추가한다. 기존 사용자 결제 조합을 재사용하되 사용자 소유권 확인과 내부 복구 진입은 구분하고 도메인 api 경계를 유지한다.
2. 짧은 DB 트랜잭션으로 실행 시각이 도래한 후보를 찾고, 각 실행 직전 주문 잠금 후 현재 상태·DB 시각·임대·재조회 조건을 다시 검사한다. 후보 목록을 읽었다는 이유만으로 실행 권리를 가정하지 않는다. 잠긴 후보 때문에 전체 처리가 멈추지 않는 조회 방식과 인덱스를 검증한다.
3. 신규 UUID 토큰과 임대 만료를 커밋한 후 HTTP를 실행한다. 사용자 요청도 같은 임대 경로를 통과한다. 응답 저장과 최종 마무리에서는 토큰과 임대 유효성을 다시 검사한다. 동일 토큰의 중복 실행도 최종 상태·주문 잠금·원자적 수량 반영으로 방어한다.
4. 완료·재예약·경고 시각 반영과 임대 해제도 소유권을 확인한다. 오래된 작업은 새로운 작업의 예약과 임대를 지우지 않는다. 미해결 결과와 일시적 DB 오류는 후속 실행 가능성을 남기며 프로세스가 죽으면 임대 만료 후 회수한다.
5. 경고 간격 판단은 재시작·다중 서버에서도 유지되게 DB에 저장한다. 필요한 필드·인덱스 변경은 새 Flyway 버전으로 추가하며 기존 이력과 개발 데이터를 보존한다. requiresReview는 최종 정리 시 해제하고 경고 반복을 중단한다.
6. 스케줄러는 켜기/끄기 설정을 제공하고 실행 중 작업 수와 회당 처리량을 제한한다. 병렬 작업을 무제한 쌓거나 실행 대기 중 임대를 선점하지 않는다. 종료 시 신규 작업 접수를 중단하며 강제 중단은 임대 만료·토큰 검증으로 수렴시킨다.
7. 단위·실제 MySQL·HTTP·Redis 검증 후 주 에이전트가 리뷰하고, 문제가 해결되면 위키·도식을 자동 복구가 있는 현재 흐름으로 갱신한다.

DB 트랜잭션 실패를 성공·결제 거절로 바꾸지 않는다. 복구 작업 한 건의 실패가 다른 주문의 진행을 막지 않게 하고, 반복 실패 시 다음 예약과 임대 만료로 재진입한다. 주문 생성 후 결제 미요청 기록의 next_recovery_at은 만료 시각을 유지한다.

## 검증 기준

- 사용자 재요청 없이 성공·거절·지연·응답 유실 주문이 자동으로 최종 결과에 수렴하고 수량이 일치한다.
- 미요청 주문을 만료 전 임의 결제하지 않으며 만료 후 종료 확인을 통해서만 점유를 해제한다.
- PG 장기 중단 중 점유 유지·requiresReview·경고 간격·10초 재예약을 검증하고 PG 복구 후 최종 정리를 확인한다.
- 다중 앱이 같은 후보를 가져도 유효 임대 소유자는 하나이고, 서로 다른 주문은 병렬로 진행한다.
- 임대 획득 직후·PG 성공 직후·결제 저장 직후·주문 마무리 직전의 중단 후 재시작이 저장된 상태로 수렴한다.
- 임대 만료 후 새 토큰이 발급되면 옛 작업의 늦은 결과·해제·예약 변경을 거절한다. PG는 중복 청구되지 않고 재고는 중복 확정·해제되지 않는다.
- 사용자 요청과 복구 경쟁, 만료 경계, DB 잠금 대기 후 시각, 실행 용량과 후보 공정성을 실제 MySQL에서 검사한다.
- 스케줄러 비활성화와 설정 검증, 종료·재시작, 오류 격리 및 기존 사용자 결제 회귀를 검사한다.
- Java 21 전체 clean build, 위키 링크·Excalidraw 원본/SVG 검사와 렌더링을 확인한다.

## 워커 구현·검증 기록

- 사용자 결제와 복구가 주문별 임대를 공유하고, 주문 잠금 이후 DB 시각과 토큰을 검사한다. 결제 저장과 주문·수량 마무리는 각각 별도 트랜잭션에서 소유권을 재검사하며 잠금 대기 중 임대가 만료되면 변경을 롤백한다. PG 통신은 트랜잭션 밖에서 하나의 3초 예산을 공유한다.
- 후보 조회는 `SKIP LOCKED`를 사용하고 실행 스레드에서 임대를 획득한다. 기본 주기·회당 건수·동시 실행·임대 시간은 각각 `limited-sale.recovery.interval`·`batch-size`·`concurrency`·`lease-duration`으로 설정하며 `enabled`로 스케줄러를 끌 수 있다. 미해결 재시도는 결과 확인 후 기본 10초, 경고 반복은 `warning-interval` 기본 5분이다.
- 새 Flyway V5는 마지막 경고의 다음 시각을 추가한다. 최종 정리는 재고와 주문을 같은 트랜잭션으로 반영하고 복구 예약·임대·운영 확인 표시를 지운다.
- Java 21 `./gradlew clean build` 결과 총 194건, 실패 0·오류 0·건너뜀 0이다. MySQL·Redis·HTTP 통합 검사에서 잠긴 후보, 두 노드의 경쟁과 병렬 작업, 사용자 요청 경합, 미요청 만료, 지연·거절·응답 유실, 경고·재시도, 토큰 교체와 잠금 대기 중 만료를 확인했다. 후보 조회의 기존 인덱스 컬럼과 MySQL `EXPLAIN`의 사용 가능 인덱스를 확인했다.
- 임대 커밋 직후와 실제 PG 성공 직후에는 예외를 주입해 중단했고, 결제 저장 후 마무리 실패는 DB 트리거로 재현했다. 영속 중간 상태에서 별도 앱 인스턴스를 종료·재시작해 수렴을 확인했으나 OS 프로세스 강제 종료 자체는 실행하지 않았다. 5분 경고와 재시도 검사는 격리 DB의 예정 시각을 조정했으며 실제 5분 장기 대기는 수행하지 않았다.
- 테스트 PG 연결의 UTC 옵션 누락으로 지연 완료 판정이 9시간 어긋나는 것을 발견해, 테스트 연결을 실제 Mock PG 설정과 동일하게 맞췄다. 상세 로그와 변경 파일은 `/tmp/1-7-4-worker-report.md`에 기록하며 주 에이전트의 독립 코드리뷰·위키 갱신은 별도로 남는다.

## 주 에이전트 독립 리뷰와 검증

- 임대 취득·후보 조회·실행 용량 제한, 사용자 요청과 복구 경합, 잠금 후 DB 시각·토큰 검사, 결과 저장과 수량 반영·재예약·해제, 종료 및 테스트 코드를 검토했다. 추가 코드 수정이 필요한 문제는 발견하지 못했다.
- 마지막 코드 변경 이후 주 에이전트가 Java 21 `./gradlew clean build`를 실행해 3분 27초에 성공했다. XML 결과는 판매 앱 단위 74개·통합 94개, PG 단위 11개·통합 15개로 총 194개, 실패·오류·건너뜀 모두 0개다. 로그는 `/tmp/limited-sale-174-primary-build.log`다.
- [자동 복구 위키](../wiki/recovery.md)를 추가하고 결제·실패·실습·영속·운영 설명과 루트 README를 현재 자동 복구 흐름으로 맞췄다. 재시작·오래된 작업 차단·운영 확인 경고와 설정값을 설명했다.
- 복구 도식 1개를 추가하고 기존 서버 경계·응답 유실 복구·마이그레이션 그림 3개를 갱신했다. 렌더러로 SVG를 생성한 뒤 변경 그림 4개를 직접 확인했다.
- `python3 scripts/check-wiki-diagrams.py`: 위키 18페이지·링크 377개·Excalidraw/SVG 33쌍 통과. `git diff --check` 통과.
- 검증 범위는 예외·DB 트리거 주입과 앱 인스턴스 종료·재시작, 격리 DB 예정 시각 조정을 포함한다. OS 프로세스 강제 종료와 실제 5분 이상 장애 대기는 수행하지 않았으며 그 결과를 입증했다고 주장하지 않는다. 대량 데이터 처리량과 실행 계획 선택도 측정하지 않았다. 해당 실험 확대는 다음 1-7-5에서 협의한다.
- 커밋·푸시·PR·머지 및 다음 단계 시작은 수행하지 않았다.

## 1-7-3·1-7-4 통합 코드리뷰 보완

사용자가 워커 대신 주 에이전트에게 직접 리뷰·수정을 지시했다. 결제 통신·엄격 응답 검증, 최종 상태 유지, 주문·수량 마무리, 사용자/복구 공유 임대와 오래된 토큰, 재예약·종료 경로를 검토했다.

- 운영 확인 경고가 커밋 전에 출력되어 이후 임대 만료·DB 오류로 롤백돼도 로그가 남는 문제를 수정했다. 표시와 다음 경고 시각이 저장되지 않은 시도에서 반복 경고가 발생할 수 있었다.
- 두 회귀 검사에서 기존 코드가 실패하는 것을 확인했다. 트랜잭션 afterCommit에 경고 출력을 등록해 커밋 전과 롤백에는 출력하지 않고 성공 커밋 뒤에만 출력한다. 경고 예약·상태 판정은 기존 DB 트랜잭션에 남긴다.
- 이 변경은 로그를 영속 메시지로 전달하는 기능이 아니다. 커밋 직후 프로세스 중단 시 로그 누락까지 방지하지는 않는다.
