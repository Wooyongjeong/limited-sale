# 한정 수량 제품 판매 서비스 기획

작성일: 2026-11-10

## 목표

정해진 시간에 열리는 판매 이벤트에서 한정 수량의 제품을 선착순으로 주문하는 Java·Spring 백엔드를 만든다. 동시성, 데이터 정합성, Redis, Kafka 활용과 장애 복구 경험을 포트폴리오로 설명할 수 있어야 한다.

기능 수보다 문제 재현, 설계 선택, 측정, 개선 과정을 우선한다. 구현은 AI가 주로 담당하고, 개발자는 요구사항 결정과 설계 검토, 실험, 결과 검증을 맡는다.

## 합의한 방향

- 서비스 주제는 선착순 한정 수량 제품 판매다.
- 언어와 프레임워크는 Java와 Spring을 사용한다.
- DB는 로컬 Docker의 MySQL을 사용한다.
- DB 중심의 정확한 구현부터 시작해 Redis와 Kafka를 단계적으로 도입한다.
- 모니터링과 부하·장애 실험을 함께 구성한다.
- AI 협업 과정과 개발자 본인의 판단 근거를 기록한다.

## 기능 범위

첫 버전에는 이메일·비밀번호 회원가입·로그인, 로그아웃·내 로그인 정보, 제품 등록·조회, 판매 이벤트 관리·조회, 주문 요청, 주문 결과 조회, 내 주문 조회를 포함한다. USER·ADMIN 권한을 구분하며 사용자·관리자 세부 인증 정책은 상세 설계에서 결정한다. 부하 테스트에서는 서로 다른 사용자와 같은 사용자의 재시도를 구분한다.

결제는 포트폴리오 전체 기간에 걸쳐 판매 서버와 별도로 실행하는 Mock PG HTTP 서버로 처리한다. PG의 결제 기록은 별도 MySQL 스키마·계정에 저장하고 판매 서버는 HTTP로만 접근한다. 주문 생성과 결제 요청 API를 분리하며 주문 생성 시 수량을 점유한다. 실제 PG 연동은 계획하지 않는다. Mock PG를 포함한 주문·결제 흐름을 1단계에서 설계하며, 결제 성공 시 주문을 확정하고, 명확한 실패 시 점유를 해제한다. 타임아웃은 결과 확인 후 처리한다. Mock PG는 성공·명확한 실패·처리 지연·결제 성공 후 응답 유실을 재현한다. 응답 대기 3초, 결과 재조회 10초 간격, 주문 후 5분 경과 시 미결제 정리를 기본값으로 하며 설정으로 변경한다. 실패·취소가 확정되기 전에는 시간만으로 점유를 해제하지 않는다. 서버 재시작 후에도 DB 상태를 바탕으로 복구한다. 상세 계약은 [1단계 복구 정책](stages/01-mysql-order.md#확정한-결제-결과-확인복구-정책)을 따른다. 장바구니, 배송, 사용자 주문 취소·환불, 회원 탈퇴·비밀번호 변경은 초기 범위에서 제외한다. 복잡한 프런트엔드와 마이크로서비스 분리는 추가 범위로 잡지 않는다. 결제 실패에 따른 재고 복구는 사용자 취소 기능과 구분해 설계한다.

판매 이벤트 하나에는 제품 하나를 등록한다. 사용자별 구매 수량 한도는 이벤트마다 설정하며, 별도 설정이 없으면 기본값은 1개다. 한 번에 여러 개 구매하거나 여러 번 나눠 주문할 수 있으며, 이벤트별 사용자 누적 구매 수량으로 한도를 적용한다. 예를 들어 한도가 3개이면 2개 구매 후 1개를 추가 구매할 수 있다. 주문 수량은 양의 정수이며 남은 구매 한도와 판매 수량을 넘을 수 없다. 남은 재고 또는 사용자 잔여 구매 한도가 요청 수량보다 적으면 전체 요청을 거절하고 일부 수량만 자동 구매하지 않는다. 주문 시 재고와 사용자 구매 한도를 함께 임시 점유한다. 결제 성공 시 구매를 확정하고 명확한 실패 시 점유를 해제한다. 타임아웃 시에는 결제 결과를 확인하기 전까지 점유를 유지한다. 이벤트의 판매 한도는 해당 이벤트에 전용으로 배정된 수량이다. 여러 이벤트가 하나의 공용 재고를 공유하는 구조는 초기 범위에 포함하지 않는다. 제품명과 판매 가격은 이벤트에 별도로 보관한다. 판매 가격은 이벤트 생성 시 관리자가 지정하며 제품 기준 가격을 기본값으로 제공한다. 주문에도 해당 가격을 별도로 보관해 제품 정보 변경이 기존 주문을 바꾸지 않게 한다.

가격은 원화 정수로 개당 1원~10억원이며 무료·소수점·다중 통화는 제외한다. 이벤트 판매 수량은 1~100만개다.

인증은 이메일·비밀번호와 Redis 세션으로 확정했다. 1단계에서 인증용 Redis를 도입하고, 2단계에서 캐시·분산 요청 제한으로 확장한다. 세션은 마지막 요청 후 30분 유휴 만료를 기본값으로 하고 설정으로 변경할 수 있다. 여러 기기 로그인을 허용하며 로그아웃은 현재 세션만 종료한다. 공개 가입은 USER만 생성하고 ADMIN은 별도 초기화 명령으로 생성한다. 세부 범위는 [1단계 인증 정책](stages/01-mysql-order.md#확정한-인증-범위)에서 관리한다.

API 응답은 HTTP 상태 코드, 도메인별 enum 성공·오류 코드, 제네릭 데이터와 메시지를 담는 공통 템플릿을 사용한다. 상세 계약은 [1단계 API 응답 방향](stages/01-mysql-order.md#확정한-공통-api-응답-방향)을 따른다.

## 반드시 지킬 규칙

확정 정책: 결제는 Mock PG를 사용하고, 이벤트마다 제품 하나와 사용자별 구매 수량 한도를 설정한다. 한도 기본값은 1개다. 아래 검증 기준은 주문 수가 아닌 제품 수량을 기준으로 해석하며, 미정인 주문·결제 정책은 1-1에서 함께 확정한다.

- 확정 주문의 제품 수량 합계는 이벤트의 판매 한도를 넘지 않는다. 확정 수량과 결제 대기 중 점유 수량을 합산해 초과 판매를 방지한다.
- Mock PG가 모두 성공하고 장애와 요청 제한이 없는 상황에서, 접수 기간 안에 구매 한도 이내의 유효 요청이 판매 한도만큼 수량을 채울 수 있으면 해당 수량만큼 주문이 확정된다. 모든 요청을 거절하는 구현은 통과로 인정하지 않는다.
- 같은 사용자의 구매 수량은 해당 이벤트의 사용자별 한도를 넘지 않는다. 동시 주문에서도 확정 수량과 결제 대기 중 점유 수량을 합산해 한도를 지킨다.
- 재시도와 메시지 중복 전달이 추가 주문을 만들지 않는다. 클라이언트 요청 키가 같고 입력도 같으면 기존 주문·결제 결과를 반환하며, 같은 키로 이벤트·수량을 바꾸면 충돌로 거절한다.
- 비동기 도입 시 접수 응답과 주문 확정 응답을 구분한다. 1·2단계는 Kafka 접수 응답과 구분해 주문·결제 결과를 응답한다. 결제 결과가 불명확할 때의 응답과 조회 계약은 추가로 정한다. 주문 금액은 서버가 판매 이벤트의 가격으로 결정하며 클라이언트가 보낸 가격을 신뢰하지 않는다.
- 장애로 처리가 지연된 요청은 상태를 추적하고 복구할 수 있어야 한다.
- 접수된 요청은 정해진 검증 시간 안에 최종 결과에 도달해야 한다. 시간 초과나 처리 누락을 성공으로 간주하지 않는다.
- 최종 주문 기록은 MySQL을 기준으로 검증한다. Redis와의 일시적 차이는 감지·복구 정책을 정한다.

선착순의 기준은 상세 설계에서 확정한다. 클라이언트가 버튼을 누른 시간, HTTP 요청 도착, Kafka 기록, DB 확정 순서는 서로 다를 수 있다. 초기 DB 버전은 재고 점유 트랜잭션이 성공한 순서로 판매 가능 수량을 소진하며, 요청 도착 순서의 엄격한 보장을 주장하지 않는다. 비동기 전환 시 순서 보장 범위와 파티션 전략을 다시 정의한다.

## 이벤트 운영 정책

시작 후 이벤트명·설명 수정은 허용하지만 제품·가격·시작 시각·구매 한도·판매 수량·종료 시각 변경과 삭제는 금지한다. 관리자는 신규 주문을 중단할 수 있고 기존 주문·결제는 계속 처리한다. 종료·중단 상태로 기록을 보존한다. 시작 전에는 제품·가격·기간·판매 수량·구매 한도 수정과 삭제를 허용한다. 중단한 이벤트는 판매 기간 안에서 기존 조건을 유지한 채 재개할 수 있다. 종료 후 신규 주문·재개는 금지하고 기존 조회·결제·복구는 계속 처리한다. 상세 정책과 구현 범위는 [1단계 문서](stages/01-mysql-order.md#확정한-이벤트-운영-정책)를 따른다.

## 이벤트 시간 정책

접수 가능 시간은 시작 시각 이상, 종료 시각 미만으로 정한다. 시작 전과 종료 시각 이후에는 새로운 주문 요청을 거절한다. 시간의 기준은 클라이언트나 HTTP 도착 시각이 아닌 MySQL 수량 점유 트랜잭션의 잠금 획득 후 DB 시각이다. 이벤트 상태도 함께 판정하며 시각은 UTC로 저장한다.

종료 전에 재고를 점유한 주문은 종료 후에도 결제를 처리할 수 있다. 비동기 도입 후 종료 전에 유효하게 접수한 요청도 종료 후 처리할 수 있다. 비동기 소비자가 처리 시각을 기준으로 접수 기간을 다시 검사해 기존 요청을 탈락시키지 않는다. 접수는 주문 확정이나 수량 확보를 의미하지 않으므로, 최종 결과는 품절일 수 있다.

종료 후에도 기존 요청의 결과 조회와 재처리는 허용한다. 기존 요청의 재시도는 같은 요청으로 식별하고, 새 주문 기회로 취급하지 않는다. 비동기 단계에서는 접수 시각과 접수 식별자를 영속적으로 보관하고, 접수 응답을 반환하는 기준을 확정한다.

동기 단계에서는 동일 요청의 기존 주문·결제 상태를 조회해 재시도에 응답한다. 같은 사용자의 새 주문과 기존 요청의 재시도는 구분한다. 확정 기록이 없다는 이유로 새 주문을 만들지 않고 해당 요청의 결제 대기·결과 미확인 상태도 확인한다. 비동기의 영속 접수와 종료 후 처리는 3단계에서 적용한다.

테스트는 시작 직전·정각, 종료 직전·정각, 종료 전 접수 후 종료 후 처리, 종료 후 기존 요청 재시도를 포함한다. 경계 시각은 제어 가능한 시계로 검증하고, 부하 테스트와 분리한다.

## 기술 구성 제안

| 구성 요소 | 역할 | 도입 시점 |
|---|---|---|
| Java, Spring Boot | 애플리케이션 뼈대, 이후 API와 주문 로직 | 0단계부터 |
| MySQL | 로컬 연결 준비, 이후 주문 기록과 트랜잭션 | 0단계부터 |
| Docker Compose | 로컬 의존 서비스 실행과 재현 | 0단계부터 확장 |
| Spring Boot Actuator, Micrometer | 0단계 health, 1단계 지표 구성 | 0단계부터 |
| Prometheus, Grafana | 지표 수집과 대시보드 | 1단계 |
| k6 | 부하 생성과 응답 시간 측정 | 1단계 |
| Redis | 세션 저장소, 이후 조회 캐시·분산 요청 제한 | 1단계 세션, 2단계 캐시·요청 제한 |
| Kafka | 주문 요청의 비동기 처리와 재처리 | 3단계 |

0단계에서 Java 21, Spring Boot 3.5.16, Gradle 8.14.3, Spring Data JPA와 Flyway를 선택한다. 별도 Mock PG와 도메인·DB 기본 구조는 1-1 계약을 따르며 테이블·인덱스 상세는 1-2에서 점검한다.

### 함께 결정하는 진행 원칙

각 소단계를 시작할 때 AI는 목표와 범위, 미정인 기획·정책·설계 선택을 정리해 개발자에게 질문한다. 선택지에는 추천안과 이유, 주요 장단점을 함께 제시한다. 개발자가 답변해 확정하기 전에는 해당 결정에 의존하는 구현을 시작하지 않는다. 답변이 없다는 이유로 추천안을 확정된 것으로 간주하지 않는다.

이미 확정한 내용은 반복해서 묻지 않고 현재 단계에 적용되는 합의로 요약한다. 새로운 결정이 없으면 실행할 범위와 완료 기준을 제시하고 개발자의 진행 확인을 받은 뒤 구현한다. 사용자가 특정 범위를 명시적으로 맡긴 경우에는 그 범위의 실행 지시를 진행 확인으로 본다. 다만 미정 정책까지 임의로 결정하라는 위임으로 해석하지 않는다.

확정한 내용과 선택 이유는 관련 설계 문서에 기록한다. 구현 중 정책 변경이나 새로운 설계 선택이 필요하면 해당 작업을 멈추고 다시 함께 결정한다. 구현은 사용자가 해당 소단계의 구현 시작을 지시한 뒤 Orca의 `gpt-6.1-terra` 모델·`high` reasoning effort 워커에게 맡긴다. 주 에이전트는 사용자와 정책을 정하고 워커의 변경 사항·실제 산출물·검증 근거를 확인한다. 모델을 사용할 수 없으면 알리고 임의로 다른 모델로 대체하지 않는다. 실험 단계에서는 개발자가 실행 결과와 예상 결과를 비교하고 해석을 남긴다.

각 소단계가 끝나면 AI는 변경 내용, 검증 결과, 남은 문제를 보고한다. 다음 소단계로 자동 진행하지 않고 개발자와 다음 범위 및 미정 사항을 확인한다.

각 단계 문서의 체크리스트에서 정책 확정, 구현 시작 지시, 워커 구현, 주 에이전트 검증을 별도로 기록한다. `1-1 → 1-2`처럼 소단계 순서대로 진행하며 앞 단계의 합의가 있어도 현재 소단계에 새 결정이 필요한지 확인한다. 정책에 대한 동의만으로 구현 시작 지시를 받았다고 간주하지 않는다. 정책·설계 협의 단계는 주 에이전트가 사용자와 진행하고, 문서 확정은 코드 구현과 구분해 기록한다. 체크 완료 시 관련 결정 문서와 실행 명령·결과 등 근거를 남기며, 환경 문제로 검증하지 못한 항목은 완료 처리하지 않는다.

### 0단계: 프로젝트 뼈대

단일 애플리케이션과 Gradle Wrapper, 로컬 MySQL Compose, 환경변수 예제, JPA·Flyway 연결과 Actuator health를 준비한다. 도메인 패키지의 책임만 표시하고 업무 API·로직·테이블은 만들지 않는다. Redis, Kafka와 지표 수집·대시보드 등 전체 모니터링 구성은 포함하지 않는다.

완료 기준: 빌드와 최소 컨텍스트 테스트, Compose 설정 검증, 실제 MySQL 연결과 local 프로파일의 health 확인을 모두 통과한다. Docker를 실행할 수 없어 실제 연결을 확인하지 못하면 뼈대 구현과 MySQL 검증 대기를 구분해 기록한다. H2 기반 테스트로 MySQL 연결 검증을 대신하지 않는다.

현재 검증 상태: 1-2 워커가 Java 21 빌드와 실제 MySQL 8.4.7 연결, Flyway 초기화, local health를 확인했다. 주 에이전트가 Java 21 clean build·MySQL·앱 health·구조 검사를 독립 검증해 1-2를 완료했다. 다음 1-3은 별도 정책 점검·구현 지시 후 진행한다. 실행 방법은 [README](../README.md)를 따른다.

### 1단계: MySQL 기반 주문과 관측

판매 Spring 애플리케이션과 별도 Mock PG HTTP 서버를 사용한다. MySQL 트랜잭션과 조건부 수량 갱신으로 전체 판매 수량과 사용자별 한도를 지키고, 요청 식별자로 재시도를 구분하는 설계를 검토한다. 여러 번 주문을 허용하므로 주문 테이블의 이벤트·사용자 조합을 유니크로 제한하지 않는다. 동일 사용자의 동시 신규 주문에도 누적 구매 한도를 지켜야 한다. Mock PG 호출과 DB 커밋은 하나의 원자적 작업으로 보장할 수 없으므로 주문·결제 상태, 재고 점유·복원, 결제 재조회·재시도 경계는 확정한 1-1 계약을 따르고 구현 소단계에서 상세를 점검한다.

0단계의 Actuator health를 바탕으로 1-9에서 Micrometer 지표 노출, Prometheus와 Grafana를 연결한다. 관측 구성을 마친 뒤 1-11에서 k6로 기준 성능을 측정하고 DB 경합을 관찰한다.

기본 구현 후 API 인스턴스 2개가 같은 MySQL을 사용하도록 실행한다. 부하가 두 인스턴스 모두에 전달됐는지 확인하고, 단일 프로세스 내부 동기화에 의존하지 않는지 1단계에서 검증한다.

세부 작업과 소단계별 완료 기준은 [1단계 문서](stages/01-mysql-order.md)에서 관리한다.

1-7에서 실제 DB를 사용한 동시성 검증을 시작하고, 1-10에서 여러 인스턴스로 확장한다. 1-9의 관측 도구를 갖춘 뒤 1-11의 성능 기준값을 측정한다.

완료 기준:

- 한도보다 많은 동시 요청에도 초과 판매가 없다.
- Mock PG 전체 성공·장애와 요청 제한이 없는 정상 시나리오에서, 접수 기간 안에 서로 다른 유효 사용자 10,000명이 각각 수량 1개로 제품 1,000개에 요청하면 정확히 1,000건의 주문이 확정되고 잔여 수량은 0이다.
- 같은 사용자의 동시 주문에서도 이벤트별 구매 한도를 넘지 않고, 동일 요청의 재시도가 중복 주문·중복 결제를 만들지 않는다.
- API 인스턴스 1개와 2개에서 수량·중복 검증을 모두 통과한다.
- 접수 기간의 경계 시각과 종료 후 재시도가 이벤트 시간 정책을 따른다.
- DB 트랜잭션 내 저장 실패 시 같은 트랜잭션의 수량 변경도 롤백된다. Mock PG 결과와 DB 상태가 어긋난 경우는 정해진 조회·복구 절차로 수렴한다.
- 테스트 후 실제 DB 기록과 잔여 수량을 대조한다.
- 처리량, 오류율, 응답 시간과 실행 환경을 기록한다.

### 2단계: Redis 캐시·분산 요청 제한과 비교

1단계의 Redis 세션을 유지하고, 측정한 병목을 기준으로 분산 요청 제한과 조회 캐시를 추가한다. 수량·중복 여부의 원자적 사전 판정은 필요성이 확인되면 별도로 설계한다. Redis를 도입했다는 이유만으로 모든 주문 판단을 옮기지 않는다.

조회 캐시 실험과 주문 경로 실험은 분리한다. 주문 경로에서는 요청 제한을 끈 비교와 켠 비교를 구분한다. 요청 제한으로 거절한 요청이 늘어 응답 시간이 짧아진 결과를 주문 성능 향상으로 해석하지 않는다.

세부 작업과 소단계별 완료 기준은 [2단계 문서](stages/02-redis.md)에서 관리한다.

수량·중복 여부의 Redis 원자적 사전 판정은 기본 소단계에 포함하지 않는다. 2-6에서 필요성이 확인되면 MySQL과의 불일치 복구 설계를 먼저 작성하고 별도 소단계로 추가한다.

완료 기준:

- 같은 조건에서 변경 전후 성능과 DB 부하를 비교한다.
- 실제 주문 처리량, 요청 제한 비율, 최종 주문 결과를 함께 비교한다. 조회 캐시는 적중률과 조회 지연을 별도로 측정한다.
- 요청 제한이 없는 정상 시나리오에서 정확한 주문 수량 기준을 유지한다. 제한이 있는 실험은 거절 수와 재시도 정책을 기록하고 한도 미달 주문의 원인을 설명한다.
- 캐시·요청 제한 장애 시 동작을 각각 정하고 검증한다. 세션 인증 실패를 DB 처리로 우회하지 않으며, 인증된 사용자 식별 없이 주문을 허용하지 않는다.
- 캐시 만료와 Redis 재시작 후에도 DB의 주문 규칙이 유지된다.
- Redis 상태와 DB 기록의 차이를 검사하고 복구 방법을 기록한다.

### 3단계: Kafka 기반 비동기 주문

요청 접수와 주문 처리를 분리하고 접수 상태를 조회할 수 있게 한다. 소비자는 중복 메시지에도 안전하게 동작해야 한다. 재시도, 재처리, 실패 요청 보관 정책을 설계한다.

Redis 변경과 Kafka 전송은 하나의 DB 트랜잭션으로 묶이지 않는다. DB 저장 후 이벤트 유실 문제도 있다. 영속적인 접수 기록과 아웃박스 등 대안을 비교하고, 접수 응답을 반환할 수 있는 시점을 먼저 정의한다. Kafka 도입만으로 종단 간 정확히 한 번 처리를 보장한다고 설명하지 않는다.

3-3 이후의 작업 순서는 DB 영속 접수와 아웃박스를 사용하는 권장 초안을 기준으로 한다. 아직 확정된 전달 방식은 아니다. 3-1에서 Kafka 직접 접수를 선택하면 접수 원본, 상태 조회가 가능해지는 시점, 기간 내 접수 증명, 요청 유실·중복 대응을 포함해 3-3 이후 계획과 구조 문서를 먼저 수정하고 함께 확정한다.

세부 작업과 소단계별 완료 기준은 [3단계 문서](stages/03-kafka.md)에서 관리한다.

3-3만 끝난 상태는 접수·조회까지의 중간 결과이며 비동기 주문 서비스 완료로 보지 않는다. 3-1에서 정한 재처리와 순서 정책을 3-6까지 구현·검증한 뒤 전체 경로를 공개한다. 각 소단계의 국소 장애 검증을 먼저 하고, 4단계에서는 전체 구성에 걸친 장애·복구 실험과 포트폴리오 정리를 수행한다.

완료 기준:

- 접수 지연과 최종 주문 완료 지연을 각각 측정한다.
- 메시지 재전달과 소비자 재시작에도 초과 판매·중복 주문이 없다.
- 소비자 중단 시 적체를 관측하고 재개 후 처리 결과를 검증한다.
- 이벤트별 순서 보장과 병렬 처리의 한계를 설명한다.
- 접수 후 주문되지 않은 요청을 식별하고 복구한다.
- 종료 전 접수한 요청은 종료 후에도 처리되고, 종료 후 신규 요청은 거절된다.
- 복구 후 모든 접수 요청이 주문 확정·품절·처리 실패 등 정의된 최종 상태에 도달하는지 접수 기록과 대조한다. 미완료 요청 수는 0이어야 하며 처리 실패의 원인과 건수를 보고한다.

### 4단계: 장애 검증과 포트폴리오 정리

1단계에서 검증한 API 인스턴스 2개 구성을 기반으로 Redis 중단, Kafka 중단, 소비자 강제 종료, DB 저장 실패, 응답 유실 후 재시도를 재현한다. 복구 후에는 여러 인스턴스에서 초과 판매·중복 주문이 없는지 다시 확인한다.

완료 기준:

- 장애별 예상 동작과 실제 동작을 비교한다.
- 복구 후 DB 기록, 잔여 수량, 요청 상태를 대조한다.
- 복구 후 검증 기한 안에 모든 접수 요청이 최종 상태에 도달했는지 확인한다. 실패로 종결된 요청도 원인과 기대 결과를 대조하며, 모두 실패했다는 이유로 정합성 검증을 통과시키지 않는다.
- 대시보드, 실험 명령, 결과, 설계 선택 근거를 다른 사람이 재현할 수 있게 남긴다.

## 모니터링 계획

| 대상 | 관찰할 지표 | 확인할 문제 |
|---|---|---|
| HTTP API | 요청 수, 오류율, p50·p95·p99 지연 | 요청 폭주와 응답 악화 |
| 주문 업무 | 접수·확정·품절·중복·실패·요청 제한 건수, 미완료 요청 수, 대기 시간 | 업무 결과와 처리 누락 |
| JVM | 힙, GC, 스레드 | 애플리케이션 자원 병목 |
| DB 연결 풀 | 활성 연결, 대기 연결, 연결 획득 시간 | 연결 고갈 |
| MySQL | 쿼리 지연, 잠금 대기, 데드락 | DB 경합 |
| Redis | 명령 지연, 메모리, 연결 실패 | Redis 병목과 장애 |
| Kafka | 소비 지연, 발행 오류, 재시도와 실패 건수 | 적체와 처리 중단 |

애플리케이션 지표는 Micrometer로 수집한다. MySQL·Redis·Kafka 내부 지표는 단계에 맞춰 exporter 또는 해당 시스템의 지표 노출 방식을 추가한다. exporter가 필요한 지표를 Actuator만으로 관측할 수 있다고 가정하지 않는다.

Grafana에는 API 상태, 주문 결과, 비동기 처리 적체를 확인할 수 있는 대시보드를 만든다. 로그에는 요청 ID를 남기고 Kafka 도입 후 메시지에서도 추적한다. 사용자 ID와 요청 ID를 메트릭 라벨로 사용하지 않는다. 정합성은 메트릭만으로 판정하지 않고 DB 대조 쿼리로 검증한다.

초기에는 지표와 구조화 로그를 우선한다. 분산 추적과 로그 수집 서버는 여러 프로세스의 흐름 추적이 필요해질 때 추가한다. 알림 임계값과 성능 목표는 기준 부하 측정 후 정한다.

## 실험 방식

기본 시나리오는 Mock PG 전체 성공 조건에서 제품 1,000개에 서로 다른 사용자 10,000명이 각각 수량 1개로 요청하는 상황으로 시작한다. 이 숫자는 실험 입력이며 처리 성능 보장이 아니다. 같은 사용자의 반복 요청과 동시 요청을 별도 시나리오로 실행한다.

정상 수량 검증에서는 요청 제한을 끄고 모든 요청이 접수 가능 시간 안에 도달하도록 한다. 정확히 1,000건의 주문이 확정되는지 확인한다. 한도보다 적은 서로 다른 유효 사용자가 요청하는 시나리오도 실행해 모두 주문 확정되는지 확인한다. 이벤트별 구매 한도 설정·기본값, 같은 사용자의 동시 주문, Mock PG 결과별 시나리오도 따로 실행한다. 여러 수량 주문을 허용하면 주문 건수와 판매 수량 합계를 구분한다. 품절과 중복, 한도 초과, 결제 결과, 기간 외 요청, 요청 제한, 시스템 오류는 구분해 집계한다.

실험에는 커밋, CPU·메모리, 컨테이너 자원, 인스턴스 수, 데이터 초기화 방식, 동시 사용자 수, 실행 시간, 요청 패턴을 기록한다. 같은 조건에서 여러 번 실행해 편차를 확인한다. 로컬에서 부하 생성기와 서버가 자원을 공유한다는 한계도 명시한다.

API 접수 처리량과 최종 주문 처리량을 구분한다. HTTP 성공 응답 수를 확정 주문 수로 간주하지 않는다. 매 실험 후 판매 한도 초과, 사용자 중복, 잔여 수량과 기록 불일치를 검사한다.

비동기·장애 실험은 실행 전에 최종 결과를 기다릴 검증 기한과 예상 주문 수를 정한다. 장애 복구 후 접수 기록의 모든 요청을 최종 결과와 대조한다. 검증 기한을 넘겨 대기 중인 요청은 실패로 보고하며, 성공한 요청만 골라 결과를 집계하지 않는다. 요청 제한과 영구 실패로 예상 주문 수가 달라지는 경우에는 그 조건과 계산 근거를 함께 기록한다.

## AI 협업과 개발자 역할

| 담당 | 역할 | 남길 근거 |
|---|---|---|
| 개발자 | 요구사항과 성공 기준 결정 | 주문 규칙과 시나리오 |
| 개발자 | 설계 비교와 선택 | 결정 기록과 포기한 대안 |
| AI | 구현, 테스트와 실험 도구 초안 작성 | 검토 가능한 변경 사항 |
| 개발자 | 핵심 로직 검토와 설명 | 트랜잭션·Redis·Kafka 흐름 설명 |
| 개발자 | 부하·장애 실험 실행과 해석 | 원본 결과와 분석 |
| 개발자와 AI | 실패 원인 분석과 개선 | 재현 방법과 수정 전후 증거 |

각 단계에서 개발자는 구현 전에 예상 동작과 실패 지점을 적는다. 구현 후에는 핵심 코드를 설명하고 실험 결과가 예상과 다른 이유를 검토한다. 잘못된 AI 제안도 발견 근거와 수정 과정을 기록한다.

AI 사용 기록에는 작업 목적, 요청 요약, 생성 결과, 본인이 검토한 부분, 발견한 문제, 수정과 검증 결과를 남긴다. 생산성 향상 수치는 실제 측정한 경우에만 사용한다. AI 활용을 위해 제품 판매 서비스에 별도의 AI 기능을 넣지는 않는다.
